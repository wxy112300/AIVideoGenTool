状态：`Archived / 当前设置页重构范围（WP-00 至 WP-06）完成；Memory/Attention 后续工作另立 Plan`
归档日期：`2026-08-28`

计划类型：跨 renderer、Electron service、依赖管理、队列兼容和 UX 契约的分阶段重构

## 0. 计划目的

本计划用于把设置页重构拆成多个可以独立认领、独立验证和按顺序合并的工作包。它不是一次性实现说明，也不授权任何 agent 自行扩大产品范围。

本次重构的核心问题是：当前设置页把 ComfyUI 环境管理、Python/节点依赖、H3 加速组件和工作流级策略混在了一起，导致页面重复、修复按钮含义不清，并且后续接入新的 Attention 或 H3 内存优化时容易继续堆叠设置项。

目标不是增加更多设置，而是建立清晰的职责边界：

1. `ComfyUI 环境`负责 ComfyUI 实例、核心版本、运行时绑定、服务生命周期、兼容性和安全修复。
2. `节点与依赖`负责可安装的 custom node、Python 包以及可选运行依赖。
3. 当前阶段 H3 Attention 选择暂时保留在 Settings 的`性能与加速`页，不提前迁移；Memory 功能完成并通过验证后，再统一处理 Attention、Memory 和其他工作流策略。
4. H3 Memory Optimization 仍然是工作流级能力，按现有 Memory 计划逐步接入，不把它变成 ComfyUI 全局修复选项。
5. 应用目录、代理、队列策略等应用级设置不再和 ComfyUI 核心环境混在一起。

执行任何工作包前，agent 必须重新读取：

1. `git status --short --branch`

3. 本工作包涉及文件的当前 `git diff`

源优先级遵循仓库根目录 `AGENTS.md`：

4. 本计划和其他当前实现计划
5. 当前实现、测试和截图证据
6. 历史 prototype 与研究资料

本计划不替代三份正式契约。若执行过程中确认信息架构或持久化语义发生变化，先更新契约，再修改实现。

当前工作区在创建本计划时已经存在用户对 `docs/H3_MEMORY_OPTIMIZATION_INTEGRATION_PLAN.md` 的未提交修改。所有 agent 必须保留该修改；不得用历史快照覆盖该文件，也不得把它当作本次设置重构的并行编辑目标。

## 1.1 持续可用性契约

应用需要在重构期间持续可用，因此“每阶段可合并”是硬性条件，不是完成后的附加检查。任何工作包即使已经实现目标，也不能在没有通过本节门槛前合并到用户正在使用的分支。

需要明确的现实边界：不能保证同一个已经启动的 Electron 进程在代码被替换后无需重启就自动获得新代码；可以保证用户正在使用的 checkout 不被 agent 的半成品直接破坏，并保证每一个合并点都是可以启动、可以回退的完整版本。

### 运行方式

- 用户日常使用的 checkout 与 agent 工作区分离。agent 使用独立 branch/worktree，不直接在正在运行的 checkout 中编辑热点文件。
- 用户当前运行的版本在 agent 工作期间继续使用；只有经过门槛检查的完整提交才允许合并到日常 checkout。
- 合并后需要按应用行为安排一次受控重启；不能承诺 Electron 进程完全无重启热切换。
- 真实 ComfyUI 安装、Python 环境、模型和用户素材默认不作为 agent 测试夹具。安装、卸载、更新和修复只在明确的真实环境 smoke 阶段执行。
- agent 不得为了验证方便改动用户的 ComfyUI 核心、工作流、模型或历史数据。

### 每阶段必须满足的门槛

每个阶段结束时必须同时满足：

1. 当前功能路径仍可运行；新功能不可以替换掉尚未验证的旧路径。
2. 类型检查和相关聚焦测试通过；共享 renderer、IPC、store、queue 或 workflow 时，必须运行 `npm.cmd run verify`。
3. 生产构建可以完成，应用可以启动到设置页和主要业务页。
4. 失败时可以通过单个阶段提交执行 `git revert`，不能依赖不可逆的数据改写或手工恢复用户目录。
5. agent handoff 必须列出实际运行过的命令、结果、未验证事项和已知风险；“代码已完成”不等于“运行已验证”。

### 分阶段兼容策略

| 阶段 | 合并后的可用状态 | 必须保留的兼容措施 |
| --- | --- | --- |

| WP-03 | 新的 `ComfyUI 环境`页面可用，旧操作仍走原 controller/IPC | 保留字段 ID、tab 别名、保存协调器和旧服务动作 |

### 合并阻断条件

遇到以下任一情况，工作包必须停在 agent branch，不得为了推进进度合并：

- `npm.cmd run verify`、相关 focused test 或生产构建失败。
- 设置保存、路径选择、服务启动/重启、离线扫描或节点安装出现回归。
- 新旧页面或 IPC 对同一个字段形成两个写入真相。
- queue/history 迁移无法保证旧记录可读，或可能改变已排队任务。
- 修复操作的目标实例、备份、服务归属或失败恢复不明确。
- 需要直接改写用户 ComfyUI、模型、工作流或历史媒体才能通过测试。
- 发现其他 agent 或用户刚修改了同一热点文件，尚未完成 diff reconciliation。

### 失败后的处理

- 未合并的工作包：保留 branch 供分析，不污染用户正在使用的 checkout。
- 已合并但回归的阶段：优先对该阶段提交执行 `git revert`，再修复原因；禁止用 `git reset --hard` 清理用户工作。
- 持久化迁移：必须先添加读取兼容和备份，再启用写入新格式；不能发布单向迁移后再补救。
- 真实环境操作失败：保留日志和备份，恢复原服务状态，并把证据写入 handoff；不得把“没有复现”写成“已修复”。

## 2. 当前基线与证据

### 2.1 当前设置页的混合职责

生产 renderer 入口是 `index.html` 导入的 `src/main.ts`，设置页主要由以下文件组成：

- `src/renderer/contracts.ts`：`SettingsTab` 类型和设置页状态契约
- `src/renderer/pages/settings/page.ts`：设置导航、面板组合和大量卡片文案
- `src/renderer/pages/settings/view-model.ts`：扫描、服务、修复、依赖安装状态
- `src/renderer/pages/settings/fields-controller.ts`：tab 切换、焦点和滚动恢复
- `src/renderer/pages/settings/page-controller.ts`：路径、Python、实例选择和扫描操作
- `src/renderer/pages/settings/service-controller.ts`：启动、重启、停止和核心更新
- `src/renderer/pages/settings/environment-controller.ts`：环境修复、H3 加速安装和刷新
- `src/renderer/pages/settings/node-dependency-controller.ts`：节点及 Python 依赖安装/卸载
- `src/renderer/pages/settings/settings-save-coordinator.ts`：设置保存和环境刷新触发
- `src/core/locales/zh-CN.ts`、`zh-TW.ts`、`en-US.ts` 及对应 `.js` 镜像：用户可见文案
- `src/styles/06-settings-layout.css`：设置页布局与响应式样式

当前 tab 包含 `system`、`acceleration`、`video`、`lora`、`image`、`nodes`、`prompt`、`upscale`、`logs`。其中：

- `system` 同时包含 ComfyUI 安装实例、核心/数据目录、服务地址、Python、文件路径、代理、GPU 和队列策略。
- `acceleration` 同时包含 H3 Attention 选择、ComfyUI Python 选择、PyTorch/CUDA/Sage/Triton/KJNodes 状态和“一键升级/修复 H3 环境”。
- `nodes` 已经包含 `llama-cpp-python` 和自定义节点。
- `h3AttentionMode` 是设置字段，但入队和任务快照又保存了 Attention 状态，后续移动它会触及队列不可变快照。

### 2.2 现有后端能力不是一个通用修复按钮

`electron/services/environment.ts` 已经分别提供以下能力：

- 环境扫描和离线文件检查
- 多个 ComfyUI 安装实例发现与选择
- ComfyUI 服务启动、重启、停止和本地/远程归属判断
- Desktop 官方更新器调用
- 源码版的安全 `git pull --ff-only`
- 数据库、PyAV 和特定源码问题修复
- 自定义节点及 Python 依赖安装/卸载
- llama-cpp-python 安装/卸载
- H3 加速依赖安装

当前 `installAttentionAcceleration()` 会检查或修改 PyTorch/CUDA 组合、`comfy-kitchen`、KJNodes、Triton、SageAttention，并触发 CUDA 自检、服务重启和重新扫描。因此它是“加速依赖组合安装/修复”，不是 ComfyUI 核心损坏时的通用修复。

### 2.3 已有扫描架构可以复用

当前 `EnvironmentRefreshCoordinator` 已把刷新分成：

- `full`：完整扫描
- `runtime`：服务和运行时刷新
- `dependencies`：节点与依赖刷新

`EnvironmentScanResult` 已包含 ComfyUI 实例、核心版本、Python、GPU、节点、模型、llama、Attention、兼容性和问题列表。第一阶段应优先重新组织展示和动作归属，不要重复建立第二套扫描真相。

## 4. 版本和状态模型

### 4.1 三类版本必须分开

页面和后端不得把以下内容合并成一个“版本”：

1. ComfyUI 核心版本/提交号
2. ComfyUI Python、PyTorch、CUDA 运行时
3. custom node 和 Python 包版本

首版只承诺：显示当前值、显示可用更新路径、执行有边界的更新。任意版本降级、源码 checkout、完整回滚只有在备份和恢复机制准备好后才能加入，不得用简单下拉框伪装成已实现能力。

### 4.2 环境状态的四个独立轴

环境概览可以提供摘要，但详情必须保留四个轴：

| 轴 | 含义 | 典型状态 |
| --- | --- | --- |
| 核心 | ComfyUI 核心是否存在、版本是否兼容 | 已安装、版本过旧、无法识别 |
| 依赖 | Python 包和节点是否满足要求 | 缺失、已安装、版本不符、待修复 |
| 服务 | 当前 endpoint 是否在线及归属 | 在线、未启动、应用管理、外部管理、远程 |
| 验证 | API/schema/真实运行是否通过 | 未验证、schema 通过、运行失败、已验证 |

ComfyUI 停止时，离线文件扫描仍然有效；“服务未连接”不能误报成“文件缺失”。

## 5. 修复操作设计

### 5.1 修复按钮的语义

推荐主动作使用“修复检测到的问题”或“按检测结果修复”，不要使用没有范围说明的“修复所有环境”。

点击后应先生成可读的操作计划，至少显示：

- 目标 ComfyUI 实例
- 将修改的核心文件或 Python 包
- 是否停止当前应用管理的服务
- 备份位置和恢复策略
- 是否会重启服务
- 完成后的重新扫描和验证项目

只有明确属于安全修复的问题才可以进入自动执行；不确定的核心更新、用户自定义目录和远程服务必须停在诊断状态。

### 5.2 操作边界

后端能力保持逻辑分离：

| 操作 | 负责内容 | 不应偷偷做的事 |
| --- | --- | --- |
| 环境扫描 | 读取实例、文件、运行时和服务证据 | 不修改文件、不自动升级 |
| 核心问题修复 | 数据库、PyAV、明确的源码错误 | 不安装 H3 加速包、不替换工作流 |
| ComfyUI 更新 | Desktop 官方更新或源码安全更新 | 不强行覆盖 dirty checkout、不处理远程服务 |
| 节点/包修复 | 安装、重装、卸载选定依赖 | 不改变其他实例、不删除模型 |
| H3 加速依赖修复 | 明确的 PyTorch/Sage/Triton/KJ 组合 | 不声称修复全部 ComfyUI 损坏 |
| 服务操作 | 启动、重启、停止应用管理的本地服务 | 不杀远程服务、不改变已排队任务 |

### 5.3 安全不变量

- 离线扫描必须可用。
- 多实例选择不能被扫描或修复悄悄改变。
- 只停止应用拥有的本地 ComfyUI；远程服务保持不动。
- 替换或迁移前尽可能创建备份。
- 失败时保留原文件、错误日志和操作上下文。
- 修复完成后自动重扫；若服务原本在线，按原归属尝试恢复。
- 不删除或覆盖应用内部工作流 JSON。
- 不移动或删除模型权重、用户素材和历史媒体。
- Python 包安装必须使用当前选定 ComfyUI Python。

## 6. Attention 与未来能力原则

### 6.1 不为每个 Attention 新增设置页

后续能力应采用数据驱动的能力登记，至少记录：

- capability id
- 所属模型/工作流
- 依赖节点和 Python 包
- 支持的 ComfyUI/Python/runtime 条件
- 安装状态和运行验证状态
- 是否实验能力
- 与其他 Attention 的互斥关系
- 真实验证证据

当前阶段：环境页读取能力状态，节点与依赖页提供安装动作，现有 Settings 的`性能与加速`页继续提供 H3 Attention 选择。新增 Attention 不应再复制一套设置页字段和扫描逻辑；它应先通过 capability metadata 进入状态扫描和依赖卡片。

Memory 完成后的统一阶段才重新决定工作流策略选择的最终位置，并把 Attention、Memory、Spectrum、Turbo/SLA 的 requested/resolved/runtime evidence 统一起来。

### 6.2 H3 Attention 的迁移风险

当前 `h3AttentionMode` 是全局 Settings 字段，但 `src/core/queue-task-factory.ts`、`electron/queue-enqueue.ts`、`src/core/workflow.ts` 和 queue recovery/history 已经使用任务级 `attentionMode`。

因此：

- 页面搬迁阶段不得直接删除 `h3AttentionMode`。
- 当前阶段不得把 Attention 选择迁移到创建页，也不得借页面重组提前改变全局设置语义。
- Memory 完成前不得启动 Attention 的全局到任务级统一迁移；新 Memory 字段可以按 Memory 计划独立增加，但必须继续读取现有 Attention 快照。
- 后续统一迁移必须增加 draft/task 的 requested state 和 resolved state。
- 已排队任务必须保持原执行快照。
- 旧 queue/history 记录需要兼容读取。

### 6.3 H3 Memory Optimization

遵循 `docs/H3_MEMORY_OPTIMIZATION_INTEGRATION_PLAN.md` 的现有用户修改和能力边界：

- 它是 H3 工作流能力，不是 ComfyUI 全局修复能力。
- 放在创建页 H3 高级设置或对应计算/增强区域。
- 首版由 gate 控制，默认状态不能凭静态扫描直接宣称已生效。
- 不和 Spectrum、SLA、Sparse Attention 或 async offload 混成一个开关。
- 环境页只显示节点/依赖/运行证据。
- 在 Memory 功能完成前，不要求同时迁移现有 Attention 设置；Memory 的实现与 Attention UI 迁移分开验收。
