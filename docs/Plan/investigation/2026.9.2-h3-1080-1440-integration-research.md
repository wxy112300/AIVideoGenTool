# H3 1080p / 1440p 接入调查

> 状态：当前实施决策输入，不代表 1080p / 1440p 已产品化。
>
> 基线：JointAV producer、History 管理和基于 committed JointAV 的 720p / 768p bilinear latent 二次采样已接入。高分辨率选项仍保持关闭，直到本文对应的真实 Gate 通过。

## 1. 结论

1080p 和 1440p 必须按两类入口分别实现，不能只是扩大一个 resolution union：

| 入口 | 1080p | 1440p |
| --- | --- | --- |
| Create | H3 单阶段高分辨率直出；必须有独立资源 profile 和真实 smoke | 对用户是原生 1440p 生成；内部固定 720p 首遍 + H3 learned latent 二采 |
| History → Upscale | 从兼容 committed JointAV 做 H3 latent 二采 | 从兼容 committed JointAV 做 learned latent 二采，并默认采用时空分块以控制 24GB 峰值 |

不得把 Create 1440p 描述成单阶段直出，也不得把 SeedVR2、MP4 像素超分或 bilinear latent 插值冒充 learned H3 高分辨率路径。

推荐实施顺序：

1. History `720/768 → 1080` learned 3D 二采；
2. History `720/768 → 1440` 的时空分块二采；
3. Create 1080 单阶段短片 profile；
4. Create 1440 复合任务，共用第 2 步的 second-sampling service；
5. 每档通过后再研究 `480/540 → 1080/1440`，不作为首发默认源。

## 2. 当前本机证据

已确认环境：ComfyUI 0.33.0、Python 3.12.11、Torch 2.10.0+cu130、RTX 4090 24GB。

已安装：

- `h3-latent-upscaler`，固定 revision `a5ed6e9586f0b14250a0018f78568e0076e4bd9d`；
- `LocalVideoStudio-H3` JointAV serializer/loader；
- 现有二采 graph 所需 AV split/concat、conditioning resize、分支 noise 和 audio sigma 节点此前已通过 live `/object_info`。

未安装：

- H3 learned 3D upscaler 权重；`models/latent_upscale_models` 当前只有 `ltx-2.3-spatial-upscaler-x2-1.0.safetensors`，不能用于 H3；
- MMH3 Ultimate Upscale / Split Upscale 节点。

本轮调查时 ComfyUI 未运行，因此没有新增 live `/object_info` 或 1080p / 1440p 执行证据。

## 3. 上游事实

### 3.1 当前 bilinear 二采

`rockerBOO/h3-latent-upscaler` 的 GPL-3.0 节点解决了 H3 AV NestedTensor、CONST flow noise、audio sigma 和 conditioning 对齐问题。其 README 明确把 `scale_by=1.5`、bilinear、15 steps、denoise 0.4 称为起点而非调优结论。

本项目当前 720p / 768p 路线属于这一类。它已证明二采结构和 JointAV 生命周期可行，但 bilinear/bicubic 会出现 ghosting / double-image，不能据此直接宣称高质量 1080p / 1440p。

### 3.2 Learned 3D upscaler

`LBH-123-AI/Minimax_h3_latent_Upscaler` 权重模型卡声明 Apache-2.0，提供约 691 MB 的 BF16/FP16 safetensors，支持连续 1.0–4.0 倍。训练分布以 2 倍为主，并覆盖 1.5、2.5、3、4 倍和任意中间倍率。

companion ComfyUI 节点支持目标尺寸、32 像素对齐、temporal chunking 和执行后卸载；README 明确说明它节省首遍时间而不降低最终高分辨率 refinement 的峰值显存。

阻塞项：`LBH-123-AI/Comfyui_Minimax_h3_latent_Upscaler` 当前仓库页面仍未声明 LICENSE。权重许可不能替代节点源码许可，普通用户自动安装继续 fail closed。

### 3.3 高分辨率分块

`bbaudio-2025/Comfyui-MMH3-UltimateUpscale` 当前声明 MIT，提供 temporal chunk + spatial tile + overlap/stitch，支持 learned 3D 或 model-free interpolation，并保持原 audio latent。其 24GB 起始建议为 576–768 像素 tile、136–170 帧 chunk。

这使 1440p 在 24GB 上有了明确的候选执行形态，但仍需审计：

- 代码包含从其他社区实现改造的 learned upscaler / split 逻辑，必须复核第三方 provenance；
- 当前项目二采会按 audio sigma 重新采样 audio，而 Ultimate 路线原样保留 audio，产品 contract 必须明确选择并做 A/B；
- tile seam、色偏、快速运动断裂和时间边界需要真实视频检查，不能仅靠节点 README；
- 当前项目队列需要阶段进度、取消、恢复和 partial cleanup，不能把长时间单节点黑箱直接视作完整集成。

### 3.4 Native Engine 只能作为能力证据

X-MinimaxH3 1.0.0 声明 RTX 4090 / 24GB INT8 可进行最高 1080p × 15 秒首遍和最高 1440p 二采，并公开了 720p 与 1440p 二采对比。它使用独立 Native Engine、INT8 streaming/compact backend 和不同 Torch 工具链。

这些结果证明目标在同级硬件上可达，但不证明本项目的 ComfyUI FP8/INT8 workflow 已达到相同资源边界。不能用其 smoke 替代本项目 Windows + ComfyUI smoke，也不应为了该能力引入第二个应用运行时。

## 4. 几何合同

高分辨率交付继续使用“名义短边 + 实际 32 像素网格尺寸”。以 16:9 为例：

| 源 | 目标档 | 当前 H3 网格算法的实际输出 |
| --- | --- | --- |
| 864×480 | 1080p | 1952×1088 |
| 864×480 | 1440p | 2592×1440 |
| 1280×720 | 1080p | 1920×1088 |
| 1280×720 | 1440p | 2560×1440 |

UI、queue snapshot、History 和输出文件名必须显示/保存实际尺寸。目标档不能被当作精确像素高度。

## 5. 产品 Gate

### Gate A：History 1080 learned 二采

- 明确许可的 learned node 实现和固定 revision；
- H3 BF16/FP16 权重固定 revision、bytes、SHA-256、catalog 与离线扫描；
- live `/object_info` 精确 schema；
- learned graph 构造测试，不与 bilinear provider 混淆；
- 720/768 源各至少一次短片真实 smoke，验证视频、音频、JointAV 和 lineage；
- 记录峰值 VRAM、shared GPU memory、RAM、逐阶段耗时和实际几何。

### Gate B：History 1440 分块二采

- Gate A 全部通过；
- 固定 tile/chunk/resource plan，queue recovery 不随重启后瞬时空闲显存漂移；
- 取消、失败、重试、partial 文件清理和 final JointAV commit；
- 5 秒与至少一个较长样例检查 seam、色偏、主体一致性、音频和时间边界；
- 24GB 下不进入不可控 shared-memory thrash。

### Gate C：Create 1080 单阶段

- 新建 H3 delivery plan，而不是扩大全局 Draft resolution 语义；
- FL2VA Base 首先验证，Ref2VA 和 LoRA 分别门禁；
- 1080 短片直接采样输出 MP4 + 单份 `final-clean-av`；
- 按帧数和实际像素建立资源上限，不能照搬 Native Engine 的 15 秒声明；
- 不可用时显示精确原因，不静默回退到 768p 或 post-upscale。

### Gate D：Create 1440 复合任务

- 固定 720p 首遍，提交 `first-pass-clean-av` checkpoint；
- 第二阶段复用 Gate B 的 service；
- 二采失败时保留首遍结果用于重试，但不得将其标记为 1440p 成功；
- 最终提交独立 `final-clean-av`，两份 artifact 以 lineage 关联；
- UI 只展示一个 1440p 交付任务，Queue/History 可查看真实阶段。

## 6. 当前决定

- 720p / 768p bilinear H3 二采维持现状，作为已集成的基础路径。
- 1080p / 1440p 暂不加入普通用户 UI。
- 下一实现包应先解决 learned 节点许可/替代实现和 720/768 → 1080 的最小真实 smoke。
- 1440p 优先采用可恢复的时空分块路线，不尝试把当前整幅 bilinear graph 直接放大到 1440p 后靠 offload 硬撑。
- Create 1080 和 Create 1440 是两个不同 delivery plan；前者 direct，后者 composite。
