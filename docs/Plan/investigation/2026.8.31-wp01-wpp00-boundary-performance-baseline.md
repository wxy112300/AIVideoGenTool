## 0. 调查结论

目前“操作卡顿、交互不顺、启动慢”更像渲染/状态/启动边界的工作量问题，不能先归因于“缺少动画”。动画可以改善等待的主观反馈，但不会减少以下已存在的工作：整页 root 替换、历史卡片全量 DOM 构造、全量 controller teardown/rebind，以及队列进度下的完整状态持久化和 IPC 快照。

本轮可安全自动测到的唯一性能数值来自现有 jsdom History 500 条 fixture：四种 History 变体都渲染 500 张卡片；DOM parse 代理耗时为 `247.01–295.26 ms`，controller mount 代理耗时为 `45.88–95.40 ms`。这是合成测试环境的代理值，不是 Electron/Chromium GUI 的 Long Task，也不能直接当作用户 cold-start 时间。

基于当前证据，下一轮应该优先刻画和测量：

1. **Confirmed path / 合成代理已测到**：History 页把 500 条记录一次性变成完整 markup，再由整页渲染器写入 `root.innerHTML`；这在现有 fixture 中是最大主线程代理成本。
2. **Confirmed path / 实际成本未测**：队列进度回调调用 `updateTask`，每次都会 `JsonStore.update`（完整 JSON 持久化）并 `sendState`（完整 `AppState` 快照）；即使 renderer 侧随后只做局部 Queue patch，主进程序列化、磁盘写入、structured clone 和 IPC 负担仍存在。
3. **Strong inference / 尚无时长**：`app.whenReady` 到 `createWindow` 之间串行等待 `store.load`、默认素材目录 materialize、History output path restore、IPC/media protocol 注册；窗口创建后又并发进行 ComfyUI runtime profile takeover。这个顺序很可能影响启动感，但当前没有真实 cold/warm 计时。

真实 Chromium layout/paint/decode、IPC bytes/frequency、state JSON 大小、ComfyUI 启动、first usable 和 background-settled 仍是 **Unknown / Not measured**。本报告不提前设计 HTTP、通用 scheduler、框架替换或大规模动画方案。

### 2.4 `sendState` 和整页 render 的触发源

#### Main/queue 的 state 发送

`sendState` 总是将传入的完整 `AppState` 通过 `state:changed` 发送；它只对 queue signature 做日志去重，不对 payload 做差分。当前调用路径包括：

- `electron/main.ts`：draft/image draft 保存、settings 保存、history/image-history 操作、image asset 或 runtime 相关 state 变化，以及 queue composition 的 `updateTask`/`setQueueLifecycle`。
- `electron/queue-enqueue.ts`：video/extension/image/upscale 入队后的 state。
- `electron/queue-ipc.ts`：queue update/remove/move/reorder/duplicate/randomize/pause-boundary/reset。
- `electron/queue-worker.ts`：start/continue/pause/cancel 生命周期。
- `electron/queue-executor.ts`：claim、task stage/progress、completion/failure/recovery；其 progress callback 会进入 `updateTask`。

`updateTask` 的当前顺序是：`store.update` → `persist`（JSON.stringify + 临时文件/replace）→ snapshot（structured clone）→ `sendState(next)`。视频/extension 的 `waitForTask` progress callback 直接 `void updateTask(task.id, { progress, stage })`；图片批次有约 2 个百分点的 renderer-facing gate，但仍会反复执行上述 store path。回调频率、state JSON 大小和每次耗时本轮没有测量。

#### 整页 render 触发路由

`src/main.ts` 的 `render()` 只调用 `rendererApp.render()`；`renderer-app` 通过 lifecycle cleanup 后进入 `render-coordinator`。触发来源分为：

- bootstrap 初次 runtime/state/version 准备后的 render，以及 bundled workflow finally 的 render。
- route、Create mode、History kind/layout/detail/back、image preview dimension 改变。
- Create 的 media/prompt/model/reference/workflow 操作和必要的 save 后刷新。
- Queue action、upscale、settings form/scan/install/service 状态；高频 Queue preview/progress 本身尽量走 live patch。
- History filter/action/version/detail 变化，以及 history controller 的明确 `requestRender`。
- `state-events.ts` 在非输入编辑、非 draft save、History 可见内容变化、或无法保持 queue layout 时的 `requestRender`。
- runtime event 在 Create/Settings 页的 `requestRender`；environment/custom-node coordinator 的 snapshot render。

可复核命令：

```powershell

```

#### Full render 的具体工作量和 owner

`src/renderer/render-coordinator.ts` 的 full render 顺序是：保存 History/Queue 局部上下文 → 捕获 focus/playback → 停止当前渲染出的全部 `<video>` → `root.innerHTML = renderShell(...)` → icon/shell/page/controller/overlay/log/scroll/playback/focus 重新绑定。因而一次整页 render 不是只改一个文本节点，而是会触发 DOM 替换、controller cleanup/rebind、media listener/observer 重建和 focus/playback restore。

| hotspot | owner | 当前证据/风险 |
|---|---|---|
| full root replacement | `src/renderer/render-coordinator.ts` | 所有未被 state-events gate 的 render 都会走；真实 browser layout/paint 尚未测 |
| state event routing | `src/renderer/state-events.ts` | 已有 Queue live patch、输入保护、History skip；分支正确性需 characterization tests 固化 |
| History markup | `src/renderer/pages/history/page.ts` | `projects.map(...).join("")` / `orderedAssets.map(...).join("")`，500 条全部进入 DOM |
| History masonry | `src/renderer/pages/history/layout-controller.ts` | 读取卡片 geometry，批量 `replaceChildren`；列计算已纯化，但 full card set 仍存在 |
| History media | `src/renderer/pages/history/media-controller.ts` | 为所有 media surface 建 listener/observer；当前 loader/warmup 由 view 驱动 |
| History media I/O | `src/renderer/pages/history/media-helpers.ts` | image cover decode/save 和 video cover scheduler；真实文件/IPC/decode 未测 |
| root composition | `src/main.ts` | 同时组装 queue/history/environment/live status 和全局 handlers；共享调用 hotspot |
| main state boundary | `electron/main.ts` + queue modules | full state snapshot、持久化和 event 发送；高频 progress 的 cost 未测 |

## 3. WP-P00：启动、后台和 History 性能基线

### 3.1 P00 marker 定义与当前 seam

下表先定义下一轮应统一使用的含义，再标明当前实现是否存在可记录 marker。现有日志名称保持原义，不能把“有日志”误报成完整 lifecycle duration。

| marker | 本计划定义 | 当前最接近的 seam | 当前状态 |
|---|---|---|---|
| process-ready | Electron `app.whenReady().then` callback 开始；不等于 ComfyUI child process ready | `app.whenReady` callback + `app.ready` log | **Available as event, duration Not measured** |
| state-loaded | `JsonStore.load` 完成并完成默认 image input library materialize | `app.state-loaded` log | **Available as event**；当前 log 发生在 `restoreHistoryOutputPaths()` 之前，因此不等于完整 startup state ready |
| window-created | `createWindow` 开始/BrowserWindow 构造完成 | `createWindow` entry；`window.created` log 在 `new BrowserWindow` 之前 | **Available as log, but marker placement is imprecise** |
| DOM-ready | BrowserWindow `webContents` 的 `dom-ready` | 没有 listener | **Not measured / no current marker** |
| first-usable | renderer 已取得初始 state/runtime/version，完成首个 shell render，route controls 可交互 | `bootstrap.ts` 的 `options.render()`；capture harness 等 `.app-shell` | **Not measured**；`.app-shell` harness wait 不是应用时长 marker |
| background-settled | startup 中非首屏的 runtime profile alignment、environment refresh、performance refresh、bundled workflow inspect 都到达成功/失败终态 | detached `alignLocalComfyUiRuntimeProfile`、bootstrap `refresh*`/workflow chain | **Not measured**；当前没有 aggregate join 或 terminal marker |

### 3.2 当前 startup 顺序

#### Main startup（窗口前的串行段）

```text
module load
  → requestSingleInstanceLock / crash reporter / protocol setup
app.whenReady callback
  → app.ready log
  → set application menu
  → new JsonStore(userData/studio-state.json)
  → await store.load()
       read JSON / parse / migrate / normalize / possibly persist
  → await materializeDefaultImageInputLibraryDirectory()
  → app.state-loaded log
  → await restoreHistoryOutputPaths()
  → registerMediaProtocol()
  → registerIpc()
  → createWindow()
       window.created log currently before BrowserWindow constructor
       attach close/render-process/unresponsive/load-failed listeners
       loadURL(dev) or loadFile(production)
  → detached alignLocalComfyUiRuntimeProfile(settings)
```

`store.load()` 的 fallback 还可能执行 corrupt-file backup、重置 defaults、persist；正常路径会进行 history/imageHistory/queue/draft/settings migration and normalization，并在必要时 persist。以上 filesystem/JSON 的数据依赖 state 文件大小，当前没有实际冷启动时长。

#### Renderer bootstrap

```text
window.studio.getState()
  → loadUiLocale(state.settings.uiLocale)
  → setRendererState(initialState)
  → Promise.all(getAppVersion, getComfyRuntimeState, getPromptRuntimeState)
  → set runtime/version/title
  → options.render()                         # first render request
  → detached refreshPerformanceMetrics()
  → detached refreshEnvironment(settings)
  → getBundledWorkflow(...)
       cache / optional inspectWorkflow
       finally options.render()              # possible second render request
```

`render-coordinator` 的 render body 还可能等待 Create/Settings prompt pack 动态加载；当前没有 render start/end marks。

#### Shutdown 顺序

```text
BrowserWindow close
  → preventDefault unless allowWindowClose
  → inspect migration / running task / worker / native prompt / dirty settings
  → no work + no dirty: finishWindowClose()
  → otherwise window:close-requested overlay
       renderer responds window:close-response
       finish-tasks: interruptForExit(true)
           /interrupt + worker/prompt settle (up to 15s wait)
       force-exit: interruptForExit(false)
  → releasePromptRuntime
  → forceStopComfyProcesses
  → allow close, destroy window, app.quit (non-darwin)
window-all-closed → app.quit (non-darwin)
```

这是必须保留的 lifecycle contract；本轮没有改变它，也没有为了基线启动或停止真实 ComfyUI。

### 3.5 未测项与最小 instrumentation allowlist

下列项目必须标为 Not measured，不能从当前 logs 或 jsdom 数字推断：

- Electron process-ready→state-loaded→window-created→DOM-ready→first-usable 的 cold/warm p50/p95。
- state file 大小、JSON.parse/normalize/persist、`structuredClone`、IPC payload bytes/frequency。
- Chromium Long Task、style/layout/paint、History scroll/return、video/image decode 和真实文件 cover I/O。
- Create typing/selection、Queue high-frequency progress、Settings scan/install 的真实 frame loss。
- ComfyUI process ready、runtime profile takeover、environment scan 和 background settle。
- 无动画对主观等待感的独立贡献；动画实验不得代替上述 measurement。

下一 WP-P00 只允许下列 instrumentation；先记录原始数据，再讨论实现：

1. **Main startup marks（仅 `electron/main.ts`）**：使用 monotonic clock 记录 `whenReady-entry/app.ready`、`store.load-start/end`、`materialize-start/end`、`state-loaded`、`restoreHistoryOutputPaths-start/end`、`registerMediaProtocol`、`registerIpc`、`createWindow-entry`、BrowserWindow constructed；不改变 await 顺序或业务行为。
2. **WebContents marks（仅 `electron/main.ts`）**：在当前 `mainWindow.webContents` 增加一次性 `dom-ready`、`did-finish-load`、已有 `did-fail-load` 的 structured dev/test record；不将 ready-to-show 误当 DOM-ready。
3. **Renderer marks（仅 `src/renderer/bootstrap.ts`、`src/renderer/render-coordinator.ts` 的 test/dev guarded seam）**：记录 `getState` resolve、runtime/version Promise resolve、首个 render request/start/root replacement/bind-complete、workflow finally render；使用可注入 clock，默认关闭。
4. **Long Task/render counts（仅 dev/test harness）**：可选 `PerformanceObserver({type: "longtask", buffered: true})`；记录 render request count、full root replacement count、单次 root/render duration。没有 Chromium observer 输出时保持 Not measured。
5. **State boundary counters（仅 `JsonStore`/queue test seam）**：记录 `JSON.stringify` 字节数、persist duration、snapshot/IPC dispatch count；不得改变持久化频率、队列语义或 payload shape。
6. **History reuse**：继续使用 `createHistoryPerformanceFixture(500)`；只追加 test-only scroll/return 和 optional long-task counters，不修改既有 fixture/生产 media scheduler。
7. **Matrix**：至少 empty/500 History，Create input，Queue progress，page switch，History mount/scroll/return；cold 与 warm 各自独立记录，真实 Electron 与 jsdom 输出分开。
