## History 500 performance（actual，非 before/after claim）

对同一 500 video + 500 image fixture，6 次 packaged run 均完成四种列表操作与 video/image detail return。操作耗时为最小/平均/最大毫秒；`max Long Task` 是该操作窗口内 Chromium 暴露的最大值：

| 操作 | samples | operation duration | max Long Task | detail scroll error |
| --- | ---: | ---: | ---: | ---: |
| video / masonry | 6 | 322.3 / 337.1 / 349.3 | 无条目 | 0px |
| video / album | 6 | 539.7 / 572.5 / 624.7 | 205ms | 0px |
| image / masonry | 6 | 616.3 / 672.6 / 777.9 | 305ms | 0px |
| image / album | 6 | 491.1 / 506.9 / 547.6 | 128ms | 0px |
| video / detail return | 6 | 912.7 / 1091.7 / 1203.4 | 236ms | 0px |
| image / detail return | 6 | 935.8 / 977.6 / 1042.6 | 251ms | 22px（4/6 次） |

36 个操作均实际执行，document/body 横向 overflow 为 0；Long Task budget `<=50ms` 在有条目的操作上失败，最高约 305ms，不能声称 C04 达到性能预算。History detail return 的图片滚动误差 4/6 次为 22px，超过既定 `<=8px`。这两项是测量暴露的独立修复入口，按计划不在 C04 内顺手修改。

原始 trace：代表性 cold sample 生成 startup trace（empty、history-500、legacy）以及 history performance trace；截图和路径均在 manifest 对应 run 目录。trace 不是 jsdom benchmark，也没有被解释为相对 0.56.2 的提升；当前仓库没有同机、同参数、同采集方式的 P00 before baseline。
