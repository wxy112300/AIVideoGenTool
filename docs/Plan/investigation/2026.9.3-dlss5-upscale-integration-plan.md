# ComfyUI-DLSS5 调研与接入计划

> 状态：Proposed / static research only
>
> 调研日期：2026-09-03
>
> 上游基线：`HECer/ComfyUI-DLSS5` v0.2.2，release commit `310524aa283602832cbdd827ce4e35565c859a7e`
>
> 本文是实施决策与验证计划，不代表 DLSS Super Resolution、Neural Rendering 或任何插帧能力已经接入、检测通过或真实运行成功。

## 1. 结论

建议接入。安装体验采用一个完整的 **ComfyUI DLSS5** 依赖卡和一次用户主动触发的下载任务：节点仓库、当前 ComfyUI Python 中的 requirements、VapourKit、SR/NR DLL 与本机配置都由这一项编排，不在界面上拆成多张运行时卡，也不要求用户另装 Python。能力开关仍要区分 SR、NR 和不存在的 FG，避免一个模糊选项改变任务语义。

首发候选应仅为 **DLSS Super Resolution（实验性）**，作为 History 成功视频版本上的新 Upscale provider，与 Real-ESRGAN、FlashVSR、SeedVR2 和 H3 native second sampling 并存。只有在本机完成相同素材、相同输出几何的真实基准测试后，才能把它标成“最快”或设为默认。

| 能力 | 上游 v0.2.2 现状 | 本项目建议 |
| --- | --- | --- |
| Super Resolution | 已提供 2×、3×、4×，需要色彩、深度和运动向量输入 | 第一阶段 PoC 和首发候选 |
| Neural Rendering | 已提供 NGX Feature 18 的实验性增强，可单独运行或接在 SR 后 | 独立实验 Gate，不与 SR 就绪状态绑定 |
| Frame Generation / 插帧 | **未实现**；没有 FG 节点、运行时或示例 workflow | 不纳入本次承诺；继续使用现有 RIFE |
| Ray Reconstruction | **未实现**；上游能力名是 experimental Neural Rendering，不是 RR | 产品文案不得称为 Ray Reconstruction |

当前不能确认“速度比其他所有模型快很多”。上游没有与 SeedVR2、FlashVSR、Real-ESRGAN 的同条件吞吐对比；Easy pipeline 还会执行 Depth Anything 与光流/RAFT，这些预处理可能成为主要耗时。速度判断必须拆成纯 SR、导引生成、编码和完整端到端四段实测。

### 1.1 接入对象和所有权

本计划的节点实现明确采用 **原版 `HECer/ComfyUI-DLSS5`**，固定到经过本项目验证的 release/commit。应用不 fork、不复制节点源码、不建立自己的 DLSS5 节点仓库，也不把 `DLSS5oneclick`、`DLSS5-Swapper`、`ComfyUI-DLSS5-NR` 或其他实现作为运行依赖。

“ComfyUI DLSS5 整包”指本应用中的一张产品依赖卡和一套安装编排，不是我们重新包装出来的第三方节点发行包：

| 层 | 所有者/来源 | 本项目职责 |
| --- | --- | --- |
| ComfyUI 节点、guide 节点、VapourSynth bridge 调用 | `HECer/ComfyUI-DLSS5` | 从原仓库安装固定 revision，扫描并验证节点 schema |
| 产品 workflow adapter | Local Video Studio | 构造 API-format graph，接入 Upscale queue、History 和进度 |
| 安装卡与事务 | Local Video Studio | 复用现有依赖安装队列，编排节点、requirements、runtime、日志、恢复和复检 |
| 原生 runtime | 固定的外部 Release 资产 | 用户点击后下载；本仓库和应用安装包不携带 DLL |
| Depth Anything 权重 | 官方模型源 | 只由用户下载 `model.safetensors` 并放入标准 ComfyUI 模型目录；配置元数据由应用内置，供 HECer guide 节点消费 |

截至 2026-09-03，HECer v0.2.2 是本产品目前最合适的社区候选：它已发布到 Comfy Registry，并在一个节点包中覆盖 SR 2×/3×/4×、实验 NR、Depth Anything/VDA、RAFT、短/长视频策略、示例 workflow 和运行时诊断。这个判断是“功能覆盖与产品适配度最高”，不是社区规模、速度或画质第一的证明；后两项仍以 WP2 的同条件实测为准。

## 2. 上游究竟做了什么

它不是 TensorRT、ONNX 或普通 PyTorch Upscaler。运行链路是：

```text
ComfyUI IMAGE batch
  -> Python / NumPy 临时文件或内存映射
  -> VapourKit 内置执行器 + VapourSynth
  -> D3D12 wrapper
  -> NVIDIA DLSS SR / experimental Neural Rendering DLL
  -> IMAGE batch
  -> VideoHelperSuite 编码
```

因此：

- 不需要 TensorRT；
- 只支持 Windows 10/11 x64 + NVIDIA RTX + D3D12；
- 原生 DLL 在独立子进程/运行时中执行，但仍属于高风险本机原生代码；
- ComfyUI 仍会持有完整输入和输出 `IMAGE` batch；长视频并未实现 file-to-file streaming；
- `Persistent full sequence` 只消除原生 chunk reset，不解决完整 batch 的 RAM/临时磁盘压力；
- `Bounded overlap-add` 能限制原生窗口，但会重复处理 overlap，且上层 ComfyUI batch 仍然存在。

上游只明确报告了 RTX 5090 上的本地验证。RTX 20/30/40/50 的可用性不能根据品牌名称推断，必须绑定 GPU、驱动、`nvngx_dlss*.dll`、VapourKit wrapper 和节点 revision 逐组验证。

## 3. 节点和 API 合同

上游的示例 JSON 是 ComfyUI 前端 workflow 格式，不可直接提交到 `/prompt`。本项目必须维护自己的 API-format builder，并通过运行中的 `/object_info` 核对节点 class type、输入名和枚举。

### 3.1 生产候选节点

| Class type | 用途 | 关键输入 | 输出 |
| --- | --- | --- | --- |
| `DLSSSuperResolution` | 只执行 SR | `image`、`depth`、`motion_vectors`、`scale`、`quality` | `IMAGE`、runtime report |
| `DLSS5EasyPipeline` | 自动导引 + SR/NR/组合 | `image`、`scenario`、`operation`、`scale`、`quality`、`look`、`effect_strength` | `IMAGE`、runtime report |
| `DLSS5NeuralRendering` | 只执行实验性 NR | style/intensity/structure/mask，以及成对可选的 depth/motion | `IMAGE`、runtime report |
| `DLSS5FullPipeline` | SR 后接 NR | SR、窗口模式和 NR 全部参数 | `IMAGE`、runtime report |

### 3.2 导引、安装和诊断节点

| Class type | 用途 |
| --- | --- |
| `DLSS5DepthAnythingV2` | 单帧深度估计；权重由独立 Depth Anything 模型卡准备 |
| `DLSS5VideoDepthAnything` | 32 帧窗口的时间一致视频深度；源码/权重由 Depth Anything 模型卡准备 |
| `DLSS5FlashDepth` | 隔离环境中的可选高分辨率深度后端 |
| `DLSS5OpticalFlow` | CPU Farneback current-to-previous 光流 |
| `DLSS5RAFTFlow` | TorchVision RAFT Small/Large；首次运行下载权重 |
| `DLSS5TemporalDepthStabilize` | 使用运动向量重投影并稳定深度 |
| `DLSS5RuntimeStatus` | 报告 SR/NR Python、wrapper 和 runtime 路径 |
| `DLSS5RuntimeSetup` | 下载固定 VapourKit 并写本机 `runtime/config.json` |

运动向量方向是 current-to-previous；R/G 表示 X/Y，`0.5` 表示零运动。接反方向或错误缩放可能造成拖影，不能只检查节点是否完成。

### 3.3 初始 PoC workflow

第一轮只验证视频 SR，不开启 NR：

```text
VHS_LoadVideo
  -> DLSS5DepthAnythingV2 (Small, temporal_normalization=true)
  -> DLSS5OpticalFlow (Fast PoC) ----------------------┐
  -> DLSSSuperResolution (2x, Quality) <---------------┘
  -> VHS_VideoCombine (原 FPS、原音频、独立输出文件)
```

同时保留一个最小 `DLSS5EasyPipeline` 对照 graph，设置 `operation="Upscale only"`、`scenario="Fast preview"`。它用于确认上游推荐入口可以工作，不作为最终产品 adapter 的唯一实现，因为内部导引和阶段进度不可见、参数语义也更难锁定。

第二轮才比较：

- Farneback 与 RAFT Small/Large 的速度和拖影差异；
- Depth Anything V2 与 Video Depth Anything 的时间稳定性；
- 对 SR + NR 组合路径比较 persistent 与 bounded overlap-add（SR-only 节点本身没有该参数）；
- SR only 与 SR + neutral NR。

不要在没有实验的情况下用常量深度或零运动绕过必需输入。单图可以使用上游导引节点产生零运动，但视频必须检查真实运动导引。

## 4. 统一安装、依赖和下载边界

### 4.1 复用现有 ComfyUI Python 和系统要求

- Python `>=3.10,<3.14`；
- `numpy>=1.26,<3`；
- `opencv-python>=4.8`；
- `Pillow>=10`；
- `py7zr>=0.22,<2`；
- `transformers>=4.50,<6`；
- `torchvision>=0.20`；
- Windows 10/11 x64、NVIDIA RTX、足够新的驱动；
- 至少 16 GB RAM，视频建议 32 GB 以上；
- 大容量快速临时 SSD。

应用不创建第二个 venv、不下载通用 Python，也不增加 Python 选择器。节点 requirements 必须复用 Settings → ComfyUI environment 当前绑定的 Python：Portable 对应 `python_embeded`，Desktop/源码安装通常对应自己的 `.venv`。现有 dependency installer 已具备查找并锁定所选 ComfyUI Python、执行节点 `requirements.txt`、串行安装、记录日志以及批次末尾重启复检的机制，DLSS5 应直接扩展这条路径。

`opencv-python`、Transformers 和 TorchVision 有覆盖当前 ComfyUI 环境依赖的风险，安装前先解析 requirements 与现有版本，安装前后做 import/version smoke，并保留 pip 日志；发生不可接受的公共依赖冲突时应阻止安装并给出原因，而不是悄悄创建另一套 Python 环境。

### 4.2 原生运行时

SR 需要：

- VapourSynth-capable `python.exe`；
- `vsdlsssr.dll`；
- `nvngx_dlss.dll`。

NR 额外需要：

- `vsdlssnr.dll`；
- 由统一下载 manifest 从固定外部 GitHub Release 获取、校验，并与 wrapper/GPU/驱动兼容的 `nvngx_dlssnr.dll`。

上游 `install_runtime.py` 声称会下载固定的 VapourKit `nightly-2026-08-31`。实际下载并按 SHA-256 审计该 368 MB 归档及其嵌套包后，只发现 `vsdlssnr.dll`，没有脚本所要求的 `vsdlsssr.dll`、`nvngx_dlss.dll` SR 组合。因此该 nightly 不能作为可安装 SR bundle，README/脚本声明不能代替归档成员验证。

VapourKit 归档内部带有执行 DLSS/VapourSynth bridge 所需的专用 `python.exe`。它是 DLSS5 runtime 的私有实现文件，不是第二套供 ComfyUI 安装包或模型依赖的 Python 环境：不出现在环境选择器中、不接受普通 pip 安装、不被其他 workflow 复用，也不单独显示为依赖卡。用户只会看到统一的 DLSS5 runtime 阶段。

上游脚本在下载 VapourKit 前要求 `nvngx_dlssnr.dll` 已存在；本项目不直接复用这个交互限制，而是实现自己的 **用户触发式统一安装编排**。参考 `DLSS5oneclick` 的外部 release 下载方式和 `DLSS5-Swapper` 的安装记录/恢复方式，应用本身与 Git 仓库不携带这些二进制；用户点击“下载并安装 DLSS5”后才从固定的外部 GitHub Release 下载。

这里没有第二个 DLSS5 节点仓库依赖。依赖拓扑是：

- 必需：现有 ComfyUI、原版 HECer 节点、所选 ComfyUI Python 中的 requirements；
- SR 必需 runtime：来源可复现且经过成员/hash/schema 审计的 `vsdlsssr.dll` 与兼容 `nvngx_dlss.dll`；当前没有找到这样的公开 wrapper bundle，SR 必须保持 unavailable；
- NR 可选 runtime：固定 VapourKit `vsdlssnr.dll` 与单独下载的 `nvngx_dlssnr.dll`；基础 NR 已实机验证；
- 产品视频 I/O：复用应用现有的 VideoHelperSuite 依赖，不重复注册或下载第二份；
- guide 权重：Depth Anything 独立模型卡；RAFT 继续使用 TorchVision 权重缓存；
- 非首发可选项：VDA-S 会使用其固定的官方源码/权重，FlashDepth 需要自己的隔离环境。

`DLSS5oneclick` 和 `DLSS5-Swapper` 只是安装设计参考，绝不能被写进 HECer 节点的 required dependencies，也不能与 HECer 一起克隆到 `custom_nodes`。

用户看到的是一个安装项，内部允许有多阶段：

```text
下载/更新 ComfyUI-DLSS5 仓库
  -> 使用所选 ComfyUI Python 安装 requirements
  -> 下载固定 VapourKit release
  -> 下载固定 DLSS runtime assets
  -> SHA-256 与预期文件检查
  -> staging 解压
  -> 原子安装到 ComfyUI-DLSS5/runtime
  -> 写 install-manifest.json 与 runtime/config.json
  -> 重启 ComfyUI
  -> /object_info + DLSS5RuntimeStatus 复检
```

下载 manifest 至少包含：

```ts
interface Dlss5DownloadArtifact {
  id: string;
  sourceRepository: string;
  releaseTag: string;
  assetName: string;
  downloadUrl: string;
  sha256: string;
  expectedBytes?: number;
  archiveType: "7z" | "zip" | "file";
  expectedFiles: string[];
  targetRelativeDirectory: string;
}
```

初始候选下载源以实际 PoC 锁定为准：VapourKit 使用 HECer 已验证的固定 nightly；DLSS runtime 可参考 `DLSS5oneclick` 使用的 `RankFTW/rhi-repo` release 资产解析方式。不得跟随浮动 `latest` 后直接覆盖已验证 runtime，版本升级必须先更新应用 catalog 中的 manifest。

### 4.3 安装安全和恢复

许可证不作为本计划的产品化阻塞项：应用不随安装包或源码仓库分发第三方 DLL，下载由用户在明确按钮上主动触发。实现仍需保留以下工程安全边界：

- 所有下载先写 `.partial`，完成后计算 SHA-256；
- 只接受 manifest 声明的 HTTPS GitHub Release URL、asset 名称和文件清单；
- 解压到 staging，验证 PE 文件、架构、大小和预期文件后再替换；
- `install-manifest.json` 记录来源、release、hash、安装时间和每个 owned file；
- 重装只补齐或替换 manifest 管理的文件，不扫描后删除未知 DLL；
- 覆盖已有 managed runtime 前创建可恢复备份，失败自动恢复；
- 卸载只删除 install manifest 拥有的文件，保留用户额外放入的内容；
- `runtime/config.json` 包含机器绝对路径，不得写入 catalog、History、日志导出或仓库；
- workflow 与 DLL 都按本机代码执行处理，完整安装日志需可查看且路径对外导出时脱敏。

`DLSS5-Swapper` 当前版本会把核心 DLL payload 随发行包携带，因此不能作为“不打包 DLL”的直接先例；本项目只借鉴它的缓存校验、安装记录、备份/恢复和 owned-file 删除思路。二进制获取采用 `DLSS5oneclick` 式的用户点击后外部 Release 下载，但不照搬其“动态取最新 tag、第一个 asset、无 hash”的实现。

### 4.4 Depth Anything 独立模型卡

Depth Anything 不放进 DLSS5 依赖卡的内部状态明细，而是在 **Settings → Video models** 下作为独立模型卡展示。它是视频导引模型，不进入 Create 的基础视频模型选择器。

建议模型 id/角色：

- id：`depth-anything-v2`；
- category：`video`；
- role：`depth-guide`，用于把它从生成模型选择器中排除；
- 首发组件：Depth Anything V2 Small；
- V2 Base、V2 Large、Video Depth Anything Small 留待后续阶段；
- consumer：`dlss5-sr`、未来 `dlss5-neural-rendering`，以及其他需要深度导引的 workflow。

HECer 节点当前按 Hugging Face model id 调用 `from_pretrained`。首发适配层把 Small profile 改为从标准 ComfyUI 模型目录读取用户提供的 `model.safetensors`，并从节点包内置的 `config.json` 与 `preprocessor_config.json` 创建 Transformers 元数据；模型卡只扫描这一份 safetensors 权重，不下载或扫描 Hugging Face snapshot。remote ComfyUI 只能做 runtime validation，不能假装管理远端磁盘。

默认 DLSS fast profile 依赖 V2 Small；VDA-S 只在时间一致高质量 profile 中启用。RAFT 属于 TorchVision 运行依赖/权重缓存，不混入 Depth Anything 模型卡。FlashDepth 是另一套隔离环境，继续作为后续可选项。

## 5. 与当前 Local Video Studio 的接入位置

### 5.1 产品入口

保持 `WORKFLOW_CONTRACT` 的结果驱动规则：从 History 中选中一个成功视频版本，再创建独立 Upscale queue task。不要把 DLSS 插进 Create 的初始生成 workflow，也不要替换现有 provider。

首发 UI 名称建议：

- 中文：`DLSS Super Resolution · 实验性`
- 英文：`DLSS Super Resolution · Experimental`

文案说明应包含：Windows/NVIDIA only、2×/3×/4×、需要原生运行时、速度和质量仍待本机验证。不要只显示“DLSS 5”，以免用户误解为包含 Frame Generation。

### 5.2 Catalog 和环境扫描

新增建议：

- custom node id：`comfyui-dlss5`；
- repository：`https://github.com/HECer/ComfyUI-DLSS5.git`；
- directory/alias：`ComfyUI-DLSS5`；
- model/provider id：`dlss5-sr`；
- adapter id：`dlss5-sr`；
- input mode：`video`；
- required workflow nodes：`DLSSSuperResolution`、选定 depth/motion guide、`VHS_LoadVideo`、`VHS_VideoCombine`；
- diagnostic nodes：`DLSS5RuntimeStatus`；
- optional capability nodes：`DLSS5NeuralRendering`、`DLSS5FullPipeline`、VDA、RAFT、FlashDepth。

DLSS provider 本身不要伪造传统模型权重 component；Depth Anything 权重由独立模型卡表达。环境证据应分成：

1. 节点目录存在；
2. Python requirements import/version 通过；
3. SR runtime 文件和配置可解析；
4. NR runtime 由统一下载 manifest 获取且 release/asset/hash 通过；
5. `/object_info` 节点与关键 enum/schema 通过；
6. 当前 GPU/驱动/runtime tuple 自检通过；
7. 真实最小 workflow 通过。

Settings 中只显示一个 `ComfyUI DLSS5` 依赖卡和一个统一安装/更新动作。卡片内部可以分阶段报告 repository、ComfyUI Python requirements、VapourKit runtime、DLSS runtime 和节点注册状态，但用户不需要逐个安装，也不显示“安装 Python”。Depth Anything 的权重完整性来自独立视频模型卡；ComfyUI 离线时两张卡都可以完成文件扫描，在线后再补 `/object_info` 和 runtime status。

### 5.3 Workflow builder

不要继续把所有 DLSS 逻辑堆进 `src/core/upscale.ts`。建议新增：

- `src/core/dlss5.ts`：纯函数的 options、geometry、API workflow builder、required-node/schema validator；
- `src/core/dlss5.js`：按当前双源约定同步生成；
- `src/core/workflow-metadata.ts`：记录上游 repository/release、API schema 和节点包；
- `src/core/upscale.ts`：只做 provider dispatch 与现有公共 load/combine 复用。

运行时仍走当前 `electron/services/comfy-ui.ts` 的 `/object_info`、upload、`/prompt` 和 output tracking。新增专属 preflight，检查的不只是 class type，还包括：

- `scale` 是否仍包含 `2x/3x/4x`；
- `quality` 是否包含固定首发 preset；
- guide node 的输入名和方向合同；
- runtime status 是否能分别报告 SR/NR；
- 上游版本是否落在我们验证过的兼容区间。

### 5.4 Queue snapshot 和持久化

当前 `UpscaleQueueTask` 的 `modelId`、`targetHeight`、`tileMode`、`faceRestore` 不足以表达 DLSS。新增字段必须是可选且有旧记录默认值，例如：

```ts
interface Dlss5UpscaleOptions {
  operation: "super-resolution";
  scaleFactor: 2 | 3 | 4;
  quality: "quality" | "balanced" | "performance" | "ultra-performance";
  depthMode: "depth-anything-v2" | "video-depth-anything";
  motionMode: "fast-optical-flow" | "raft-small" | "raft-large";
  nodeRevision?: string;
  runtimeRevision?: string;
}
```

建议挂到 `UpscaleRequest`/`UpscaleQueueTask` 的 `dlss5?: Dlss5UpscaleOptions`，而不是扩大现有 `faceRestore` 的含义。队列时冻结全部值，后续 Settings 或对话框变化不得改写已经等待或运行的任务。

现有 `targetHeight` 是 720/1080/1440/2160 档位，而 DLSS 原生输出是源尺寸的 2×/3×/4×。不要用一次额外 resize 隐藏二者不匹配。DLSS 选中时，UI 应以倍率为主控并显示实际输出尺寸；`targetWidth`/`targetOutputHeight` 保存真实几何。旧任务继续按 `targetHeight` 解释，迁移时 `dlss5` 缺失即表示非 DLSS 任务。

### 5.5 Queue、进度和 History

一个 DLSS task 仍然是一个重型 GPU 后处理任务，遵守单重任务串行策略。进度至少区分：

1. 读取视频；
2. 深度估计；
3. 光流/RAFT；
4. DLSS SR；
5. 可选 NR；
6. 编码和音频复用。

取消必须终止当前 ComfyUI prompt，并确认上游 VapourKit 子进程没有遗留。失败日志要保留 node、runtime report、原生返回码和临时目录提示，但要删去用户绝对路径。

成功后继续使用现有 History lineage：在同一 asset 下新增一个 `kind="upscale"` 版本。History metadata 记录 operation、scale、quality、guide、upstream node/runtime revision、源/输出尺寸、FPS、帧数和分阶段耗时。原视频和音频不可被覆盖。

### 5.6 Preserve list

- Real-ESRGAN、FlashVSR、SeedVR2 modular/native 和 H3 native upscale 全部继续可用；
- Upscale 只从成功 History version 发起，并生成同一 asset 下的新版本；
- queued task 保持不可变 execution snapshot；
- 原始 FPS、音频、时长和输入文件不被静默改写或覆盖；
- RIFE 仍是独立插帧能力，DLSS SR 不改变 generation/output FPS 合同；
- ComfyUI 离线时仍可检查文件，运行时证据只在服务连接后补充；
- 同时只执行一个重型 GPU generation/post-process stage；
- 任一 DLSS 失败都不得静默切换到其他 provider。

## 6. 分阶段实施计划

### WP0：统一下载 manifest 与安装事务

交付：可测试的 download manifest、统一安装 service 和 dry-run 计划，不进入普通用户下拉框。

- 固定 HECer 节点 release/commit，不追踪浮动 `main`；
- 固定 VapourKit 与 DLSS runtime 的 GitHub Release、asset、bytes 和 SHA-256；
- 一个用户点击触发 repository、requirements、runtime 和 config 全部阶段；
- 实现 `.partial`、staging、hash、expected-files、备份、原子替换和 rollback；
- 生成 `install-manifest.json`，重装/卸载只操作 owned files；
- 支持 dry-run 显示来源、下载体积、目标目录和将要替换的文件；
- 下载失败或 hash 不符时保留日志，不提交半安装状态。

Exit：在不把第三方二进制提交到本仓库或应用安装包的前提下，用户一次点击可重复完成 DLSS5 整包安装并恢复失败事务。

### WP1：隔离运行时 PoC

交付：实验 API workflow、`/object_info` snapshot、最小输出和 evidence record，不进入普通用户下拉框。

- 在 Settings → Video models 注册独立 `Depth Anything` 卡，只扫描用户放入标准模型目录的 V2 Small `model.safetensors`，配置元数据由应用内置；
- 通过 WP0 的统一动作在用户选中的 ComfyUI 上安装固定节点和 runtime；
- 记录 Windows、GPU、driver、Python、Torch/CUDA、ComfyUI、节点和 runtime tuple；
- 先跑单图 2× SR，再跑 16–33 帧短视频 2× SR；
- 验证输出帧数等于输入帧数，FPS/时长不变，原音频保留；
- 检查 VapourKit 子进程退出、取消和临时文件清理；
- 记录错误组合，例如 `0xBAD00001`，不得静默 fallback 到其他 upscaler。

Exit：至少一个受支持硬件 tuple 的 2× SR 真实成功；这只叫 Runtime validated，不叫 Product integrated。

### WP2：同条件质量与性能基准

使用同一组源视频和完全相同的最终几何，对比：

- Real-ESRGAN x4plus + exact resize；
- FlashVSR；
- SeedVR2 modular；
- SeedVR2 native INT8；
- DLSS SR：Farneback、RAFT Small 和选定视频深度组合；
- 可选：DLSS SR + neutral NR，单独列结果。

至少覆盖：静态人像、快速运动、细线/文字、纹理重复、场景切换、压缩噪声、动画/游戏画面和生成式人物视频。

每组记录：

- wall-clock、首帧延迟、处理 FPS；
- depth、flow、SR、encode 分阶段耗时；
- dedicated/shared VRAM、RAM、临时磁盘峰值；
- 输出帧数、FPS、时长、音频和实际尺寸；
- PSNR/SSIM/LPIPS（有参考时）、VMAF（适用时）；
- 盲评：脸、头发、文字、薄线、闪烁、拖影、scene-cut reset 和纹理 hallucination。

Exit：只有 DLSS 在代表性视频上同时满足速度、稳定性和最低质量线，才允许 `badge="最快"`；否则只显示“实验性”。默认 provider 的变更需要单独产品决定。

### WP3：Catalog、扫描和安装 UX

- 注册 `comfyui-dlss5` custom node、`dlss5-sr` provider 和 `depth-anything-v2` 视频导引模型；
- `repositoryUrl` 必须直接指向 `https://github.com/HECer/ComfyUI-DLSS5.git`，并固定经过验证的 release/commit；不使用自建镜像或包装仓库；
- 一个 DLSS5 卡复用现有串行安装队列、超时、日志、备份与重启复检，并编排 repository、pip 与 runtime 下载；
- 一个按钮完成 DLSS5 整包安装/更新，不把内部 artifact 拆成独立依赖卡；
- 沿用现有卡片状态和动作：未安装、排队中、处理中、正在重启并复检、可用、可更新、修复/重装、卸载；不另做 DLSS 专用安装窗口；
- 安装批次开始时锁定所选 ComfyUI 实例、data root 和 Python；与其他节点安装串行，批次末尾最多重启一次；
- HECer 自带的 `DLSS5RuntimeSetup` 只保留为诊断/手动 fallback，不通过生成 queue 执行产品安装；产品安装必须由 Settings 的 dependency installer 完成；
- 应用安装的目录和 runtime 由 manifest 管理；检测到 ComfyUI Manager/用户手装副本时可以扫描和使用，但不得把它误标成 app-owned 或在卸载时删除；
- Depth Anything 独立卡负责 V2 Small/Base/Large 与 VDA-S 文件证据；
- 新增 DLSS runtime 专属离线 probe；
- 区分 node installed、SR runtime ready、NR runtime ready、runtime validated；
- 多 ComfyUI 安装时始终写入当前明确选中的 data/custom_nodes 目录；
- remote ComfyUI 只做连接和 runtime/schema 验证，不显示本地安装、修复或卸载动作；
- ComfyUI 离线时仍能检查文件与配置，在线后才补 `/object_info`；
- 对 `runtime/config.json` 做路径归属校验和日志脱敏。

Exit：离线、连接、缺文件、错误 ABI、安装成功、失败、超时和重启复检状态都可解释。

### WP4：生产 API adapter 和队列

- 新增 typed `Dlss5UpscaleOptions` 和旧记录默认；
- 新增 `src/core/dlss5.ts` builder/schema validator；
- 在 `renderUpscaleWorkflow` 做独立 provider dispatch；
- queue enqueue 做 source、geometry、runtime 文件和兼容性前置检查；
- execution claim 时以实时 `/object_info` 再验证关键 schema；
- 增加 DLSS 节点阶段、进度和超时策略；
- 取消、失败、retry 清理 ephemeral runtime state，不修改 immutable options；
- History 写入可复现 metadata 和同 asset lineage。

Exit：SR-only 的完整 History → Queue → ComfyUI → History 路径真实成功，并通过重启、取消、失败和重试。

### WP5：Upscale 对话框

- 在现有 History Upscale dialog 中增加 provider；
- DLSS 选中时显示 2×/3×/4×，而不是误导性的固定短边档；
- 显示实际输出尺寸、预计磁盘、兼容性和实验状态；
- 首发只暴露少量 presets：`Quality`、`Balanced`、`Performance`；高级 guide/window 参数可先由固定 profile 管理；
- unavailable 状态给出具体恢复动作：节点、当前 ComfyUI Python 中的 requirements、SR runtime、GPU/driver 或 runtime schema；不得提示另装 Python；
- 不显示 Frame Generation、Ray Reconstruction 或 NR 控件。

Exit：现有四类 pixel provider 和 H3 native path 均保持可用；键盘/focus、disabled reason 和 queue submission 回归通过。

### WP6：Neural Rendering 独立实验 Gate

仅在 SR 已产品化且统一下载/运行时路径稳定后开始：

- 新增独立 operation，例如 `neural-rendering` / `super-resolution-plus-neural-rendering`；
- 首次启用时用户必须显式确认 NR 的实验性、兼容性和画质风险，不再要求手工提供 DLL；
- 不把 NR readiness 作为 SR readiness 的条件；
- 用 neutral/faithful 作为首个评估 preset；
- 检查脸部、皮肤、头发、细线、闪烁、scene cut 和风格漂移；
- History 明确记录这是 experimental NR，不写成 Ray Reconstruction。

Exit：单独真实质量 Gate 通过后才进入实验 UI；不自动设为默认。

### Future：Frame Generation

本仓库当前无 FG。若以后接入，必须作为独立 provider/operation 调研，继续遵守“生成 FPS 与交付 FPS 分离”的现有合同。它不能复用 `DLSS5OpticalFlow` 或 RAFT 的名字就宣称已经插帧，也不能替换或静默改写现有 RIFE snapshot。

## 9. Rollout 和回退

Rollout 顺序：

```text
unified opt-in install + manual PoC
  -> hidden/experimental provider
  -> opt-in Settings dependency
  -> History Upscale experimental option
  -> evidence-backed badge/default decision
  -> optional NR experiment
```

回退必须简单：

- 禁用 catalog capability 不删除用户运行时；
- 已完成 History 版本继续可查看；
- 旧 DLSS queue task 在 provider 不可用时进入明确 failed/unavailable，不切换到 SeedVR2 或 Real-ESRGAN；
- 卸载只删除应用管理且精确匹配的 custom-node/runtime 目录，必须使用现有确认和日志合同；
- 只删除 `install-manifest.json` 明确拥有的文件；未知文件和用户额外放入的 DLL 一律保留。

## 10. 决策门

建议现在批准的是 **WP0–WP2：统一下载事务、Depth Anything 模型卡与隔离 PoC、同条件 benchmark**，而不是直接批准完整 UI 接入。

进入产品实现前必须同时满足：

- 用户一次点击可以从固定 release 完成 DLSS5 repository + runtime 整包安装，且本仓库/应用包不携带第三方 DLL；
- Depth Anything V2 Small 在独立视频模型卡中可扫描用户提供的 `model.safetensors`，并由 DLSS workflow 消费同一份标准模型目录；配置元数据由应用内置；
- 固定版本在至少一个目标 GPU tuple 上真实 2× 成功；
- 输出帧数、FPS、时长、音频和几何正确；
- 对现有 Upscaler 的同条件数据证明速度/质量价值；
- 长视频的 RAM、临时盘、取消和子进程清理可控；
- `/object_info` schema 和上游版本策略已锁定；
- 下载 manifest、hash、owned-file 记录和失败回滚已经验证。

在这些 Gate 通过前，正确产品结论是：**DLSS SR 是一个很有潜力、但成熟度与兼容性仍需实机验证的实验性快速 Upscale 候选；NR 是独立的实验增强能力；FG 当前不存在。** 外部下载不是产品化阻塞项，但固定来源、hash 和可恢复安装仍是基本工程要求。

本轮仓库影响分类为 documentation-only / patch-level research artifact；未修改产品行为，不单独触发版本号更新。

### 11.2 用户可见行为

#### ComfyUI DLSS5 卡片

位置：Settings → Nodes & dependencies，与其他 custom-node 卡使用同一布局、按钮和安装队列。

卡片标题固定为 `ComfyUI DLSS5`，副标题说明它安装的是 HECer 原版节点。卡片至少显示以下可独立诊断的行：

| 行 | Ready 条件 | 缺失时动作 |
| --- | --- | --- |
| HECer node | 目录来源匹配、revision 匹配、入口文件存在 | 安装/更新/修复节点 |
| ComfyUI requirements | 当前选中 Python 的 import/version probe 通过 | 用相同 Python 补齐依赖 |
| DLSS SR runtime | VapourKit Python、`vsdlsssr.dll`、`nvngx_dlss.dll` 和 config 均有效 | 下载或修复统一 runtime |
| DLSS NR runtime | `vsdlssnr.dll`、`nvngx_dlssnr.dll` 和 manifest hash 有效 | 显示实验组件缺失/修复；不得阻塞 SR |
| Runtime registration | 在线 `/object_info` 存在首发节点且 schema 匹配 | 重启并复检或报告上游不兼容 |
| Hardware | Windows、NVIDIA GPU、driver/runtime probe 通过 | 显示具体不兼容原因 |

卡片总体状态按以下优先级计算：

```text
remote endpoint                         -> runtime-only / 不可本地安装
正在排队或安装                          -> 复用现有队列状态
node 或 SR runtime 缺失                 -> 未安装 / 需要修复
离线且磁盘证据完整                      -> 已安装，等待运行时验证
在线 schema 或硬件检查失败              -> 不可用，显示原因
SR 全部通过、NR 缺失                    -> SR 可用 · NR 未准备
SR 和 NR 均通过                         -> 可用 · NR 实验组件已准备
```

单击“安装/更新”后，用户只发起一个队列项。日志按顺序显示：锁定环境、节点仓库、requirements、SR runtime、NR runtime、写配置、重启、复检。NR 下载失败时保留已经原子提交且验证通过的 SR 能力，卡片显示“SR 可用 · NR 修复失败”；不能为了可选 NR 回滚健康的 SR。每一个内部 artifact 自身仍必须采用 staging 后原子提交。

支持现有动作语义：

- `install`：缺什么补什么；已有且 hash/revision 正确的内容跳过。
- `update`：只更新到 catalog 已批准的新 pin，不跟随浮动 `main/latest`。
- `repair`：重新验证并替换损坏的 app-owned 文件，不覆盖未知文件。
- `reinstall`：备份 app-owned 节点和 runtime 后安装干净副本；成功后保留可恢复备份记录。
- `uninstall`：需要现有确认 UI；只删除 manifest-owned 文件。用户/Manager 手装内容不删除。

#### Depth Anything 卡片

位置：Settings → Video models，排在基础视频生成模型之后，并明确标记 `Guide model / 深度导引`。它可以被 DLSS5 和未来其他 workflow 消费，但绝不能出现在 Create 页的基础生成模型下拉框。

首发只要求 `Depth Anything V2 Small`：

- 默认且必需；
- Base/Large 和 Video Depth Anything Small 留待后续阶段，不得阻塞 SR 首发；
- 卡片必须显示标准模型目录中的权重或缺失；
- 用户按卡片提示从官方源下载 `model.safetensors` 并放入目标目录，应用不得下载 JSON 或在 GPU queue 开始后静默联网；
- 卡片提供官方权重下载页、目标目录提示和重新扫描反馈；
- remote ComfyUI 不显示本地准备动作。

#### Upscale 操作

入口保持为 History 成功视频版本上的 Upscale。选择 DLSS 后：

- 目标控件切换为 `2× / 3× / 4×`，默认 2×；
- 质量控件为 `Quality / Balanced / Performance`，默认 Quality；
- 首发 guide profile 固定为经 PoC 选定的 fast profile，不在 UI 暴露深度、光流和窗口参数；
- 显示输入尺寸和精确输出尺寸；
- 显示 `Windows + NVIDIA · Experimental`；
- 不显示 tile mode、face restore、NR、RR 或 FG 控件；
- DLSS 不可用时禁止提交并显示单一、具体的恢复动作；
- 提交后产生普通 immutable upscale task 和同 asset 下的新 History version。

### 11.3 数据合同和兼容迁移

不要继续依靠散落的字符串判断 provider。先建立以下最小类型；名称可以为适应当前代码略调，但语义不可改变。

```ts
export type Dlss5Scale = 2 | 3 | 4;
export type Dlss5Quality = "quality" | "balanced" | "performance";

export interface Dlss5UpscaleOptions {
  operation: "super-resolution";
  scale: Dlss5Scale;
  quality: Dlss5Quality;
  guideProfile: "depth-anything-v2-small-farneback";
  nodeRevision: string;
  runtimeBundleId: string;
}
```

当前 `UpscaleQueueTask.targetHeight` 只允许固定短边档，不能用它伪装 DLSS 倍率。采用兼容扩展：

```ts
interface UpscaleRequest {
  targetHeight?: 720 | 768 | 1080 | 1440 | 2160;
  targetScale?: Dlss5Scale;
  dlss5?: Dlss5UpscaleOptions;
}

interface UpscaleQueueTask {
  targetHeight?: 720 | 768 | 1080 | 1440 | 2160;
  targetScale?: Dlss5Scale;
  dlss5?: Dlss5UpscaleOptions;
  // targetWidth + targetOutputHeight 始终保存实际输出像素
}
```

规则：

- 旧记录没有 `targetScale/dlss5` 时，完全沿用 `targetHeight`。
- `modelId === "dlss5-sr"` 时必须有 `targetScale` 和 `dlss5`，不得依赖 `targetHeight`。
- 非 DLSS pixel provider 和 H3 native 必须有 `targetHeight`，不得带 `targetScale/dlss5`。
- 新增一个纯函数 normalization/validation helper，所有 UI、queue、filename、history、estimate 和 workflow 代码都通过它读取 target；不要让各文件自行判断。
- DLSS 实际尺寸为输入宽高分别乘倍率；如节点 schema 对奇数尺寸有限制，必须从真实运行/源码获得对齐规则，并在 enqueue 前显示最终尺寸。不得偷偷拉伸或改成最近的旧短边档。
- task 中冻结 `nodeRevision` 和 `runtimeBundleId`。执行时发现当前环境已经切换到不兼容组合，应明确失败/要求重建任务，不能静默用新 runtime 改写 queued snapshot。

Catalog 增加 guide role，默认值必须保持旧模型行为：

```ts
export type CatalogModelRole = "generation" | "guide";

interface CatalogModelDefinition {
  role?: CatalogModelRole; // absent === "generation"
}
```

`depth-anything-v2` 使用 `category: "video"`、`role: "guide"`。同步扩展 environment scan profile 中对应字段。Create 页只列 `role !== "guide"`；Settings 的 Video models 同时列 generation 和 guide，但将 guide 放在生成模型之后。必须给这个过滤行为加测试，不能只靠 UI 文案隐藏。

运行时扫描建议使用明确结构，避免把一段 detail 字符串当状态源：

```ts
interface Dlss5RuntimeScan {
  ownership: "app-managed" | "external" | "missing";
  nodeRevision: string;
  requirementsReady: boolean;
  srRuntimeReady: boolean;
  nrRuntimeReady: boolean;
  configReady: boolean;
  objectInfoReady: boolean | null; // offline === null
  hardwareReady: boolean | null;
  missing: string[];
  warnings: string[];
  runtimeBundleId?: string;
}
```

### 11.5 DLSS runtime manifest 与安装事务

Manifest 必须是 catalog 中的静态、可审查数据，不在运行时抓 `latest`：

```ts
interface Dlss5RuntimeArtifact {
  id: "vapourkit" | "dlss-sr" | "dlss-nr";
  capability: "sr-required" | "nr-optional";
  repository: string;
  releaseTag: string;
  assetName: string;
  url: string;
  sha256: string;
  bytes?: number;
  archive: "7z" | "zip" | "file";
  expectedFiles: readonly string[];
}

interface Dlss5RuntimeBundle {
  id: string;
  nodeRevision: string;
  artifacts: readonly Dlss5RuntimeArtifact[];
}
```

约束：

- 不使用 `nightly-2026-08-31` 作为 SR 候选：归档 SHA-256 匹配发布资产，但嵌套成员审计确认其中没有 `vsdlsssr.dll` 或 `nvngx_dlss.dll`。
- SR 候选必须同时固定 wrapper 和 NVIDIA runtime，并在接入前验证归档成员、hash、VapourSynth 注册 schema 和最小真实运行；缺少任一项就保持 unavailable。
- `nvngx_dlssnr.dll` 的 release、asset 和 SHA-256 必须在 PoC 前真实下载并审计后填写。找不到可固定的 asset/hash 就停止并报告；禁止占位 hash、空 hash、浮动 API 解析或“第一个 asset”。
- 如果 VapourKit 已经包含 `nvngx_dlss.dll`，不要再下载第二份 SR DLL；artifact 划分以实际归档内容为准。
- 下载 URL 只允许 HTTPS 和 manifest 声明的 GitHub repository/release；重定向后的最终 host 也要在允许列表内。
- 不执行归档内的脚本、EXE 或 DLL；只提取 expected-files 白名单。

建议持久目录：

```text
<selected ComfyUI data root>/.local-video-studio/
  dependencies/comfyui-dlss5/install-manifest.json
  runtimes/dlss5/<runtimeBundleId>/...
```

HECer 节点自己的 `runtime/config.json` 只写指向上述 app-owned runtime 的绝对路径。这样更新节点仓库时不会把 300 MB 以上 runtime 当作 Git checkout 的一部分。若当前 HECer pin 的 config loader 不支持这种布局，先在 focused test/PoC 中确认后调整目录；不得直接修改 HECer 源码实现私有协议。

单个 artifact 安装算法：

```text
校验 selected local ComfyUI 与目标路径 containment
  -> 在系统 temp/local-video-studio/dlss5/<uuid> 创建 staging
  -> 下载为 <asset>.partial，实时上报 bytes/total
  -> HTTP 完成后 fsync/close
  -> 校验 expected bytes（若有）和 SHA-256
  -> 解压时拒绝绝对路径、盘符、..、symlink/reparse point 和非白名单成员
  -> 校验每个预期文件存在、非空、x64 PE（适用时）
  -> 运行只读版本/import probe
  -> 将旧 app-owned artifact 移到带时间戳 backup
  -> rename staging 到最终目录；Windows 占用时按现有受控 copy fallback
  -> 原子写 install-manifest.json
  -> 失败则恢复旧目录并保留错误日志
  -> finally 删除 staging/.partial
```

完整 install 动作顺序：

1. 在入队时冻结 selected ComfyUI root、data root、Python 和 endpoint。
2. remote endpoint 立即拒绝本地安装。
3. 检查当前 GPU queue/ComfyUI 生命周期，不能在 HECer worker 正运行时替换 runtime。
4. 使用现有 custom-node installer 安装/更新原版 HECer pin，保留本地修改和旧目录备份规则。
5. 使用同一 ComfyUI Python 检查 Python `>=3.10,<3.14`。
6. 安装 requirements，使用 `--upgrade-strategy only-if-needed`。若已装 `opencv-contrib-python` 且 `cv2` 版本满足要求，过滤 `opencv-python`，避免两个 OpenCV wheel 互相覆盖。
7. 对 NumPy、Pillow、Transformers、TorchVision、Py7zr 和 cv2 做 import/version probe；失败保留完整 pip 日志。
8. 安装/复用固定 VapourKit 和 SR runtime。
9. 尝试安装固定 NR runtime；失败记录 warning，不把健康 SR 变成 unavailable。
10. 写 HECer config 和 app install manifest。
11. 批次结束按现有策略最多重启一次 app-managed ComfyUI。
12. 运行依赖 refresh、`/object_info` schema 检查和 `DLSS5RuntimeStatus` 复检。

安装日志不能输出 access token；导出日志时对用户绝对路径脱敏。下载失败、hash mismatch、归档结构错误、目标占用、Python ABI 不支持和 runtime probe 失败必须是不同错误码/用户提示，不能统一显示“安装失败”。

### 11.6 Depth Anything 资产管理

首发模型标识：

```text
catalog id: depth-anything-v2
role: guide
default repo: depth-anything/Depth-Anything-V2-Small-hf
consumer: dlss5-sr
```

执行前从官方模型仓库固定一个 immutable revision，并记录核心文件名、大小/ETag 或可取得的 hash。不得以浮动 `main` 作为已验证版本。

首发只把一个大文件交给用户管理，目标目录固定为所选 ComfyUI 的标准模型根目录下：

```text
<model root>/depthanything/Depth-Anything-V2-Small-hf/model.safetensors
```

`config.json` 与 `preprocessor_config.json` 是 pinned revision 对应的运行时元数据，随应用的 DLSS5 Depth Anything 适配层内置并写入节点包的 `assets/depth-anything-v2-small/`。它们不是模型卡组件，不出现在下载清单中，也不由安装器从网络获取。

模型卡扫描规则：

1. 只检查配置的 ComfyUI model root（以及默认 `<data root>/models`）下的 `depthanything/Depth-Anything-V2-Small-hf/model.safetensors`。
2. 缺失状态只报告这个 safetensors 文件；旧的 `.local-video-studio/huggingface` snapshot 即使存在也不算可用。
3. DLSS5 节点安装/更新时写入内置 JSON 并应用本地权重适配层；这一步不下载模型文件。
4. 在线时允许通过 HECer `/object_info` 和 runtime probe 确认实际可加载；remote ComfyUI 只显示远端验证结果，不扫描本机磁盘。

卸载 Depth 卡不删除用户的 `model.safetensors`，也不删除其他模型目录；节点包适配层随 DLSS5 节点目录的安全替换处理。

### 11.7 离线扫描和在线验证

离线 scan 必须在 ComfyUI 未启动时工作，并分别报告：

- HECer 目录是否存在；
- Git origin/revision（读取失败时只报告 unknown，不能假定 app-owned）；
- app install manifest 是否有效；
- requirements import/version；
- runtime config 是否解析，所有 resolved path 是否位于允许目录或明确标记 external；
- SR/NR expected files、hash 和 PE 架构；
- Depth Anything 标准模型目录中的用户权重；
- Windows/GPU 基础证据。

在线 refresh 再增加：

- `/object_info` 中 required class types；
- 每个 required input 名、类型、enum 和输出 index 与 frozen schema fixture 一致；
- `DLSS5RuntimeStatus` 的实际结果；
- 最小 runtime self-test（只在用户明确执行诊断时运行，不在每次普通扫描中启动重型 GPU 工作）。

必须把以下状态区分开：`installed on disk`、`statically recognizable`、`registered online`、`runtime ready`、`real smoke validated`。任何前置状态都不能替代后一状态。

### 11.8 API workflow 实现

第一阶段不要直接把 HECer example workflow JSON 提交给 `/prompt`，也不要把 `DLSS5EasyPipeline` 当生产 adapter。先完成 schema fixture，再在 `src/core/dlss5.ts` 构建最小、显式 graph：

```text
现有 VHS 视频加载节点
  ├─ frames -> HECer Depth Anything V2 Small guide
  ├─ frames -> HECer Farneback current-to-previous motion guide
  └─ frames + depth + motion -> HECer DLSSSuperResolution
                             -> 现有视频组合/编码节点
audio ------------------------^ 原样复用
fps --------------------------^ 原样复用
```

Builder 规则：

- 输入是 immutable `UpscaleQueueTask`、上传后的 source path 和已验证 schema。
- scale/quality 只从 `task.dlss5` 读取。
- 输出尺寸必须与 `targetWidth/targetOutputHeight` 一致；不再追加隐藏的 exact-resize 节点掩盖错误。
- 音频和 FPS 直接来自现有 VHS load outputs，保持源时长和声道。
- 首帧运动向量、方向和数值范围必须按 HECer pin 的实现；不得猜测或反向。
- 不引入 KJNodes/VRAM Debug 作为 DLSS 必需依赖。清理显存走当前公共执行生命周期。
- 生产 builder 不包含 NR 节点；NR 在 WP6 使用单独 operation/builder。
- 返回 graph 前运行静态 validator：节点存在、edge output index 合法、枚举在 `/object_info` 中、文件前缀安全、倍率和几何一致。

为了避免 schema 漂移，测试 fixture 应记录 HECer pin 的必要子集，而不是整个巨大 `/object_info`：每个使用节点只保留 class type、required inputs、enum 和 outputs。运行时发现不兼容必须 fail closed，提示更新应用或恢复 catalog pin。

### 11.9 Queue、执行、History

Enqueue：

1. 验证 source asset/version 仍存在且是成功视频。
2. 验证 `modelId=dlss5-sr`、`targetScale` 与 `dlss5` 一致。
3. 计算并冻结实际输出尺寸和输出文件名，例如包含 `dlss-2x`，避免与短边档命名冲突。
4. 使用最近环境快照做友好 preflight；快照缺失时允许进入等待，但写明 execution-time recheck。
5. 创建不可变 task，不保留 renderer draft 对象引用。

Execution claim：

1. 重新读取当前 `/object_info` 和 runtime readiness。
2. 对比 task 冻结的 node revision/runtime bundle。
3. 上传/解析 source，构建 graph，提交 `/prompt`。
4. 将 depth/flow/SR/encode 映射为清晰阶段；无法获得细粒度事件时不能伪造百分比。
5. cancel 同时中断 Comfy prompt，并等待 HECer/VapourKit 子进程退出；超时后记录残留 PID/错误，不宣称已清理。
6. 失败保留可操作日志；绝不自动换 Real-ESRGAN/SeedVR2。
7. 成功后验证文件存在、可探测、帧数/FPS/时长/尺寸/音频符合预期，再提交 History。

History metadata 至少记录：

```text
provider: dlss5-sr
operation: super-resolution
scale: 2|3|4
quality
guide profile
HECer node revision/version
runtime bundle id
GPU/driver tuple（可取得时）
input/output width/height
input/output fps/frame count/duration
audio preserved
wall-clock 和各阶段耗时（可取得时）
```

应用重启恢复 queued task 时保留这些字段；旧 task 没有字段时沿用旧 provider 逻辑。失败/取消 task 的恢复不得重新选择当前 UI 默认值。

### 11.11 分阶段文件所有权与交付顺序

为降低 Luna 上下文负担，严格按以下顺序完成；每一阶段通过 focused tests 后再进入下一阶段：

#### 阶段 A：类型、catalog 和纯函数

文件：catalog types/definitions、`src/types.ts`、新 `src/core/dlss5.ts`、对应 `.js` 和纯函数测试。

完成条件：

- HECer pin、runtime manifest 和 Depth guide role 可静态读取；
- Create 过滤 guide；Settings 仍能列出 guide；
- 旧 upscale records normalization 测试通过；
- DLSS 2×/3×/4× geometry 与无效组合测试通过；
- 尚不显示用户入口。

#### 阶段 B：安装与扫描

文件：新 runtime/depth services、dependency installer/scanner、environment wiring、必要 IPC、focused tests。

完成条件：

- 全部下载使用 mock/local fixture 测试，不依赖测试时访问公网；
- hash mismatch、截断下载、路径穿越、未知文件、Windows rename failure、rollback、取消和 owned-file uninstall 均有测试；
- 当前 ComfyUI Python 被正确使用；remote 安装被拒绝；
- 离线 scan 不要求启动服务；
- Settings 卡沿用现有安装队列状态。

#### 阶段 C：workflow 和 queue

文件：`src/core/dlss5.*` builder、upscale dispatch、task factory、enqueue、Comfy service、History、相关测试。

完成条件：

- frozen schema fixture 的 API graph 静态验证通过；
- immutable task、execution recheck、旧记录和无 silent fallback 测试通过；
- 输出 metadata/lineage 测试通过；
- 仍不把“静态通过”写成 runtime validated。

#### 阶段 D：UI

文件：Upscale dialog/controller、Settings view-model/page/controller/fragments、i18n、CSS（仅必要时）、相关 UI tests。

完成条件：

- History → Upscale 可选择 DLSS 并生成倍率任务；
- 缺依赖时 disabled reason 指向 Settings 卡；
- Depth 卡不出现在 Create；
- 现有 providers、焦点、编辑 waiting task 和 responsive checks 通过。

#### 阶段 E：真实验证和发布

完成阶段 A–D 和 `npm.cmd run verify` 后才进行。使用用户允许的本机 ComfyUI/GPU：

1. 卡片一键安装；记录下载来源、hash、日志和重启结果。
2. `/object_info` schema capture。
3. 单图 2× Quality。
4. 16–33 帧短视频 2×，验证音频和 FPS。
5. 场景切换、取消、失败重试、应用重启恢复。
6. 3×/4×和长视频边界。
7. 与现有 provider 同条件 benchmark。

只有真实输出成功后，才在 catalog compatibility evidence 中写入 GPU、driver、ComfyUI、Python/Torch/CUDA、node revision、runtime bundle 和 workflow ID。没有真实设备时停在“实现完成，等待 runtime validation”。

### 11.12 必跑测试

阶段内 focused tests 至少包括：

```text
npm.cmd test -- tests/model-catalog.test.ts tests/dependency-catalog.test.ts
npm.cmd test -- tests/dependency-installer.test.ts tests/dependency-scanner.test.ts tests/node-install-queue.test.ts
npm.cmd test -- tests/upscale.test.ts tests/queue.test.ts tests/queue-services.test.ts tests/comfy-ui.test.ts
npm.cmd test -- tests/secondary-dialogs.test.ts tests/settings-selectors.test.ts tests/settings-status.test.ts
npm.cmd run typecheck
```

新增测试文件后把它们加入相应 focused 命令。最终必须运行：

```text
npm.cmd run verify
```

关键断言清单：

- 原版 HECer URL 和固定 revision；没有任何其他 DLSS repo 被注册为依赖。
- DLSS card 是一个队列项；内部进度不生成多张卡。
- SR ready 与 NR ready 独立。
- 当前 ComfyUI Python 被调用，系统 Python 未调用。
- 手工安装目录不会被 app uninstall 删除。
- remote endpoint 没有本地安装动作。
- Depth guide 在 Settings 可见、Create 不可见。
- 2×/3×/4×实际尺寸正确，旧短边任务不变。
- queued snapshot 不随 UI 或 runtime 更新被改写。
- 缺节点/schema/runtime 时 fail closed；不存在 fallback。
- 成功 History 保留 source lineage、音频、FPS 和实际尺寸。
- 现有所有 upscale provider graph snapshot/行为保持。

### 11.13 停止并报告的条件

出现以下任一情况，不要自行绕过，应停止相关阶段并写明证据：

- 找不到可固定并校验的 NR asset/hash；
- HECer pin 的实际 `/object_info` 与计划使用节点不一致；
- 当前 ComfyUI Python 为 3.14 或其他 HECer 不支持 ABI；
- requirements 会不可逆覆盖当前关键 Torch/CUDA/NumPy 环境且无法安全保持；
- HECer config 不支持 app-owned 外部 runtime 目录，且唯一办法是修改/patch 上游源码；
- 真实运行发现倍率、motion direction、音频或帧数不符合合同；
- Windows Defender/文件占用导致 worker 无法稳定安装、启动或清理；
- 目标文件在执行期间被其他 agent/用户修改，无法无损合并；
- 需要删除未知目录、用户 DLL、外部 HF cache 或其他非 manifest-owned 文件。

这些情况不允许用“先写死路径”“跳过 hash”“改用 latest”“复制另一仓库代码”“关闭验证”或“自动换 provider”解决。

### 11.14 Definition of Done

首发 DLSS SR 只有同时满足以下条件才叫完成：

- 产品安装的是固定原版 HECer 节点，一张卡可安装、更新、修复和安全卸载；
- 安装完全沿用应用环境、队列、日志、重启和扫描习惯；
- Depth Anything 独立 guide 卡工作，且不污染 Create 模型选择；
- 2×/3×/4×任务合同、queue snapshot、workflow、取消/重试和 History lineage 完整；
- offline scan、online schema/runtime validation 和至少一个真实 GPU smoke 都通过；
- 现有 provider 回归通过，`npm.cmd run verify` 通过；
- README 当前版本摘要、`CHANGELOG.md` 和版本号同步更新；这是新用户能力，应按执行时当前版本升级下一个 minor，使用 `npm.cmd version minor --no-git-tag-version`，不要硬编码本文撰写时推算出的版本；
- 最终报告明确区分 automated tests、static workflow validation、real runtime smoke 和未测硬件组合。

如果阶段 A–D 已完成但没有目标 GPU/runtime，状态必须写为“产品实现完成，等待真实 DLSS runtime 验证”，不能标记 Definition of Done。

### 11.15 Luna 每阶段回报格式

不要一次性声称全部完成。每结束一个阶段，按下面格式回报后再继续：

```text
阶段：A/B/C/D/E
完成：实际落地的行为
修改文件：git diff --name-status 中属于本阶段的文件
保留项：确认未改变的现有 provider/流程
测试：命令 + 通过/失败数量
静态证据：catalog/schema/graph/hash 等
真实运行：未运行 / 运行环境与结果
剩余风险：具体事项
下一阶段：准备修改的文件和入口
```

最终交付前必须再执行一次：

1. `git status --short`，确认没有意外生成物、模型、DLL、runtime、日志或临时文件进入仓库。
2. `git diff --name-status` 和完整 `git diff`，特别检查没有删除用户文件或覆盖无关改动。
3. 核对 `package.json`、根 `package-lock.json` 和 `packages[""]` 的版本完全一致。
4. 核对 README 只写当前版本摘要，完整变化进入 `CHANGELOG.md`。
5. 最终报告列出未测试的 GPU 世代、driver/runtime 组合和 NR/FG 非目标能力。
