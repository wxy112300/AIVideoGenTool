# AD-01：X-MinimaxH3 原生二次采样与 ComfyUI 路线详细调查

状态：Static validated
调查日期：2026-08-31
所属计划：[X-MinimaxH3 功能吸纳计划](../active/2026.8.31-x-minimaxh3-feature-adoption.md)
调查范围：上游 X-MinimaxH3、上游 ComfyUI connector、官方 ComfyUI H3 节点、社区 latent upscaler，以及本地 H3/队列/历史/运行时边界。

本报告是 AD-01 的只读研究产物。它完成了源码、manifest、workflow、许可证、版本组合和本地代码边界的静态比对，但没有把任何新节点、模型、依赖或 workflow 接入产品，也没有完成本机真实二次采样。Static validated 不等于 Runtime validated。

## 1. 先给结论

### 1.1 上游的“ComfyUI 集成”不是纯 ComfyUI 二次采样

X-MinimaxH3 的 integrations/comfyui 是一个很薄的 HTTP client/custom-node connector。它把 H3 模型和二次采样请求交给已经在 8090 端口运行的 Native H3 Serve；ComfyUI 侧不加载 H3 的 DiT、VAE、文本编码器或 latent upscaler。connector 的二次采样节点最终调用 /api/v1/jobs/{source_job_id}/second-sampling，拿回 Native Engine 生成的视频。

所以：

- 它证明了“ComfyUI 可以作为前端编排入口”；
- 它不证明“只用 stock ComfyUI 就能得到上游同等的原生 2K”；
- 这条 connector 路线与我们未来的 Web/API adapter 有参考价值，但不能作为 AD-03 的纯 ComfyUI POC 证据。

### 1.2 Native Engine 不是原生 2K 算法的必要条件

“原生 2K”在上游合同中实际对应 2k = 1440，也就是通常的 2560×1440 目标几何，而不是简单把已经解码的 1080p 视频做普通后处理放大。它的核心是：

1. 第一阶段生成低于目标分辨率的 clean joint AV latent；
2. 对视频 latent 做 H3 专用空间或学习型 3D latent upscaling；
3. 对 reference/keyframe conditioning 做对应尺度变换；
4. 按 H3 的 video/audio 双时钟规则恢复 noise/flow 状态；
5. 以第二次采样完成高分辨率 AV latent，再用 H3 VAE 解码。

这条计算路径可以在 ComfyUI graph 中表达。Native Engine 的价值主要在显存预算、模型驻留/卸载、预取、分块、队列、artifact、监控和严格资源合同；它不是二次采样数学本身的先决条件。

### 1.3 stock ComfyUI 还不够，ComfyUI 加 H3 专用节点可以做

官方 ComfyUI 已经提供 H3 的 NestedTensor AV latent、视频 24 通道、音频 32 通道、双 sigma 时钟和基础 reference/guide 节点；官方 LTXVSeparateAVLatent/LTXVConcatAVLatent 也能拆接 NestedTensor。

但是完整的二次采样路径仍需要 H3 专用节点或等价实现，至少包括：

- 视频 latent upscaler；
- reference/keyframe conditioning upscaler；
- 对 NestedTensor 安全、且符合 H3 flow/CONST 语义的 AddNoise；
- video shift 12、audio shift 3 的 sigma 处理；
- 第二采样的 clean-latent、DisableNoise/denoise 以及 output/artifact 边界。

官方 stock AddNoise 的通用实现会对 NestedTensor 做不适用的 count_nonzero/nan_to_num 路径，而且直接套通用 (1 - sigma) 逻辑不能自动保证 H3 的 flow 语义。因此，“只利用 ComfyUI”应准确表述为“ComfyUI 核心 + 可审计的 H3 专用 custom nodes + H3 模型文件”，而不是“stock ComfyUI 零扩展”。

### 1.4 PyTorch 2.13 能跑，不代表我们的 2.10 结论错了

上游成功使用 PyTorch 2.13.0+cu130，是因为它建立了一个不同的运行时合同：

- Linux x86/WSL2；
- Python 3.10.20；
- PyTorch 2.13.0+cu130；
- CUDA runtime 13.0，CUDA toolkit 13.3；
- RTX 4090 / SM89；
- SageAttention、SpargeAttn 固定 commit，并应用了针对 PyTorch 2.13/C++20 的 patch；
- 只运行 Native H3 服务，不把它塞进我们当前的 Windows ComfyUI/custom-node 全栈。

我们此前在 Windows 11、RTX 4090、Python 3.12、ComfyUI 0.33.x、H3 custom nodes 和 PyTorch 2.10+cu130 上得到的“2.13 不兼容或爆显存”结论，针对的是另一组联合变量，尤其是 Windows、ComfyUI 调度/卸载、Sage/KJ kernels、VAE 和 renderer 运行路径的组合。现有证据不能得出“我们的兼容做得不够好”；更准确的结论是：2.10 是当前本地 ComfyUI 主线的已验证基线，2.13 只能作为隔离 Native runtime 的候选实验，不能全局升级。

### 1.5 上游的 2K 是两阶段资源合同，不是把单阶段上限偷偷放大

上游 24GB INT8 profile 的第一阶段上限是 1080p/15 秒，第二阶段才允许 2K/1440p；16GB 是实验性同级合同；8GB W4A8 第一阶段最多 720p、第二阶段最多 1080p。它没有在任务中途静默切换到另一个 profile。

这解释了为什么产品可以展示“原生 2K”：目标不是要求一次性把完整 15 秒 2560×1440 AV 采样常驻显存，而是把第一阶段和第二阶段做成明确的资源分段。我们应吸收这种 capability/resource contract，而不是只把 UI 里的分辨率选项加到 1440。

### 1.6 我们当前的主要缺口是 artifact 和产品边界，不只是节点

本地已经有 H3 ModelSamplingAV/sigma 的检测和基础 H3 workflow，但当前 workflow 是“第一采样后立即 VAE decode/save”，没有：

- clean joint AV latent 的联合序列化与恢复；
- latent upscaler/conditioning upscaler；
- H3 二次采样 task/provider；
- parent/child history artifact 关系；
- 1440 资源 capability profile；
- 真实 /object_info schema 快照和可重复的最小二次采样证据。

本地现有 h3ContextLatentPath 是 Motion Context 方向的上下文路径，不能直接假定为 Native H3 clean AV latent。这个边界已经在 [H3 Native AV 长视频计划](../../H3_NATIVE_MASKED_AV_LONG_VIDEO_PLAN.md) 中记录，本报告沿用该结论。

### 1.7 吸纳策略

采用“ComfyUI-only 先行、Native sidecar 条件化”的路线：

1. 吸收上游的 manifest、capability profile、evidence state、artifact 元数据和节点行为契约；
2. 在现有 PyTorch 2.10 ComfyUI 基线中做独立 AD-03 POC；
3. 先证明 720p → 1080p 的纯 ComfyUI 二次采样，再探 720p/1080p → 1440p；
4. artifact、队列、历史和资源合同稳定后，才决定是否需要 Native sidecar；
5. 不复制 X-MinimaxH3 的 all-rights-reserved 源码，不把其 2.13 环境改成产品全局依赖。

## 3. 上游产品和运行时边界

### 3.1 Native H3 Serve 的实际架构

上游架构文档给出的边界可以概括为：

~~~text
Browser / REST
    -> aiohttp API + auth
    -> durable queue / recovery
    -> NativeBackendManager
    -> NativeH3Engine
    -> NativeH3Pipeline
    -> AV latent / VAE / safe output path
~~~

它把 job identity、用户/API、队列和输出安全路径放在 backend/app 层，把显存、eviction、prefetch、kernel 和模型执行放在 engine 层。h3serve/app.py 仍然承担相当多的 JobRecord、路由和恢复编排，因而它是“边界清楚的模块化单体”，不是完全拆开的微服务。这一点与我们当前 headless rearchitecture 的“先模块化单体、后 API adapter”判断一致。

上游 Native Engine 选择性借鉴了：

- SGLang：数学图/执行图思路；
- LightX2V：eviction-first、双 buffer、H2D prefetch；
- FastVideo：typed request/stage；
- Comfy Kitchen：kernel；
- ComfyUI/Spectrum：行为参考和验证 oracle。

上游明确没有把 ComfyUI 或 Spectrum 整体复制进 Native runtime。我们也应把这些当作行为/架构参考，而不是可直接 vendor 的代码来源。

### 3.2 ComfyUI connector 的真实职责

上游 integrations/comfyui 的安装和运行方式是：

1. 将 connector 节点和示例 workflow symlink 到 ComfyUI；
2. 先启动 H3 Serve 的 FL2VA 或 Ref2VA profile；
3. 再启动 ComfyUI；
4. H3 模型只在 H3 Serve 中加载，ComfyUI 侧建议 --cpu --disable-all-custom-nodes --whitelist-custom-nodes ComfyUI-H3-Serve-Connector，以避免 4090 被第二份模型占满；
5. H3ServeSecondSampling 接收 ComfyUI 的 VIDEO 和目标分辨率/steps/strength/acceleration，向 Native service 发请求，返回下载后的视频。

connector 的 requirements.txt 没有第三方依赖，只复用 ComfyUI 提供的 torch、Pillow 和 NumPy；它的 pyproject.toml 要求 Python >=3.10、ComfyUI >=0.30.0，但这只描述 connector 适配层，不描述 Native H3 的 torch/kernel 合同。

### 3.3 上游二次采样的语义

上游把首次生成和二次采样分成两个不同的 request/spec：

| 对象 | 作用 | 关键内容 |
|---|---|---|
| GenerationSpec | 第一阶段生成 | mode、resolution、aspect、duration、frames、quality、acceleration、checkpoint、refs |
| SecondSamplingSpec | 从已完成卡片继续高分辨率采样 | source clean AV latent、target resolution、steps、strength、acceleration、preserve_audio、conditioning reuse |

Native backend 保存 .h3-latents/<safe-job-id>.pt，二采样请求只能解析位于受控 .h3-latents 目录内的 source artifact，并把二采样结果建成 child job。这个“source latent 必须是已完成卡片的 clean joint AV latent、路径必须受控、child 要有 parent 关系”的语义，比单纯的 h3ContextLatentPath 更严格。

上游 README 将二次采样的典型档位描述为 preserve/standard/enhance/strong，对应约 0.10/0.20/0.25/0.30 denoise/strength；steps 允许 1–8；2K 映射到 1440p。我们应保留这些是“能力/合同候选值”，直到本地 workflow 和显存实测完成。

## 4. 纯 ComfyUI 路线的技术核查

### 4.1 官方 H3 latent 结构

当前官方 ComfyUI H3 实现的关键事实：

| 项目 | 结构 |
|---|---|
| AV latent 容器 | NestedTensor((video, audio)) |
| video latent | [B, 24, T, H/16, W/16] 语义；视频 DiT patch 为 1×2×2 |
| audio latent | [B, 32, 2, T40] 语义 |
| 帧率 | 24 fps |
| 帧数 | 17k + 5，最小 5，最大 362 |
| 图像几何 | 宽高为 32 的倍数 |
| H3 时钟 | video shift 12，audio shift 3；由 ModelSamplingAV/MiniMaxH3SigmaShift 处理 |

官方 H3 节点包括：

- EmptyMiniMaxH3LatentAV
- MiniMaxH3ImageToVideo
- MiniMaxH3AddGuide
- MiniMaxH3ReferenceToVideo
- MiniMaxH3SigmaShift

官方 LTXV AV 节点包括：

- LTXVSeparateAVLatent：从 NestedTensor 拆出 video/audio；
- LTXVConcatAVLatent：把 video/audio 重新组成 NestedTensor。

这部分说明 ComfyUI 已经具备表达 H3 双分支 latent 的基础类型，不需要 Native Engine 才能创建或采样 H3 AV latent。

### 4.2 纯 ComfyUI 二次采样的最小 graph

一个可验证的 FL2VA POC 应接近以下逻辑，而不是把第一采样直接连到 VAE Decode：

~~~text
H3 first generation
    -> clean joint AV latent
    -> LTXVSeparateAVLatent
        -> video branch
            -> H3 latent upscale
        -> audio branch
            -> H3-safe AddNoise / inverse flow handling
    -> LTXVConcatAVLatent
    -> H3 second sampler with no fresh image/video noise
    -> H3 video/audio VAE decode
    -> output + joint AV latent artifact
~~~

如果有 reference/keyframe conditioning，还需要：

~~~text
reference/keyframe visual conditioning
    -> H3 conditioning upscale
    -> second sampler guider/conditioning
~~~

第二采样必须使用第一阶段完成后的 clean latent，不能把已经有噪声的中间采样状态当作可恢复 artifact，也不能仅仅 VAE decode 后用普通超分模型替代。

### 4.3 社区 H3 专用节点的行为

已检查的社区实现提供了四类关键能力：

| 节点 | 输入/行为 | 采用建议 |
|---|---|---|
| MiniMaxH3LatentUpscale | 对 H3 video latent 的 [B,24,T,H,W] 做 scale/interpolation；H/W 对齐到 2×2 patch | 作为行为参考；优先写独立适配层 |
| MiniMaxH3ConditioningUpscale | 同步调整 minimax_refs、minimax_keyframes 等 visual latent conditioning | 纳入 AD-03 必测项 |
| MiniMaxH3AddNoise | 对 NestedTensor 分支分别处理，避免通用 AddNoise 的 NestedTensor 操作和错误 flow 缩放 | 不能直接拿 stock AddNoise 代替 |
| MiniMaxH3ShiftSigmas | video shift 12、audio shift 3 的 sigma schedule | 与官方 ModelSamplingAV 逐版本核对 |

latent upscaler 有两种路线：

1. 纯插值：不加载额外 upscaler model，适合先验证 shape、NestedTensor、第二 sampler 和 artifact；
2. 学习型 3D upscaler：对 H3 24 通道 video latent 做 Conv3d/3D learned resize，通常保留 audio、VAE 和 DiT 的分工，质量潜力更高但引入约 690 MB BF16 权重和新的 license/runtime 变量。

建议先做纯插值路径的结构 POC，再单独替换为 pinned learned upscaler。这样能区分“第二采样图不正确”和“upscaler 权重/质量/显存不稳定”两个问题。

### 4.4 stock ComfyUI 与 ComfyUI-only 的准确答案

| 问题 | 结论 |
|---|---|
| Native Engine 是实现原生 2K 的算法必要条件吗？ | 不是。二次 latent sampling 的算法可以用 ComfyUI graph 表达。 |
| 只用当前 stock ComfyUI、不加节点可以吗？ | 目前不能把完整 H3 二次采样安全地视为 stock 能力；AddNoise/flow/NestedTensor 细节仍需专用节点或等价补丁。 |
| ComfyUI + 自己实现/审计过的 H3 节点可以吗？ | 技术上可以，是 AD-03 的首选验证路线。 |
| 上游 connector 能作为纯 ComfyUI 证明吗？ | 不能；它调用 Native H3 Serve。 |
| ComfyUI-only 能自动达到上游 24GB/15 秒/1440p 合同吗？ | 不能先验保证，必须在本地 GPU、torch、Comfy revision、kernels 和 workflow 上实测。 |

### 5.2 许可证和可再分发风险

本次调查确认的许可证边界：

| 对象 | 已知状态 | 对我们的含义 |

## 6. Torch、CUDA、driver 和 kernel 组合

### 6.1 上游安装脚本的精确组合

上游安装脚本不是普通的 pip install -r requirements.txt：

1. 建立 Python 3.10 venv；
2. 强制 cuda_home=/usr/local/cuda-13.3，检查 nvcc 以及 cublas/cusolver/cusparse headers；
3. 从 PyTorch cu130 index 安装 torch==2.13.0+cu130 和 torchvision==0.28.0+cu130；
4. checkout 固定 revision：
   - MiniMax-H3 8d8824efaf94586c0cc9ac7ad8d0723d4d6420ea
   - LightX2V 205d5c872d01557935dc87d67156f4f94069ea65
   - SageAttention eb615cf6cf4d221338033340ee2de1c37fbdba4a
   - SpargeAttn ae5b629ebb41e41f86b3ea2ab5a3283f13ac151a
5. 应用 minimax-h3-vae-temporal-host-sink.patch、sageattention-pytorch213-cxx20.patch、sparge-pytorch213-cxx20.patch；
6. 在 CUDA_HOME、TORCH_CUDA_ARCH_LIST=8.9、--no-build-isolation --no-deps 下编译 Sage/Sparge。

上游 requirements.lock 没有把 torch 放进 lock，而是把 Torch 作为安装脚本中的显式 runtime contract。这种拆分值得吸收：普通 Python 包锁定与 GPU ABI/kernel 锁定不是同一个依赖层。

### 6.2 上游 release evidence 与版本不一致

上游 release manifest 声称 v1.0.0、2026-08-29、707 tests passed、4 skipped；当前 VALIDATION.md ledger 声称 709 passed、4 skipped、0 failed，并额外记录 connector suite 24 passed、12 个权重的 bytes/SHA 通过和 real smoke 640×352/56 frames。

这是上游证据版本化不一致，不能简单合并为一个数字。我们吸收时必须让每次 evidence 绑定：

- upstream commit；
- validation document commit；
- test count；
- model manifest SHA；
- runtime tuple；
- smoke route 和输出 hash。

### 6.3 与本地 2.10 基线的逐项比较

| 维度 | 上游 Native H3 release | 本地已验证基线 |
|---|---|---|
| OS | Linux x86/WSL2 | Windows 11 |
| GPU | RTX 4090 / SM89 | RTX 4090 / SM89 |
| Python | 3.10.20 | 3.12.11 |
| PyTorch | 2.13.0+cu130 | 2.10.0+cu130 |
| CUDA runtime | 13.0 | wheel 为 cu130；本地完整 toolkit/ABI 组合仍按既有环境记录 |
| CUDA toolkit | 13.3 | 不是同一套上游 Native build contract |
| H3 执行 | Native H3 pipeline | ComfyUI 0.33.x + custom nodes |
| Attention/kernel | 固定 Sage/Sparge commit + C++20 patches | SageAttention 2.2.0 + cu130torch2.10、KJ/相关节点 |
| 历史结果 | upstream full preflight/real smoke | 5/124 frame 生成通过；360 frame 出现 WDDM shared-memory paging；Windows SM89 FP8 SageAttention 在 H3 TokenRefiner/main DiT abort |

本地历史研究还记录了：

- H3 Memory + DynamicVRAM async offload 组合曾完成 5 和 124 帧 smoke；
- 360 帧进入 WDDM shared-memory paging，未得到稳定采样步；
- 全局 --use-sage-attention 在 H3 TokenRefiner/main DiT 路径 abort；
- KJ 公开 Sage 路径也有相同类别风险；
- 当前产品策略已撤回 H3 Memory execution，不应因为上游用了 eviction 就自动重新打开。

因此当前处理方式：

1. 保留 PyTorch 2.10 作为本地 ComfyUI 的主验证基线；
2. 不为了吸收上游而修改全局 torch、Python、ComfyUI 或 Sage；
3. 如果未来要试 2.13，建立独立 venv/Native experiment，完整固定 Linux/WSL2、toolkit、patch、kernel、model 和 route；
4. 2.13 只有在整套实验合同的静态和 runtime gate 都通过后，才能作为 sidecar 候选，不能反向成为主应用依赖。

## 7. 上游资源 profile 与“原生 2K”合同

上游将执行偏好和显存合同做成 CUDA-free 的 ResourceBackendDefinition 表；launcher 在模型加载前选择 profile，任务中途不跨 profile，也不静默降级。

### 7.1 关键 profile

| Profile | 权重 | provisioned VRAM | planner budget | 第一阶段 | 第二采样 | 额外约束 |
|---|---|---:|---:|---|---|---|
| int8_24gb | INT8 | 24 GB | 23.25 GB | 360/480/720/1080；最高 1080p/15s | 720/1080/2K（1440p） | max short edge 1088；max pixels 1920×1088；exact/compact/whole-query execution |
| int8_16gb | INT8 | 16 GB | 15.25 GB | 同上但 1080 为 experimental | 720/1080/2K（1440p） | evidence 标注为 2026-08-29 的实验 gate |
| w4a8_8gb | W4A8 | 8 GB | 7.25 GB | 360/480/720 | 720/1080 | max short edge 736；max pixels 1280×736；最多 1 个 reference item；compact streaming |

int8_24gb 的 2K 不是一个单阶段 2K profile，而是：

~~~text
first pass: 低于 2K 的完整 AV 生成
    -> clean AV latent + conditioning
second pass: H3 latent upscale + high-resolution sampling
    -> 2560×1440 级 output
~~~

上游还记录了：

- 1440 K/V memory fix；
- 8GB projection OOM 通过 2048-row chunking 修复；
- 1080 preview ratio 修复；
- smoke evidence 不等同于 throughput 或质量声明。

### 7.2 Native planner 与 ComfyUI graph 的差异

ComfyUI 当然可以按节点顺序执行二次采样，但它不会仅凭 workflow JSON 自动得到上游的 planner 合同。差异包括：

| 能力 | 简单 ComfyUI workflow | Native planner/engine |
|---|---|---|
| graph 正确性 | 可以表达节点连接和 sampler | 同样支持，但 graph 由 typed stage 固定 |
| 模型加载 | ComfyUI 负责可用时的 offload | launcher 预先选择权重 tier 和驻留策略 |
| 显存峰值 | 依赖 ComfyUI device/offload/节点行为 | 有 provisioned/planner budget 和 stage boundary |
| 二阶段切换 | 可以通过 latent 节点连接 | engine 管理 eviction、buffer、prefetch |
| 长视频 | 需要另行做 temporal/spatial tiling | profile 已规定 compact/streaming 策略 |
| artifact | 需要我们补充 joint AV serializer | Native backend 已保存 clean latent 和 safe path |
| 降级 | workflow 可能因节点/显存失败 | 上游明确禁止 silent backend switching |

所以 AD-02 必须吸收 capability profile 和 evidence state；AD-03 先在 ComfyUI 中证明 graph/shape/音频正确性；AD-07 再比较显存和速度；只有不能达到目标时才评估 AD-08 Native sidecar。

## 8. 本地代码与当前缺口

### 8.1 已有能力

本地现有 H3 相关边界包括：

- minimax_h3_fl2va 和 minimax_h3_ref2va catalog；
- H3 FL2VA/R2V 的官方 INT8、Qwen、video/audio VAE、preview TAE 等组件声明；
- supportsEndFrame、supportsVideoExtension、Ref2VA 最多 9 张图等产品字段；
- H3 MiniMaxH3SigmaShift、Turbo、LoRA、Spectrum、Memory 等基础 workflow 路径；
- environment.ts 对 /system_stats、/object_info 和 ModelSamplingAV 的离线/运行时探测；
- Electron Queue/History 已有不可变 queued snapshot、恢复、清理和路径管理边界。

这些能力足以承载 AD-03 的实验入口，但不能被误标为二次采样已完成。

### 8.2 当前 workflow 结构

当前 workflows/minimax_h3_i2v_api.json 的主路径是：

~~~text
Loaders / H3 ImageToVideo / KSampler graph
    -> SamplerCustomAdvanced
    -> VRAM_Debug
    -> video VAE decode
    -> audio VAE decode
    -> CreateVideo
    -> SaveVideo
~~~

它没有：

- LTXVSeparateAVLatent / LTXVConcatAVLatent 的二阶段分支；
- video latent upscaler；
- conditioning upscaler；
- H3-safe AddNoise；
- second sampler；
- clean joint AV latent 的持久化。

当前 R2V workflow 也没有二次采样分支。现有 targetHeight 字段包含 1440/2160 等通用值，不等于 H3 已经具备 1440 的 workflow、model、node、artifact 和 VRAM 证据。

### 8.3 当前本地 runtime 与 artifact 边界

environment.ts 目前通过版本或源文本发现 ModelSamplingAV，它证明的是 H3 dual-clock/core support，不是 H3 second-sampling support。AD-02 需要把至少以下状态分开：

~~~text
H3 core dual-clock
H3 NestedTensor split/concat
H3 second-sampling nodes
H3 learned/interpolation latent upscaler
H3 clean joint AV serializer
H3 1440 capability profile
H3 real runtime smoke
~~~

docs/H3_NATIVE_MASKED_AV_LONG_VIDEO_PLAN.md 已指出 stock SaveLatent 不能直接作为 H3 NestedTensor 的可靠联合保存方案。我们需要一个经过测试的 serializer/manifest，至少记录：

- schemaVersion；
- manifest/payload 路径；
- bytes/SHA-256；
- model family、execution model、workflow revision；
- width/height/fps/frame count；
- video shape/dtype；
- audio sample rate/channels/rate/shape/dtype；
- context frames；
- source task/version/createdAt；
- 完整性和恢复状态。

这个 artifact 是 AD-04 的职责，不能在 AD-03 中用任意 .pt 或 Motion Context 文件临时冒充。

## 10. 吸纳决策和实施顺序

### 10.1 现在吸收的内容

AD-01 结束后可以立即进入文档/纯函数设计的内容：

1. source/revision/bytes/sha256/license/profile 模型证据结构；
2. H3 2k -> 1440 的公开分辨率语义；
3. 第一阶段/第二阶段正交 capability profile；
4. GenerationSpec 与 SecondSamplingSpec 分离；
5. clean joint AV latent、child job、safe path 和 artifact manifest 的语义；
6. H3 AV latent 的 shape、NestedTensor、17k+5 frame geometry、32 对齐；
7. Static validated、Runtime validated、Product integrated 的证据状态；
8. no silent backend switching 和模型/节点/服务三态区分。

### 10.2 暂不吸收的内容

- 不把 PyTorch 2.13 写进当前产品依赖；
- 不全局启用 Sage/Sparge 或 H3 Memory；
- 不复制上游 Native Engine、connector 或其 patch；
- 不把社区 GPL custom node 直接加入专有产品；
- 不把 learned upscaler 权重加入默认安装器，直到 pinned revision 的许可证和本地显存证据确认；
- 不把 UI 的 1440/2160 通用字段当作 H3 1440 已支持；
- 不在现有默认 H3 workflow 上直接插二采样节点；
- 不在没有 /object_info 和实际最小生成的情况下声称 runtime support。

### 10.3 后续执行顺序

~~~text
AD-02 capability/evidence pure functions
    -> AD-03 ComfyUI-only 720 -> 1080 POC
    -> AD-03 1080/720 -> 1440 POC
    -> AD-04 clean joint AV artifact
    -> AD-05 queue/provider/history child task
    -> AD-06 History/Queue/Create UX
    -> AD-07 resource/doctor/real hardware evidence
    -> AD-08 only if ComfyUI route has an evidence-backed limit
    -> AD-09 only after M5 and explicit API plan
~~~

AD-03 的 workflow 必须是独立实验文件。它不应先替换当前默认 workflow，也不应让用户在没有 capability/evidence 的情况下看到“原生 2K”可选项。

## 11. AD-03/AD-04 的验收门

### Gate A：静态节点和 schema

- 当前选定 ComfyUI 的 /object_info 可读；
- 每个节点的真实 class type、input、output、version 都有快照；
- H3 core、split/concat、upscale、conditioning、AddNoise、sigma、second sampler 的连接与 schema 通过静态检查；
- workflow hash 和 source model manifest hash 已记录；
- 旧 ComfyUI 版本缺节点时，UI 只显示 unavailable，不静默替代。

### Gate B：短时真实 ComfyUI-only smoke

- 使用当前 PyTorch 2.10；
- FL2VA、无 LoRA、无 Spectrum、无 Sage；
- 先完成最小合法帧数（5 帧或 17k+5 中的最小合法值）和短时长；
- 第一阶段完成视频和音频解码；
- 同一 task 的 clean joint AV latent 能进入第二阶段；
- 第二阶段输出视频、音频和 metadata 均存在；
- 记录显存峰值、host/shared memory、sampler steps、耗时和 output hash。

### Gate C：artifact

- joint AV latent 以明确 schema 保存，不依赖 PyTorch 当前 pickle 环境的偶然可读性；
- payload 写入临时路径后原子提交；
- manifest 的 bytes/SHA 与 payload 一致；
- 重启后可恢复 parent/child 关系；
- 损坏、缺文件、版本不兼容会进入可解释失败状态；
- History 删除、任务取消和输出清理不留下孤儿 artifact。

### Gate D：资源合同

- 720p → 1080p 先测，再测 1440；
- 采样期间不同时驻留不必要的 DiT、upscaler、VAE 和 text encoder；
- peak VRAM 不仅看 nvidia-smi，还要记录 WDDM/shared-memory paging；
- 不用“自动降到 1080”掩盖 1440 失败；
- 每个 profile 的失败原因可区分：权重缺失、node schema、OOM、kernel abort、artifact、VAE/audio、license/unavailable。

### Gate E：产品回归

- queue entry 是不可变执行快照；
- parent task 和 second-sampling child task 的参数、状态、输出和历史 metadata 一致；
- cancel/restart/recovery 不破坏 latent artifact；
- History detail 能回到 parent，且媒体/音频/错误状态可查看；
- ComfyUI offline 时仍可管理 catalog/manifest，runtime validation 只在连接后补充；
- 只有一个 heavy GPU generation/post-processing stage 在执行。

## 13. 未决问题和阻塞点

以下内容仍必须在 AD-03/AD-07 通过本机 evidence 解决：

1. 当前用户选定的 ComfyUI 安装具体 revision 和 /object_info 是否有官方 H3 节点；
2. 本地 PyTorch 2.10 + ComfyUI 0.33.x 是否能稳定执行 NestedTensor 二次采样；
3. stock sampler 的 DisableNoise、H3 ModelSamplingAV 与 custom AddNoise 的组合方式；
4. 720p → 1080p、1080p → 1440p 在 RTX 4090 Windows WDDM 下的峰值显存和 shared-memory 行为；
5. learned upscaler pinned revision 的实际 LICENSE 与模型使用条款；
6. H3 clean joint AV latent 的跨进程、跨重启、跨 torch minor version 可读性；
7. H3 reference/keyframe conditioning 在二阶段尺度变化后的质量和 shape；
8. 纯 ComfyUI 的 temporal/spatial tiling 是否会造成接缝、音画不同步或 History artifact 过大；
9. 是否存在必须依赖 Native Engine 才能满足的 24GB/15 秒/1440p 资源合同；
10. 上游 release manifest 与 VALIDATION test count 不一致的具体 commit 原因。

在这些问题没有证据前，产品文案只能说“实验性 H3 二次采样候选”，不能说“已支持原生 2K”。
