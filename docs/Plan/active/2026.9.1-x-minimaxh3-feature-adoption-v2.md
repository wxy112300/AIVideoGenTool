## 0. 执行摘要

本节是已废止的 V2 执行摘要，仅用于解释当时的设计背景；其中的“优先发布”顺序不再有效。

1. MiniMax H3 的 Create 分辨率列表在 `768p` 后追加 `1080p`、`1440p`；
2. 两个高分辨率值表示“首遍 H3 生成 + clean AV latent + H3 原生二次采样”的复合任务，不是单阶段原生生成，也不是 SeedVR2/MP4 后处理；
3. `1080p`、`1440p` 始终可见，但只有专用 H3 高分辨率环境通过门禁时可选；缺环境、缺权重、schema 不兼容或只有静态证据时必须禁用并显示精确原因；
4. 选择高分辨率后，入队快照冻结 provider、首遍尺寸、二采尺寸、模型/LoRA、资源 profile、artifact 策略和 fallback 策略，执行时自然进入专用环境；不允许静默回落到 `768p`、SeedVR2、普通 ComfyUI 或另一个显存档；
5. clean H3 音视频 latent 采用一个 joint payload（固定 `video`、`audio` 两个 key）加一个 manifest，而不是把 video/audio 拆成无法原子关联的两份文件；
6. 对复合高分辨率任务，首遍和二采完成态各保存一个 joint AV artifact。两者几何不同，不能合成一个超大 payload；用同一 lineage manifest 关联。首遍 artifact 可重试二采，最终 artifact 默认供 Native Extend 使用；
7. 所有 MP4、artifact payload/manifest 和可恢复 checkpoint 都位于用户配置的同一个 `videoOutputDirectory` 根下，各自进入固定受管子目录；不写入图片素材库，也不依赖 ComfyUI 的偶然临时目录。

独立后端结论：**要引入可选的 H3 专用 sidecar/provider 边界，但不能直接复制或打包当前 X-MinimaxH3 Native Engine。** 上游原创代码是 all-rights-reserved，明确未授予 use/copy/modify/distribute；其验证环境又是 Linux/WSL2、Python 3.10.20、PyTorch 2.13.0+cu130、CUDA toolkit 13.3。产品路线应是：现有 ComfyUI provider 保持默认；高分辨率功能使用隔离的、应用托管的 H3 sidecar。sidecar 的实现来源必须在开始编码前满足以下其一：

- 获得 X-MinimaxH3 作者的书面使用/集成/分发许可；
- 只把获许可的上游服务当外部用户安装服务，通过公开协议连接；
- 基于允许使用的官方/社区组件做 clean-room 实现，不复制受限源码、测试或内部结构。

上述许可证 Gate 处置已被 V3 收窄：Gate 未通过时不得把 disabled UI 当作产品进度，也不得登记为普通用户可自动安装；只允许保留隔离的静态研究与开发者手工 POC。

## 3. 冻结的产品行为

### 3.1 Create 分辨率和门禁

对兼容的 H3 FL2VA/Ref2VA Base/LoRA 创建模式，分辨率顺序为：

```text
360p → 480p → 540p → 720p → 768p → 1080p → 1440p
```

- `1080p`、`1440p` 只表示最终交付 short edge；实际宽高继续按 ratio/source 和 H3 32-pixel grid 计算，不能假设所有比例都是 1920×1080 或 2560×1440；
- 两项可见但 disabled 时，tooltip/inline reason 必须指出是 sidecar 未安装、未启动、profile 不支持、权重缺失、hash 不符、GPU/OS 不支持、runtime 未验证还是当前模型/LoRA 不兼容；
- Draft 可以保留暂时不可用的高分辨率选择，但 enqueue 必须 blocked；刷新环境后自动重新计算 availability，不静默改写 Draft；
- 从高分辨率 H3 切换到不支持的模型时，要求用户明确选择新分辨率，不能由 `nearestSupportedVideoResolution()` 自动把它悄悄归一为 `768`；旧 persisted draft 没有新字段时保持原默认；
- 普通 `<=768p` 保持现有 ComfyUI 执行。高分辨率选择冻结 `deliveryMode: "h3-native-second-sampling"` 并路由到 ready provider；
- 首遍分辨率不是 renderer 常量，由 capability profile 给出并冻结到 task。第一版候选为 720/768，必须以实际 provider 合同和显存证据确定；
- 高分辨率任务是一张队列卡、一个用户任务、分阶段进度。内部可创建 stage/child execution record，但不得让 sidecar queue 成为第二真相。

### 3.2 阶段和输出

```text
preflight
  → conditioning / reference preparation
  → first-pass H3 sampling
  → first-pass MP4 + clean joint AV artifact A 原子提交
  → learned 3D latent upscale / temporal-spatial plan
  → Base + SA Solver native second sampling
  → final MP4 + clean joint AV artifact B 原子提交
  → media/PTS/A-V/hash validation
  → History commit
```

- 二采固定使用经验证的 Base 权重、sampler、scheduler 和 strength profile；LoRA 只影响首遍，除非未来独立证据证明某 LoRA 可参与二采；
- 二采失败时，任务显示失败在 second-sampling stage，同时保留已成功的首遍 MP4/artifact 供“重试二采”或查看；不得把首遍冒充用户选择的 1080/1440 成功输出；
- History 可提供“从此版本重新二采”的补充动作，但 Create 高分辨率是主入口；
- 首遍和最终 MP4 都在 output 根的正常视频布局中；artifact 放固定 `h3-native-av/`；formal checkpoint 放固定 `h3-checkpoints/`。每个目录都必须由 StudioPaths 和安全路径解析管理。

### 3.3 两级 clean AV artifact 决策

每个完成态 artifact 都是：

```text
<videoOutputDirectory>/h3-native-av/
  h3av_<artifactId>.safetensors  # fixed keys: video, audio
  h3av_<artifactId>.json         # manifest, committed last
```

对复合任务保存：

- `first-pass-clean-av`：低分辨率完成态，用于不重跑首遍的二采重试；
- `final-clean-av`：1080/1440 完成态，默认供 Native Masked AV Extend、后续二采或诊断使用。

两者分别是 joint video/audio payload，不把两个分辨率合并进同一个 safetensors。manifest 增加：

```ts
role: "first-pass-clean-av" | "final-clean-av" | "extend-segment-clean-av";
lineageId: string;
derivedFromArtifactId?: string;
sourceTaskId: string;
sourceVersionId?: string;
providerId: string;
providerRevision: string;
workflowRevision: string;
model/VAE/text-encoder/upscaler identity + sha256;
geometry/frame/fps/audio/shape/dtype fields;
payload bytes + sha256;
```

本计划直接复用 `H3_NATIVE_MASKED_AV_LONG_VIDEO_PLAN.md` 的 `NativeAvContinuationArtifact`、原子提交、删除、迁移、共享引用和 path fallback 规则。与并行 Extend agent 的接口冻结为：

- 一个 schema owner；
- 一个 serializer/validator/service；
- 一个 fixed directory；
- 一个 History/AssetVersion 引用类型；
- 二采只新增 `role`、lineage 和 provider/upscaler metadata，不另建 `SecondSamplingArtifact` 二进制格式；
- Extend 默认读取当前 History 版本的 `final-clean-av` 或 `extend-segment-clean-av`，绝不读取 formal checkpoint；
- 若两边同时需要修改 `src/types.ts`、`electron/store.ts` 或 History deletion/migration，必须串行由单一 owner 合并。

### 3.4 Formal checkpoint / preview / resume

- clean final AV 用于二采和 Extend；formal checkpoint 用于从某个 solver step 恢复。二者都含 video/audio，但语义不同，不能“合体”；
- checkpoint 必须额外冻结 provider/resource profile、step/next step、video/audio sigma、完整 schedule、seed、prompt/reference hash、LoRA identity、solver history 和所有影响恢复确定性的 runtime state；
- 首版先做失败/重启后的整 stage 恢复：如果 artifact A 已 committed，只重跑二采；随后再实现 sampler-step checkpoint；
- 低成本 preview 是 checkpoint 的可丢弃派生媒体，不替代 checkpoint；删除 preview 不影响恢复；
- checkpoint 使用版本化安全格式。若必须包含无法放入 safetensors 的小型结构，使用 safetensors + 严格 JSON manifest/state，禁止任意 pickle 作为长期产品契约；
- retry 不覆盖旧 committed artifact/checkpoint；cancel 只清当前 partial；clear recovery data 不删除 MP4，并明确让哪些任务失去 resume/second-sampling/Extend fast path。

### 3.5 History / Upscale 增加 H3 原生方案

用户可以从现有 Upscale 入口选择两种不同方法，但领域任务和能力门禁不能混用：

```text
Upscale 方法
  ├─ SeedVR2 / 像素视频超分：输入 MP4，适用于普通视频
  └─ H3 原生二次采样：输入兼容的 clean joint AV artifact，只适用于 H3
```

- H3 方法只在当前 `AssetVersion` 有 committed、hash/shape/producer 兼容的 clean AV artifact，原始 prompt/reference/conditioning contract 仍可重建，且 H3 provider/profile runtime-ready 时启用；
- 只有 MP4、只有音轨、只有 Motion Context latent、artifact 已清理或 source family 不兼容时，H3 方法 disabled 并显示原因，SeedVR2 仍保持可用；
- UI 可以共用 Upscale 对话框，内部应创建独立的 `H3SecondSamplingQueueTask` 或等价 discriminated task，不复用现有 `UpscaleQueueTask` 的 MP4/SeedVR2 语义；
- source History version、artifact id/hash、目标尺寸、provider/profile、Base 二采模型、steps、strength、temporal window 和 reference fingerprints 在入队时冻结；
- 二采输出作为同一 History asset 的新 version，并写新的 `final-clean-av`。源 version、源 artifact 和源 MP4 保留；失败不得覆盖源版本；
- Create 直接选择 1080/1440 与 History → Upscale → H3 原生二采调用同一个 application service/provider，只是前者自动串联首遍，后者从既有 committed artifact 开始。

#### 3.5.1 已调查的分辨率边界

上游 contract 的二采目标只有 `720p / 1080p / 1440p`，要求目标宽和高都严格大于源 canvas、按源比例与 32-pixel H3 grid 解析，并受 `target width × height × frames` 预算约束。二采使用 Base、1–8 步、四档重绘强度，时间窗口为 68–362 帧，默认保留首遍 audio latent。

`480p → 1440p` 是明确支持且已有上游真实证据的路径，不只是从代码推断：上游记录了 480p、15 秒、362 帧 clean AV 到 2560×1440、24 FPS、32 kHz 双声道的完整二采和封装；16GB INT8 release gate 也覆盖了 Ref2VA + 1 图 + 1 独立音频。它不是 3× 像素插值，而是 learned 3D video-latent upscale 后进行低噪声 H3 二采，audio latent 默认原样保留。

本项目初始开放矩阵应保守于上游静态 contract：

| 源 clean AV | 720p 目标 | 1080p 目标 | 1440p 目标 | 首版处理 |
| --- | --- | --- | --- | --- |
| 480p | 可 | 可 | INT8 16/24GB 可；8GB 不可 | 第一批真实 smoke 与开放锚点 |
| 720p | 同尺寸，拒绝 | 可 | INT8 16/24GB 可；8GB 不可 | 480 路径通过后开放 |
| 1080p | 降采，拒绝 | 同尺寸，拒绝 | INT8 16/24GB 可 | 独立 smoke 后开放 |
| 360p | contract/shape 候选 | contract/shape 候选 | INT8 contract 候选 | 缺完整质量锚点，先 disabled/evidence-gated |
| 本项目 540p / 768p | 非上游 canonical source preset | 非上游 canonical source preset | shape 上可能可行 | 每档、每比例真实 smoke 后逐项开放 |
| 外部 MP4 / 无 artifact | 不可直接 H3 二采 | 不可直接 H3 二采 | 不可直接 H3 二采 | 只显示 SeedVR2；若未来重编码，必须明确标成 encoded-media 路线 |

补充边界：

- 16:9 的名义 1440p 为 2560×1440；其他比例以 1440 short edge 和 32 对齐后的实际几何为准；
- FL2VA 与 Ref2VA artifact 不可跨服务族；INT8 与 W4A8 profile 不可静默互换；
- 8GB W4A8 上游 profile 最高只开放 1080p 二采；1440p 必须在提交 GPU 工作前拒绝；
- 首遍若使用 LoRA，二采仍固定 Base；History 必须显示“首遍 LoRA / 二采 Base”；
- Ref2VA 静态参考图和独立音频 conditioning 可以跨目标几何复用；FL2VA 首尾帧与参考视频带几何/时间语义，应重建或重新验证 conditioning，不能只凭缓存文件存在判定兼容；
- 超长/多参考视频会扩大 packed prefix，即使分辨率在表内也可能被资源 planner 拒绝；reason code 必须区分 geometry、pixel-frames、reference budget 和 runtime memory；
- 产品开放需要本项目 own smoke。上游成功记录是可行性证据，不替代 Windows/实际 provider 的 Product Integrated Gate。

## 4. Provider 与专用环境架构

### 4.1 领域契约

建议新增纯领域对象，具体命名可按现有风格调整：

```ts
interface H3DeliveryPlan {
  deliveryMode: "direct" | "h3-native-second-sampling";
  providerId: "comfyui" | "h3-native-sidecar";
  requestedResolution: 360 | 480 | 540 | 720 | 768 | 1080 | 1440;
  firstPassResolution: 360 | 480 | 540 | 720 | 768;
  secondSampling?: {
    targetResolution: 1080 | 1440;
    profileId: string;
    steps: number;
    strengthProfile: string;
    temporalContextFrames: number | "auto";
  };
  resourceProfileId: string;
  artifactPolicy: "save-final" | "save-first-and-final";
  providerEvidenceId: string;
}
```

`H3CapabilityProfile` 是 Create、queue、Settings 和错误文案的唯一限制来源，至少表达 service family、quantization、GPU architecture、VRAM tier、首遍/二采尺寸时长上限、reference image/video/audio 限制、LoRA profile、required assets/runtime、evidence level 和 reason codes。

### 4.2 应用 port

```text
H3ExecutionProvider
  inspectEnvironment()
  preflight(frozenTask)
  executeStage(stage, progress, cancellation)
  validateArtifact(reference)
  recover(checkpoint, progress, cancellation)
  releaseRuntime()
```

- Queue/application service 决定顺序、状态、取消、恢复和 History；provider 只执行冻结的 stage；
- sidecar 只监听 loopback，使用随机/配置端口和 session token；不得默认 LAN 暴露；
- app 启动时不预热 H3 sidecar。只有选中高分辨率或明确启动环境时加载；切回 ComfyUI/退出应用时按策略释放；
- ComfyUI 和 sidecar 不得同时驻留两套 H3 大模型。切换 provider 前先 drain 当前 GPU stage，再 unload/stop、确认显存释放后启动另一 provider；
- sidecar 崩溃不杀 Electron，不污染 ComfyUI managed state；错误保留日志、阶段、exit code 和可恢复 artifact；
- 不把上游 REST durable queue 直接接进产品。即便获许可复用其服务，也应使用单任务执行/查询/取消的窄 connector，并把 upstream job id 当 execution metadata，不当产品 task id。

### 4.3 Settings 环境页

新增独立 “H3 高分辨率环境” 卡片，与 ComfyUI 环境并列而非混入同一个 installed 状态：

- provider source/license 状态；
- Windows/WSL2/driver/GPU architecture；

## 8. 关键测试与验证矩阵

### 8.1 静态/单元

- capability：provider/profile/model/LoRA/GPU/env 的可用与 reason code；
- resolution：所有 ratio/source、32 对齐、1080/1440 不被 nearest helper 静默降级；
- queue snapshot：first/target resolution、provider/profile、artifact policy、steps/strength frozen；
- artifact：fixed keys、shape/dtype、hash/bytes、path traversal、partial/atomic commit、lineage；
- persistence：旧 draft/queue/history、无 artifact、失效 artifact、迁移、duplicate/retry/reset；
- reference：9 images、3 videos、3 audios、total/duration/empty/unsupported type；
- LoRA：FL2VA/Ref2VA、Base/INT8/W4A8、known/unknown、二采 no-LoRA；
- provider：preflight、progress、timeout、cancel、crash、restart、log sanitization、single GPU lease；
- renderer：disabled reason、环境刷新后 availability、连续输入/焦点、mode/model switch、enqueue；

- History：first/final media、artifact status、second-stage retry、Extend source selection、delete/migrate/shared ref。

### 8.2 Runtime Gate

每条 evidence 绑定：app commit、provider source/revision/license、OS/WSL、GPU/SM/driver、Python/Torch/CUDA/toolkit、model/VAE/Qwen/upscaler/LoRA hashes、profile、workflow/RPC schema、seed/steps/尺寸/帧数、阶段耗时、peak VRAM/shared/RAM/power/temp、artifact hashes、MP4 hash、A/V/PTS 结果。

按顺序执行：

1. provider doctor + 最小 import/ABI smoke；
2. FL2VA Base 低分辨率真实生成并保存 artifact A；
3. artifact A reload 后同尺寸低噪声二采，验证算法而非 upscale；
4. 720/768 → 1080；
5. 720/768 → 1440；
6. History/Upscale 独立执行 480 → 1080、480 → 1440；
7. 540/768 source preset 的逐比例 smoke，未通过前保持 evidence-gated；
8. app cancel、sidecar crash、app restart 后从 artifact A 重试二采；
9. final artifact B → 单段 Native Extend；
10. Ref2VA 1 image/1 video/1 independent audio；
11. Ref2VA 最大输入和 15 秒边界；
12. LoRA 首遍 + Base 二采；
13. 16GB/8GB profiles 逐个独立验证。

只有真实 MP4 和 artifact 均成功并通过检查才叫 smoke passed。workflow 构造、HTTP 200、节点 import、单步 DiT、checkpoint 或 preview 均不能冒充完整 generation。

### 8.3 产品 Gate

- `npm.cmd run verify`；
- Create、Queue、History、Settings、相关 detail pages 的两个合同 viewport；
- H3 普通 ComfyUI 360–768、Q3/INT4、FL2VA/Ref2VA、Motion Context、Boundary Extend、Native Extend、SeedVR2 邻接回归；
- local Comfy startup takeover/exit、sidecar startup/stop/crash、两者不双驻留；
- output directory change 与“未来输出/迁移已有”两种语义；
- offline file management、online schema validation、runtime smoke 三态不混淆；
- 失败不静默换 provider、模型、分辨率、LoRA 或后处理路线。

## 9. 失败策略与安全边界

以下一律 fail closed 并保留精确阶段：

- 上游授权不明确却试图复制/打包其代码；
- sidecar/runtime/asset/hash/ABI/schema/profile 不匹配；
- artifact missing/corrupt/hash/shape/producer 不兼容；
- 只有 MP4 而请求 direct second sampling；
- 1440 OOM 后自动降 1080/768；
- LoRA 或服务族不兼容；
- GPU 已有重任务或 provider 切换后显存未释放；
- 输出 MP4 缺音频、帧数/尺寸/PTS 不符；
- checkpoint 无法证明与冻结 task 完全匹配。

不得对用户声称上游的 24/16/8GB、速度或质量结果已在本项目成立。上游已验证平台是 RTX 4090 SM89 + Linux/WSL2；逻辑硬 cap 也不等于物理低显存卡验收。

## 10. REST/Web/Comfy connector 的最终定位

模块化重构已完成，所以 P9 不再受旧 M5 阻塞，但仍排在本地产品闭环之后：

```text
Electron / optional REST / optional Comfy connector
                     ↓
              ApplicationRuntime
                     ↓
      single Queue / History / State / GPU arbiter
                     ↓
       ComfyUI provider | H3 sidecar provider
```

- REST 只映射已有 application commands/queries/events；
- 默认 loopback + authentication，LAN/TLS/多租户另立安全计划；
- Web UI 若实现，消费同一 API，不复制业务规则；
- Comfy connector 只提交/观察本应用 task，不在 ComfyUI 再加载一套 H3，也不直接绕过本应用访问 sidecar；
- task id、进度、取消、History 和输出只有本应用一套真相。
