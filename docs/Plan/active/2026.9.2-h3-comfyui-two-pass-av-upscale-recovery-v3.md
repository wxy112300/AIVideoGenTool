## 1. 冻结结论

### 1.1 ComfyUI 能独立完成主路线，不需要 X-MinimaxH3 core

当前 H3 ComfyUI 工作流已经能产生 joint audio/video latent。二次采样所缺的是：

1. 正确拆分 joint AV latent；
2. 学习型 3D video-latent resize；
3. 分别处理 video/audio noise 与 sigma；
4. 重新拼成 joint AV latent；
5. 重建目标分辨率 conditioning 后进行第二遍 H3 sampling；
6. 安全保存/加载 joint AV artifact；
7. 应用侧两阶段队列、结果采集、History 和失败恢复。

这些都可以由 ComfyUI core、受管 custom nodes、API workflow 和现有 Electron 编排完成。X-MinimaxH3 的 Comfy connector 本质上只调用其独立 H3 Serve HTTP 服务，把整个仓库放进 `custom_nodes` 不会把 Native Engine 变成一个可执行 Comfy 节点。

因此 V3 决定：

- **首发只做纯 ComfyUI provider**，provider id 使用现有 `comfyui`，不新增第二套队列、History 或 Settings 真相；
- **不把 X-MinimaxH3 整仓当节点安装**，不复制、打包或自动下载其 all-rights-reserved 源码；
- sidecar 仅作为未来独立项目，只有取得明确许可、Windows 安装包和真实 smoke 后才另立计划；
- 当前 `h3-native-sidecar` 占位实现不能继续驱动产品 UI，也不能算环境集成。

### 1.2 用户可见行为

完成后，兼容 H3 Create 的分辨率顺序为：

```text
360p → 480p → 540p → 720p → 768p → 1080p → 1440p
```

- `<=768p` 继续走现有单阶段 H3 ComfyUI workflow；
- Create 选择 `1080p` 表示 **H3 原生 1080p 单阶段直出**。在资源 profile 与真实 smoke 通过后，workflow 直接以 1080p H3 canvas sampling 并保存最终 MP4 + `final-clean-av`；不得暗中改成 480p/720p 二采；
- Create 选择 `1440p` 表示 **面向用户的一条原生 1440p 直出任务**，内部采用上游推荐并有公开对比的 `720p 首遍 → 1440p H3 原生二采`。这是生成任务的内部两阶段，不在 UI 上称为 Upscale，也不使用 480p 默认源；
- `480p → 1080p/1440p` 只属于 History → H3 Upscale、低显存实验或显式性能 profile，不得作为 Create 直出默认值；
- X-MinimaxH3 的 contract 允许目标宽高大于源画布，其 README 的公开质量对比是 `720p → 1440p`；本项目以该路线作为 Create 1440p 的初始推荐锚点；
- 本项目现有 540p/768p 在 learned upscaler 的倍率范围内，但只作为 History Upscale 候选，完成自己的分辨率、比例、音频和显存 smoke 后再开放；
- UI 仍只显示一个分辨率下拉框。renderer/enqueue 必须将 `1080p` 映射为 direct-high-resolution，将 `1440p` 映射为 native-1440 composite，不能让用户看到或选择隐藏的 480p 首遍；
- 环境不完整时 `1080p/1440p` 可见但不可选，并显示具体缺项；环境就绪后自然走同一个应用托管 ComfyUI；
- 不能静默降级到 768p、SeedVR2 或普通像素插值。

History 的 Upscale 对话框保留两个语义不同的方法：

```text
SeedVR2：输入 MP4，输出像素超分视频
H3 原生二次采样：输入 committed clean joint AV，输出新 H3 版本及新的 clean joint AV
```

H3 Upscale 可从任何 **低于目标且通过兼容性验证的 clean AV** 到 1080p 或 1440p。首发至少覆盖 480p 与 720p 源；仅有 MP4、Motion Context latent、损坏 artifact 或无法重建 conditioning 时不能选择 H3 方法，但 SeedVR2 不受影响。

### 1.3 AV 文件决策

1440p 复合任务的“两种 AV”不合进一个超大文件。首遍和最终结果的 geometry 不同，应保存两个独立 joint payload，用 lineage 关联：

```text
<videoOutputDirectory>/h3-native-av/
  h3av_<firstId>.safetensors   # keys: video, audio
  h3av_<firstId>.json          # role: first-pass-clean-av
  h3av_<finalId>.safetensors   # keys: video, audio
  h3av_<finalId>.json          # role: final-clean-av, derivedFromArtifactId: firstId
```

两份文件都属于同一个 output 根，分别附着到对应 `AssetVersion`：

- Create 1080p 单阶段直出只保存一个 1080p MP4 + `final-clean-av`，不得制造同尺寸的“首遍 AV”；
- Create 1440p 内部首遍保存 720p MP4 + `first-pass-clean-av`，用于恢复/重试；最终保存 1440p MP4 + `final-clean-av`；
- History → H3 Upscale 产生的新版本同样保存自己的 `final-clean-av`；
- Extend 直接消费相同的 `NativeAvContinuationArtifact` 与文件服务，不得再造 `ExtendAvArtifact` 或另一目录；
- MP4 是 durable 主输出；AV 保存失败必须明确显示“视频成功、AV 未保存”，不得谎报 AV 可用于 Upscale/Extend。

## 4. 统一领域与持久化契约

### 4.1 不再污染首遍 resolution

保留现有低分辨率 `resolution` 语义，新增明确的 delivery plan：

```ts
type H3BaseResolution = 360 | 480 | 540 | 720 | 768;
type H3DeliveryResolution = 1080 | 1440;

type H3DeliveryPlan =
  | { kind: "direct"; baseResolution: H3BaseResolution }
  | {
      kind: "direct-high-resolution";
      targetResolution: 1080;
      profileId: string;
      artifactPolicy: "final";
    }
  | {
      kind: "native-1440";
      firstPassResolution: 720;
      targetResolution: 1440;
      profileId: string;
      artifactPolicy: "first-and-final";
    };
```

Renderer 可以把它们投影为一个列表，但 enqueue 后冻结的是整个 `H3DeliveryPlan`。旧 persisted draft 没有该字段时迁移为 `direct`，不改变原 resolution。

### 4.2 两个独立 queue task，避免复用 SeedVR2 语义

```ts
interface H3TwoPassGenerationQueueTask {
  taskType: "h3-two-pass-generation";
  generationSnapshot: /* 现有不可变 H3 request */;
  deliveryPlan: Extract<H3DeliveryPlan, { kind: "native-1440" }>;
  conditioningSnapshot: H3ConditioningSnapshot;
  outputDirectorySnapshot: string;
}

interface H3SecondSamplingQueueTask {
  taskType: "h3-second-sampling";
  sourceAssetId: string;
  sourceVersionId: string;
  sourceArtifact: FrozenNativeAvArtifactReference;
  conditioningSnapshot: H3ConditioningSnapshot;
  targetResolution: 1080 | 1440;
  profileId: string;
  outputDirectorySnapshot: string;
}
```

- Create 1080p 继续使用 generation task，但冻结 `direct-high-resolution` plan，直接运行 1080p workflow 并保存一个 final artifact；
- Create 1440p 才产生 `h3-two-pass-generation`，内部固定推荐的 720p→1440p；
- History → H3 Upscale 产生第二类任务；
- 两者共用 `H3SecondSamplingService`，而不是把 H3 塞进 `UpscaleQueueTask`；
- task snapshot 必须冻结 artifact id/path/hash、源 geometry、模型/VAE/encoder/upscaler identity、prompt、seed、参考素材 fingerprint、目标、steps/sigmas 和 workflow revision；
- queue 恢复时从冻结 snapshot 重建，不读当前 Draft 或当前 catalog 默认值。

### 4.3 conditioning 可重建性

AV 文件本身不是完整二采输入。每个可用于 H3 Upscale 的版本还必须有 `H3ConditioningSnapshot`：

- source family：FL2VA 或 Ref2VA；
- prompt/negative prompt 与 tokenizer/encoder identity；
- 首尾帧、参考图/视频/独立音频的受管路径、hash、顺序、裁剪/时长参数；
- 首遍 model/quantization/LoRA identity；
- 二采固定 Base/no-LoRA policy；
- source/target geometry、frames、fps/audio rate；
- workflow revision 与所有 sampler/sigma 参数。

首版支持顺序：

1. FL2VA Base，源素材仍在且 hash 匹配；
2. Ref2VA Base；
3. 首遍含 LoRA、二采固定 Base；
4. 更复杂参考视频/独立音频组合。

没有 snapshot 的旧 H3 MP4 不能因为“模型名像 H3”就开放原生 Upscale。

### 4.4 artifact schema 的单一 owner

沿用 `NativeAvContinuationArtifact`，最少包含：

```ts
schemaVersion: 1;
artifactId: string;
role: "first-pass-clean-av" | "final-clean-av" | "extend-segment-clean-av";
lineageId: string;
derivedFromArtifactId?: string;
sourceTaskId: string;
sourceAssetId?: string;
sourceVersionId?: string;
providerId: "comfyui";
producerNodeId: string;
producerNodeVersion: string;
workflowId: string;
workflowRevision: string;
payload: { relativePath: string; bytes: number; sha256: string };
manifest: { relativePath: string; bytes: number; sha256: string };
video: { shape: number[]; dtype: string; width: number; height: number; frames: number; fps: number };
audio: { shape: number[]; dtype: string; sampleRate: number; channels: number };
```

路径只能是 output root 下的受管相对路径。manifest 最后写入表示 commit 完成。删除时先构建引用集合：History versions、排队/恢复中的二采任务、Extend 计划任一处仍引用，都不能删除 payload。

## 5. ComfyUI 工作流设计

### 5.1 app-owned joint AV serializer/loader

新增一个最小、原创、可版本化的 custom-node 包；建议源码位置：

```text
comfy_nodes/LocalVideoStudio-H3/
  __init__.py
  nodes.py
  requirements.txt
  VERSION
```

只实现产品缺口，不复制第三方 sampler/upscaler：

```text
LocalVideoStudioH3SaveJointAV
LocalVideoStudioH3LoadJointAV
```

Save node：

- 只接受 H3 joint NestedTensor，严格要求两个 tensor；
- 固定 safetensors keys 为 `video`、`audio`，转 CPU contiguous 后写入；
- 写 `<name>.safetensors.partial`，flush/close 后原子 rename；
- 输出标准 Comfy file descriptor/metadata，绝不把 bytes 放进 prompt history JSON；
- 输出必须落在选中 ComfyUI 的 output root 下，拒绝 `..` 和任意绝对路径。

Load node：

- 只读取受管 `h3-native-av` 相对路径；
- 验证 safetensors header、固定 keys、dtype/shape 与 manifest/hash；
- 重建 H3 joint NestedTensor；
- 禁止 pickle。

Electron 的 artifact service 改为 `commitProducedFile(...)`：解析 Comfy output descriptor，安全解析 output root 内路径，流式计算 bytes/SHA，验证 header/shape，最后原子写 manifest。不要再以 `Uint8Array` 为正式写入 API。

### 5.2 两个 API workflow，不用单个超长 prompt 冒充 checkpoint

新增：

```text
workflows/minimax_h3_fl2va_first_pass_av_api.json
workflows/minimax_h3_fl2va_second_sample_api.json
```

Ref2VA 在 FL2VA 真实通过后增加对应两个 workflow，不能同时大范围猜测。

首遍 workflow：

```text
现有 FL2VA conditioning/model/sampler（Create 1440p 的内部首遍固定 720p）
  → joint clean latent
  ├→ H3 AV decode → MP4 720p
  └→ LocalVideoStudioH3SaveJointAV → artifact A
```

第二遍 workflow：

```text
Load artifact A
  → split video/audio
  → learned 3D resize video latent
  → video AddNoise（视频 sigma）
  → audio AddNoise（音频 sigma）
  → shift audio sigmas（不能照搬视频 sigma）
  → concat joint AV
  → upscale/rebuild conditioning for target geometry
  → rebuild guider with Base/no-LoRA model
  → SamplerCustomAdvanced second sampling
  ├→ decode → MP4 1440p（Create）或 1080p/1440p（History Upscale）
  └→ SaveJointAV → artifact B
```

必须以 pin 后节点真实 schema 构建，不从 display name 推断 input。尤其不能用 stock `AddNoise` 直接处理 joint NestedTensor，也不能让 audio 使用未经验证的视频 sigma；这正是社区正确二采 workflow 专门处理的边界。

两阶段拆开有意为之：第二遍 OOM/失败时，第一遍 MP4 与 committed artifact A 仍可展示和重试；应用重启后也无需重跑首遍。

### 5.3 输出采集

扩展 Comfy completion parser，但媒体和 artifact 分开收集：

- MP4 继续进入现有 `ComfyOutputService`/History media 路径；
- serializer node 的 file descriptor 进入专用 artifact collector；
- collector 只解析本次 prompt id、预期 node id、预期 output root；
- Electron 验证并提交 manifest 后才生成 `h3ContinuationData`；
- queue-history 只能持久化已 committed artifact；
- 节点写了文件但 manifest 未提交时为 orphan/partial，由有界清理器处理，不显示为 available。

## 7. capability 与状态机

统一状态至少为：

```text
not-installed
installed-on-disk
static-valid
runtime-schema-valid
runtime-smoke-passed
runtime-ready
```

Create 1080/1440 与 History H3 Upscale 只认各自 capability 的 `runtime-ready`，但依赖集合不同：

- selected ComfyUI core 和 data directory 明确；
- H3 base 模型/VAE/encoder 已扫描；
- Create 1080p 要求原生 1080p workflow、AV serializer 和对应资源 profile 通过真实 smoke；**不要求 learned upscaler**；
- Create 1440p 与 History H3 Upscale 额外要求 learned upscaler weight bytes/SHA、split/noise/sigma 节点和 second-sampling workflow；
- 当前 capability 所需 custom nodes 位于选中安装并通过 Python import；
- `/object_info` 含精确 class types 和兼容 schema；
- API workflow 静态 validator 通过；
- 当前节点/core/revision 组合有至少一次本机真实 smoke evidence。

推荐 reason codes：

```text
node-not-installed
node-revision-mismatch
node-schema-mismatch
node-license-blocked
weight-missing
weight-hash-mismatch
workflow-static-invalid
runtime-not-running
runtime-smoke-required
artifact-not-produced
artifact-missing
artifact-hash-mismatch
artifact-shape-incompatible
conditioning-missing
conditioning-source-changed
target-not-larger
profile-vram-unsupported
```

Renderer 只负责翻译 reason code；不能自己重新推导可用性。

## 8. 测试与验收矩阵

### 8.1 自动测试

- artifact：path traversal、manifest-last、partial、hash/bytes、固定 keys、shape/dtype、lineage、shared refs；
- migration：无 artifact 旧记录、Luna 当前 schema、Extend 新 schema、输出根变化；
- installer：pinned checkout、requirements failure、timeout、backup/restore、selected Python、restart/recheck；
- workflow：class ids、required inputs、目标 geometry、video/audio sigma 分支、serializer output；
- queue：immutable snapshot、stage checkpoint、retry、cancel、restart、单 GPU stage；
- History：真实 completion metadata、status card、源/派生版本、delete；
- UI：普通 H3、SeedVR2、disabled reason、ready enable、focus、keyboard、viewport。

每个共享状态/IPC/queue 工作包完成后运行：

```powershell
npm.cmd run verify
```

### 8.2 真实运行 Gate

必须保存每次 evidence：Comfy core revision、custom-node commits、Python/Torch/CUDA/GPU、模型/权重 hash、workflow revision、参数、耗时、峰值 VRAM/RAM、输出 metadata、artifact hash、日志路径。

最低矩阵：

| 场景 | 结果要求 |
| --- | --- |
| 现有 FL2VA 480p direct | 行为不变 |
| FL2VA 480p/720p first-pass AV | MP4 + audio + artifact A + History 可见 |
| Create 原生 1080p direct | 单阶段 1080p MP4 + final artifact；不经过 upscaler |
| 720p artifact → 1080p | 质量默认候选；MP4 + artifact B，A/V 正常 |
| 720p artifact → 1440p | 质量默认候选；MP4 + artifact B，A/V 正常 |
| 480p artifact → 1080p | 低显存/快速候选；MP4 + artifact B，A/V 正常 |
| 480p artifact → 1440p | 低显存/快速候选；MP4 + artifact B，A/V 正常 |
| Create 1440p composite | 两个 History versions，stage 可恢复 |
| History 480p/720p → H3 1440p | 新 version，不覆盖源 |
| 缺节点/缺权重/坏 hash | GPU 前拒绝，原因准确 |
| stage2 OOM/cancel/restart | A 保留，可只重试 stage2 |
| SeedVR2 Upscale | 无回归 |
| Extend 消费 final AV | 同一 artifact schema/load node 可用 |

完成声明必须分级：

- `static validation passed`：类型、测试、workflow JSON；
- `runtime schema validated`：`/object_info` 通过；
- `runtime smoke passed`：一条真实最小运行成功；
- `product integrated`：真实 Create/History/Upscale/恢复/UI 全链路成功。

禁止把前三级中的任一级写成第四级。

## 9. Luna Max 执行规则

1. 开始每个 WP 前重新读取当前目标文件和 `git status`；磁盘版本优先，不能回放旧 patch；
2. `src/types.ts`、`electron/store.ts`、queue executor、History migration/delete 与 Extend agent 串行交接，不能并发拥有；
3. 每次只完成一个纵切，提交前列出改动文件、preserve list、自动测试、真实测试和未验证项；
4. 没有真实 AV 文件就不要改 History UI；没有手动 second-pass 成功就不要改 queue；没有 queue 成功就不要开放 1080/1440；
5. 不修改页面布局，只在现有控件中增加最终必要选项和状态；
6. 遇到许可证、node schema、GPU OOM 或 conditioning 不可重建，停止在当前 Gate，保留可工作的前一层并报告证据；
7. 不因计划写了文件名就假定文件存在；先用 `rg --files` 与 `/object_info` 验证；
8. 最终 review 必须检查 `git diff --name-status` 和完整 diff，尤其防止意外删除旧 workflow、fallback、History migration 和 Extend 字段。

## 10. 本轮恢复的 Definition of Done

只有同时满足以下条件，才可以向用户说“原生 1080p/1440p 与带 AV 的 H3 Upscale 已完成”：

- 纯 ComfyUI 路线无需 X-MinimaxH3 core；
- 全新/已有 ComfyUI 环境都能通过应用安装或明确引导安装全部依赖；
- Create 1080p 与 1440p 均真实运行成功；
- 480p 与 720p History 的 H3 Upscale 到 1440p 均真实成功，并基于对比证据冻结默认 profile；
- Create 1080p 的单个 final MP4/AV，以及 Create 1440p 的 720p 首遍与 1440p 最终 MP4/两份 AV，均在同一 output 根下并在详情页可见；
- final AV 能被 Extend 的共用 loader/schema 消费；
- stage2 失败/重启能从 artifact A 恢复；
- 普通 H3、SeedVR2、History 删除/迁移和 Settings 离线扫描无回归；
- `npm.cmd run verify` 通过，并附真实运行 evidence。

在此之前，正确描述是“恢复计划/静态基础/某 Gate 已通过”，不能再写“Product integrated”。
