# DLSS5 双 Provider 平行接入计划

> 日期：2026-09-04
>
> 状态：Active / implementation-ready
>
> 执行对象：Luna Max 及后续实现 Agent
>
> 实施目标：在不移除任何现有 Upscale 路径的前提下，平行接入 HECer 与 AetherScale 两套实验性 DLSS5 Provider；AetherScale 先争取形成可运行路径，HECer 保留完整产品合同但明确受上游 DLL 阻塞。
>
> 前置调查：[2026.9.3-dlss5-upscale-integration-plan.md](../investigation/2026.9.3-dlss5-upscale-integration-plan.md)

## 1. 决策摘要

本计划取代旧调查文档中的“只实现 HECer `dlss5-sr`”执行路线，但不删除旧文档，也不删除已经完成的 HECer 类型、catalog、安装事务、Depth Anything、队列和 UI 工作。旧文档继续作为 HECer 调研证据；从本计划开始，产品中的 DLSS5 必须是一个 Provider family，而不是一个含糊的单一实现。

两条平行路径如下：

| 产品 Provider | 上游 | 首期用途 | 当前状态 | 是否依赖 Depth Anything |
| --- | --- | --- | --- | --- |
| `dlss5-sr`（已有持久 ID，永久指向 HECer） | `HECer/ComfyUI-DLSS5` v0.2.2 | 独立 DLSS Super Resolution 2×/3×/4× | **Blocked upstream**：公开 VapourKit 资产缺少 `vsdlsssr.dll` | 是，保留独立 guide 卡 |
| `aetherscale-dlss5`（新增） | `vizart-vj/ComfyUI-AetherScale` v0.5.5 | carrier 模式的 DLSS5 Neural Rendering + 1×/1.5×/1.724×/2×/3× 输出 | **Candidate**：静态可安装，仍需真实 RTX smoke | 否；使用 AetherScale motion packet |

产品行为必须满足：

1. 两个 Provider 同时存在、独立安装、独立扫描、独立入队、独立失败。
2. HECer 不可用不能阻止 AetherScale 安装或执行。
3. AetherScale 不可用不能改变已排队 HECer 任务的语义。
4. 任一 Provider 失败都不得静默切换到另一 Provider、Real-ESRGAN、FlashVSR、SeedVR2 或 H3 native upscale。
5. `dlss5-sr` 这个已进入当前工作树的 ID 不得改成 AetherScale；旧 queue/history 一律按 HECer 解释。
6. 两套实现都保持“实验性”，直到对应的真实 GPU smoke 和同条件 benchmark 完成。
7. Frame Generation 不在本计划内。AetherScale 也没有提供可作为产品插帧使用的 FG 节点。

### 1.1 为什么不能用 AetherScale DLL 修好 HECer

HECer 缺失的是 VapourSynth wrapper `vsdlsssr.dll`。它不是 NVIDIA 的 `nvngx_dlss.dll`，也不是 AetherScale 下载的、虽然扩展名为 `.dll` 但实际作为 D3D12 worker 进程启动的 `nvngx.dll`。

禁止以下“修复”：

- 将 `nvngx_dlss.dll` 重命名为 `vsdlsssr.dll`；
- 将 AetherScale/Merserk 的 `nvngx.dll` 复制进 HECer runtime；
- 将 `vsdlssnr.dll` 当作 `vsdlsssr.dll`；
- 因文件名相似而跨 Provider 共享 wrapper 或 runtime；
- 从未固定来源、聊天附件、DLL 聚合站或游戏目录自动抓取 HECer wrapper；
- 跳过 wrapper schema、自检或 SHA-256 后把 HECer 标记为 ready。

两套路径调用协议完全不同：HECer 通过 VapourSynth wrapper；AetherScale carrier 通过自定义 stdin/stdout 二进制协议驱动 Merserk worker。跨用 DLL 只会把可解释的“上游缺失”变成难以诊断的 ABI 错误或原生崩溃。

## 2. 已确认的上游事实

### 2.1 HECer 阻塞证据

固定基线：

```text
repository: https://github.com/HECer/ComfyUI-DLSS5
release: v0.2.2
commit: 310524aa283602832cbdd827ce4e35565c859a7e
```

HECer SR 声明要求：

```text
VapourSynth-capable python.exe
vsdlsssr.dll
nvngx_dlss.dll
```

当前证据：

- HECer 唯一公开 issue `#1 vsdlsssr.dll and vsdlssnr.dll` 报告指定包没有复制这些 wrapper，且 `vsdlsssr.dll` 根本不存在。
- 旧计划已经下载并递归审计 HECer 指向的 VapourKit nightly；SHA-256 匹配，但归档中没有 `vsdlsssr.dll` 或可组成 HECer SR 的完整 bundle。
- HECer 文档承认 `nvngx_dlssnr.dll` 没有已识别的通用官方分发。
- `vsdlsssr.dll` 是项目工作所必需的 wrapper；只有 NVIDIA runtime DLL 不能使 HECer SR 工作。

因此当前产品状态必须是：

```text
node installed/can register != SR runtime ready
basic NR artifacts found != guided NR validated
SR wrapper missing => HECer SR unavailable
```

HECer 卡片可以安装节点、扫描文件、展示 Depth guide 和已取得的实验 NR 证据，但不得循环执行一个已知不可能补齐 SR wrapper 的“修复”任务。除非未来找到可公开固定、可校验、接口匹配的 `vsdlsssr.dll` 发布资产，否则 HECer SR 的恢复动作应显示“等待上游 runtime”，而不是可点击的无效重试。

### 2.2 AetherScale 固定基线

```text
repository: https://github.com/vizart-vj/ComfyUI-AetherScale
release: v0.5.5
commit: b825f783f31b7cce45e0be02ba87c8ed5b20f9d5
release asset: ComfyUI-AetherScale-v0.5.5.zip
release asset bytes: 433107
release asset SHA-256: c73971d99e806d80bc4eccf879837272d863d7a7f66277baaa3ab6791501008c
Python: >=3.10; reuse selected ComfyUI Python
requirements.txt: intentionally empty
```

AetherScale 提供两种不同技术，不得混为一谈：

1. `AetherScaleSuperResolution` 是 NVIDIA VFX `VideoSuperRes`，不是 DLSS Super Resolution；支持 1–4× 或 exact/long-edge 输出。
2. `AetherScaleNeuralRendering` 的默认 `backend=carrier` 才是本计划的第二套 DLSS5 Provider；它是普通 DLSS carrier + motion guide + RenoDX Neural Rendering 注入，不是 HECer 的独立 DLSS SR wrapper。

首期 `aetherscale-dlss5` 只调用：

```text
AetherScaleMotionAnalysis
  -> AetherScaleNeuralRendering backend=carrier
```

不得调用：

- `backend=legacy_direct`；它会再引入 `lisitskyaa/ComfyUI-DLSS5-NR` 与 RankFTW runtime，扩大故障面；
- `AetherScaleRuntime` 的自动下载 action 作为生产安装流程；
- `AetherScaleSuperResolution` 并把它标成 DLSS5；
- `source_profile=bicubic` 并将结果标成 NVIDIA VFX 成功。

### 2.3 AetherScale carrier runtime

AetherScale v0.5.5 固定下载：

```text
source: Merserk/dlss5-visual-enhancer
release: v1.0
asset: DLSS.5.Visual.Enhancer.v1.0.zip
archive SHA-256: 5d57c2f2d2a1c247c0249e7a1024eabb5384ee9111820a4a478be6ce893b767d
archive size: approximately 468 MB; exact bytes must enter catalog after WP0 audit
```

只允许从归档中提取以下六个成员到 AetherScale 固定位置：

```text
<AetherScale node>/runtime/carrier/runtime/
  nvngx.dll
  dxgi.dll
  renodx-dlss5.addon64
  nvngx_dlss.dll
  nvngx_dlssnr.dll
  ReShade.ini
```

`nvngx.dll` 在此处被 AetherScale 当作进程执行，不是普通 load-only DLL。安装时不得执行它；只有用户明确提交 AetherScale 任务后，执行器才允许启动它。

禁止自动改用 Merserk v3.0 或浮动 `latest`。其他项目已经使用更新 Merserk 版本，但 AetherScale v0.5.5 的协议和固定 SHA 以 v1.0 为准；升级必须作为新的 runtime bundle 完整审计和 smoke，不能只替换压缩包 URL。

### 2.4 AetherScale 输出模式

上游固定枚举及内部参数：

| upstream mode | 几何倍率 | perfQuality | 产品首期状态 |
| --- | ---: | ---: | --- |
| `native_1x` | 1.0 | 5 | 保留为同分辨率增强实验项，不叫 Upscale |
| `quality_1_5x` | 1.5 | 2 | 可选，经过几何测试后开放 |
| `balanced_1_724x` | 1.724 | 1 | Advanced；默认隐藏，避免用户误解成目标分辨率 |
| `performance_2x` | 2.0 | 0 | 首期主路径 |
| `ultra_performance_3x` | 3.0 | 3 | 首期次路径，需 8K 边界检查 |

AetherScale carrier 没有 4×。AetherScale 的 4×能力属于 NVIDIA VFX node，不属于 DLSS5 carrier。UI 和 History 必须保留这一区别。

输出宽高按上游规则四舍五入到偶数，且 carrier 拒绝越过 7680×4320 边界。队列快照必须存实际 `targetWidth/targetOutputHeight`，不能只存浮点倍率后在执行时重算。

## 3. 产品能力模型

### 3.1 不使用一个布尔 `dlss5Ready`

环境状态必须按 Provider 和 capability 分离：

```ts
type CapabilityLevel =
  | "missing"
  | "installed"
  | "statically-recognizable"
  | "registered"
  | "runtime-ready"
  | "smoke-passed"
  | "blocked-upstream"
  | "incompatible";

interface Dlss5ProviderStatus {
  provider: "hecer" | "aetherscale-carrier";
  nodeId: string;
  nodeRevision: string;
  runtimeBundleId: string;
  level: CapabilityLevel;
  availableForQueue: boolean;
  installed: boolean;
  schemaValidated: boolean;
  runtimeValidated: boolean;
  smokeValidated: boolean;
  missingFiles: string[];
  incompatibleFiles: string[];
  blockedReason?: string;
  evidence?: Record<string, string | number | boolean>;
}
```

当前 `EnvironmentScanResult.dlss5Runtime` 已代表 HECer，不可直接改写成 AetherScale。采用兼容扩展：

```ts
interface EnvironmentScanResult {
  /** Legacy/current HECer evidence; preserve while old code and persisted scans exist. */
  dlss5Runtime?: Dlss5RuntimeStatus;
  dlss5Providers?: Partial<Record<"hecer" | "aetherscale-carrier", Dlss5ProviderStatus>>;
  aetherScaleRuntime?: AetherScaleRuntimeStatus;
}
```

normalize 时把旧 `dlss5Runtime` 投影成 `dlss5Providers.hecer`，不要做破坏性持久化迁移。新扫描写新字段；旧版本仍可读取已有字段。

### 3.2 Queue snapshot

当前 `Dlss5UpscaleOptions` 实际是 HECer-specific，必须停止继续扩张。保留它作为旧 HECer task 的兼容类型，并新增明确区分的 AetherScale snapshot：

```ts
type AetherScaleCarrierMode =
  | "native_1x"
  | "quality_1_5x"
  | "balanced_1_724x"
  | "performance_2x"
  | "ultra_performance_3x";

interface AetherScaleDlss5Options {
  provider: "aetherscale-carrier";
  operation: "neural-upscale" | "neural-enhance";
  mode: AetherScaleCarrierMode;
  styleProfile: "faithful" | "enhanced";
  motionProfile: "torch-lk-compact-v1";
  nodeRevision: string;
  runtimeBundleId: string;
  targetWidth: number;
  targetHeight: number;
  warmupFrames: number;
  sceneCutThreshold: number;
}
```

推荐持久字段：

```ts
interface UpscaleQueueTask {
  modelId: string;
  /** Existing HECer-only snapshot. */
  dlss5?: Dlss5UpscaleOptions;
  /** New AetherScale-only snapshot. */
  aetherScale?: AetherScaleDlss5Options;
}
```

规则：

- `modelId="dlss5-sr"` 只能带 `dlss5`，永远解释为 HECer。
- `modelId="aetherscale-dlss5"` 只能带 `aetherScale`。
- 两个 options 不能同时存在。
- 旧 `dlss5-sr` queue/history 无需改 ID，也不得自动转换为 AetherScale。
- `targetScale` 只能继续服务整数 HECer；AetherScale 使用枚举 `mode` 和冻结后的实际宽高，避免 `1.724` 浮点比较漂移。
- waiting task 编辑后重建不可变 snapshot；running/completed task 不被 UI 默认值或 runtime 更新影响。
- runtime bundle 更新后，旧 waiting task 显示“使用旧 bundle/需要重新排队”，不得静默改写。

### 3.3 Catalog IDs

新增：

```text
custom node id: comfyui-aetherscale
directory: ComfyUI-AetherScale
repository: https://github.com/vizart-vj/ComfyUI-AetherScale.git
revision: b825f783f31b7cce45e0be02ba87c8ed5b20f9d5

upscale provider id: aetherscale-dlss5
adapter id: aetherscale-dlss5
workflow id: builtin:upscale/aetherscale-dlss5
runtime bundle id: aetherscale-carrier-v1-node-0.5.5
```

保留：

```text
comfyui-dlss5 -> HECer node
dlss5-sr -> HECer provider
depth-anything-v2 -> HECer guide model only
```

不要创建一个名为 `dlss5` 的共享 custom-node card；用户要求两套仓库平行实现，所以 Settings 中应有两张仓库卡：`ComfyUI DLSS5 · HECer` 与 `AetherScale`。每张卡内部只展示自己的 runtime 分项。

## 4. Settings 与安装流程

### 4.1 HECer 卡片

卡片状态行：

| 子项 | 检查 | 当前预期 |
| --- | --- | --- |
| Node | git origin + fixed revision + `/object_info` | 可安装/可注册 |
| Python requirements | 使用 selected ComfyUI Python | 可安装 |
| HECer SR wrapper | `vsdlsssr.dll` + schema/self-test | `blocked-upstream` |
| NVIDIA SR runtime | `nvngx_dlss.dll` | 单独存在也不能使 SR ready |
| Basic NR | 当前固定 private VapourSynth runtime | 实验；不得冒充 SR |
| Depth guide | 独立 `depth-anything-v2` card | 不并入 HECer 仓库卡 |

交互：

- Node 未安装：显示“安装节点”。
- Node 已安装、SR wrapper 缺失：显示“已安装 · SR 等待上游 runtime”，不显示无效的“修复 SR”主按钮。
- 如果未来 catalog 增加经过审计的 SR wrapper bundle，再恢复“安装/修复 runtime”。
- “查看证据”应列出缺失文件、固定 revision、issue 链接和最后扫描时间。
- HECer 卡状态不参与 AetherScale 卡的按钮 enable/disable。

### 4.2 AetherScale 卡片

用户只看到一张 AetherScale 仓库卡和一个主要安装动作。内部阶段：

```text
1. install/update fixed AetherScale node
2. use selected ComfyUI Python for probes
3. install/verify optional NVIDIA VFX private vendor runtime
4. download/verify/extract carrier runtime
5. restart app-managed ComfyUI at most once
6. refresh /object_info and runtime evidence
```

一张卡不等于一个模糊 ready 状态。内部至少显示：

| 子项 | Ready 条件 | 对 carrier Provider 的影响 |
| --- | --- | --- |
| Node | fixed revision present | Required |
| Carrier | 六个 exact files + archive/file hashes + manifest | Required |
| Motion | `AetherScaleMotionAnalysis` schema | Required |
| Neural node | `AetherScaleNeuralRendering` carrier schema | Required |
| NVIDIA VFX | private `nvvfx` import + `VideoSuperRes` symbol | Optional，不阻塞 carrier |
| Runtime smoke | minimal carrier task | 发布前 Required |

安装必须使用现有 dependency queue、stage/output feedback、timeout、日志保留、backup/replace、restart/recheck 机制。禁止通过 ComfyUI workflow 排队 `AetherScaleRuntime(action=install_or_update)` 来完成安装，因为那会把下载隐藏在 GPU 队列中，缺少应用级事务与失败回滚。

### 4.3 Python 策略

AetherScale 不安装第二套 Python：

- 所有 Python probe 和可选 `nvidia-vfx` 安装都使用当前 selected ComfyUI Python；
- `nvidia-vfx==0.1.0.1` 仍安装到 `<AetherScale node>/vendor`，避免污染 ComfyUI 全局 site-packages；
- 不允许调用系统 `python`、`py` launcher 或用户 PATH 上的 Python；
- carrier 路径本身不要求 `nvidia-vfx` ready，两个 capability 独立报告。

HECer 当前为满足 VapourSynth wrapper 而组装的 private Python 只属于 HECer runtime implementation detail，不显示为可选择 Python，也不得给 AetherScale 复用。

### 4.4 AetherScale 安装事务

```text
validate selected local ComfyUI/data root
  -> reject local installation for remote endpoint
  -> install/checkout fixed node revision first
  -> stage under a unique sibling/temp directory
  -> download Merserk v1.0 archive as .partial
  -> enforce HTTPS + repository/release allowlist after redirects
  -> enforce expected bytes and archive SHA-256
  -> reject absolute paths, drive paths, .., symlink/reparse members
  -> extract only six basename+expected-directory allowlisted files
  -> verify non-empty, PE x64 where applicable, and per-file SHA-256
  -> write upstream-compatible carrier_manifest.json
  -> write app-owned install-manifest.json with owned file list
  -> move previous app-owned runtime to timestamped backup
  -> atomically promote staging; restore backup on failure
  -> remove .partial/staging in finally
  -> restart/recheck once after the entire install batch
```

必须在 WP0 下载一次真实 archive，把 exact archive bytes、最终 redirect host、六个成员的 archive path、bytes 和 SHA-256 固定到 catalog fixture。不要只依赖上游 Python 文件中的常量。

卸载规则：

- App-managed AetherScale node：按现有 custom-node 卸载规则删除 catalog directory；先停止 carrier worker。
- 手工安装 AetherScale：不得由 App 删除整个目录；只允许删除 app manifest 明确拥有的 runtime 文件，并在 UI 解释。
- 发现未知文件时保留它们并报告 partial cleanup。
- Windows 文件占用时不得循环强删；提示停止 ComfyUI/worker，执行一次受控重试。

### 4.5 NVIDIA VFX 子能力供应链

`requirements.txt` 为空，但上游第一次用 VFX 时会同步执行无 timeout 的：

```text
<selected ComfyUI Python> -m pip install nvidia-vfx==0.1.0.1 \
  --target <AetherScale>/vendor --no-deps
```

坑点：公开 PyPI 包是很小的 bootstrap/stub，实际 wheel 可能来自 `pypi.nvidia.com`。只锁 `0.1.0.1` 不等于锁定最终 wheel 内容。

执行要求：

1. WP0 捕获实际 index/redirect、wheel filename、bytes、SHA-256、Python ABI 和平台 tag。
2. 下载 host 加入精确 allowlist，不允许任意 index。
3. 使用 bounded subprocess、live output 和 cancellation。
4. 安装到 staging vendor 后执行 `import nvvfx`、version、`VideoSuperRes` symbol probe，再替换现有 vendor。
5. 无法固定最终 wheel 时只将 VFX 子能力标记 unavailable；不得阻塞 AetherScale carrier。
6. 生产 workflow 一律传 `auto_bootstrap=false`，防止任务执行时再次联网。

## 5. AetherScale 生产 workflow

### 5.1 Graph

在确认 v0.5.5 `/object_info` 后建立最小 API graph：

```text
VHS_LoadVideo
  ├─ frames -> AetherScaleMotionAnalysis
  │              └─ motion -> AetherScaleNeuralRendering
  ├─ frames ----------------> AetherScaleNeuralRendering
  ├─ audio ------------------------------------------┐
  └─ fps --------------------------------------------┤
                                                     v
                                  existing VHS_VideoCombine
```

初始固定值：

```text
AetherScaleMotionAnalysis:
  engine = torch_lk
  quality = balanced
  scene_cut_threshold = 0.22
  reset_on_scene_cut = true
  output_device = cpu_safe
  motion_mode = compact_flow
  analysis_long_edge = 512
  storage_precision = float16
  preview_frames = 1

AetherScaleNeuralRendering:
  backend = carrier
  motion_source = connected_motion
  auto_bootstrap = false
  output_device = cpu_safe
  output_precision = float16
  output_storage = auto
  clean_cache = true
  carrier_gpu = windows_high_performance
```

下面这些值不能直接按上游默认写死为产品默认，必须在 WP5 smoke 中选择并固化：

```text
style
strength
preset
auto_mask
carrier_warmup_frames (upstream default is 120; may dominate short clips)
carrier_scene_cut_threshold
```

首轮 PoC 同时测试 `warmup_frames=0/2/8/120`。最终产品默认必须以首帧稳定性与总耗时证据为依据。没有证据前 UI 不暴露“更快/更高质量”文案。

### 5.2 为什么用 connected motion

`motion_source=auto` 会初始化 OpenCV DIS fallback，即使连接 motion packet，也会给 ComfyUI Python 增加 OpenCV 要求。首期固定 `connected_motion` 并连接 `AetherScaleMotionAnalysis(engine=torch_lk)`，避免为了 carrier 再安装或替换 OpenCV wheel。

必须验证：

- packet width/height 与 input 完全一致；
- direction 是 current-to-previous；
- frame 0 reset；
- scene cut reset 生效；
- packet 每个后续 frame 都有 flow；
- 生产 graph 不出现 silent zero-motion。

如果上游遇到无效 packet 会静默使用 zero motion，产品 adapter 应在构图前通过固定 schema和运行结果 stats 阻止这种情况。无法从 stats 证明实际 guide 被使用时，保持 experimental 并提交上游改进；不要伪造验证结果。

### 5.3 音频、FPS 和输出

AetherScale 节点只接收/返回 ComfyUI `IMAGE` tensor，没有视频文件 loader、音频输入或 mux。产品必须复用现有 VHS load/combine：

- 原音频直接从 loader 连接到 combine；
- output FPS 使用 source FPS；
- 不改变 frame count；
- VFR 输入按当前产品既有规范处理，不能声称保留原始 VFR；
- 成功前使用 ffprobe 验证尺寸、帧数、FPS、时长和音频；
- 缺音频的源允许输出无音频，不能把它当作 mux 失败。

### 5.4 静态 validator

提交前验证：

- AetherScale stats 输出 index 不得误接到 IMAGE input。

## 6. 需要显式处理的坑点

### 6.1 名称与产品承诺

- AetherScale Super Resolution = NVIDIA VFX VSR，不是 DLSS SR。
- AetherScale carrier = DLSS + RenoDX Neural Rendering carrier，属于实验集成。
- HECer = VapourSynth wrapper 路径，目前 SR wrapper 缺失。
- UI 不显示“官方 DLSS5”“NVIDIA 官方节点”或“最快”，直到取得相同条件实测。

### 6.2 隐式网络和首次任务卡死

AetherScale 上游默认允许 node 在执行时 pip install 或下载约 468 MB runtime。生产 graph 必须 `auto_bootstrap=false`。所有网络只发生在用户点击 Settings 安装/修复之后，并进入现有安装队列。

### 6.3 原生进程伪装为 DLL

carrier worker 文件名为 `nvngx.dll`，但由 `subprocess.Popen([nvngx.dll, "--video"])` 执行。这可能触发 Windows Defender/SmartScreen、企业策略或文件 quarantine。

要求：

- 安装页明确说明将启动第三方原生 worker；
- 显示 source、release、archive hash 和本地路径；
- 扫描 Windows Zone.Identifier、文件存在/大小/PE 架构，能取得时记录 Authenticode 状态但不把“未签名”自动等同恶意；
- worker 启动失败与 NGX 初始化失败使用不同错误码；
- 不自动添加 Defender 排除项，不要求用户关闭杀毒软件；
- quarantine 后允许从固定 hash 的 archive 重新修复。

### 6.4 持久注册表修改

AetherScale carrier 默认写入：

```text
HKCU\Software\Microsoft\DirectX\UserGpuPreferences
value name = absolute worker path
value data = GpuPreference=2;
```

这是持久宿主状态，不得当作无副作用实现细节。

生产 Gate：

1. 安装/首次启用前在 UI 披露高性能 GPU 路由。
2. 记录同名旧值是否存在及原值；不要覆盖后丢失。
3. App-owned worker 卸载时仅恢复本应用修改过的值；如果用户/其他程序已再次修改则保留并警告。
4. 最好向上游提交 `system_default/no_registry` 选项；在没有此选项前，记录这是实验限制。
5. 不允许通过注册表声称选择了某一块具体 NVIDIA GPU；上游只设置 Windows High Performance，不能保证精确 adapter。

### 6.5 多 GPU 路由

Motion Analysis 使用 PyTorch `cuda_device`，carrier worker 由 D3D12/Windows preference 选卡，两者可能不是同一 adapter。首期：

- 只支持自动 High Performance；
- UI 不显示虚假的精确 GPU selector；
- History 同时记录 Torch device、`nvidia-smi` 列表和 expected high-performance GPU；
- 多 GPU 机器必须有单独 smoke；
- 无法确认 worker 实际 adapter 时写 `unknown`，不要用 expected 代替 actual。

### 6.6 取消与进度

v0.5.5 carrier/VFX frame loop 没有清晰的 ComfyUI per-frame interruption/progress hook。`/interrupt` 可能要等 node 返回才生效。

要求：

- 在 120+ frame smoke 中实测 cancel latency；
- 先发 ComfyUI interrupt，等待 bounded grace period；
- 对 app-managed local ComfyUI，可在确认 task-owned worker PID/command/path 后终止 worker，并按现有 runtime recovery 重启；
- remote endpoint 不允许本机 kill，显示“已请求取消，等待远端节点返回”；
- 不按文件名全局杀死 `nvngx.dll`，必须验证 PID、父进程、命令行和 runtime path；
- worker 残留、ComfyUI restart 和 cancel timeout 分开记录；
- 在没有上游进度事件时只显示阶段/不确定进度，不伪造逐帧百分比。

如果无法做到可靠取消，Provider 仍可停在 hidden/diagnostic，不进入普通用户入口。

### 6.7 长视频并非真正 file-to-file streaming

AetherScale 按帧处理并可把输出放在 mmap/pagefile，但 ComfyUI/VHS 仍可能持有完整 input 和 output IMAGE batch；下游 combine 也可能物化 tensor。不能把这一实现宣传为任意长度视频流式处理。

首期限制：

- 在有证据前限制 clip 时长/帧数或按估算 commit memory 阻止高风险任务；
- `clean_cache=true` 使用 anonymous/pagefile backing，仍消耗 Windows commit/pagefile；
- `clean_cache=false` 可能留下大型 `.mmap` 文件，生产 workflow 禁止；
- 测试 pagefile disabled、pagefile space insufficient、磁盘 temp 不足、下游 materialization；
- 成功/失败/取消后检查 stale mmap/temp；
- 多小时 file-to-file 路径作为 Future，不在本计划 DoD。

### 6.8 CPU staging、8-bit carrier 和性能承诺

carrier 每帧执行 Torch tensor -> CPU float -> RGBA8 -> worker -> CPU RGBA8 -> output tensor。不是 CUDA zero-copy，并会把 neural output 限制在 8-bit carrier 数据路径。潜在影响：

- 高分辨率 PCIe/CPU copy 成为瓶颈；
- 10-bit/HDR source 丢失精度或出现 banding；
- `float16` output storage 不会恢复 worker 已量化掉的信息；
- worker 比现有模型快的假设必须用 wall-clock、CPU、GPU、VRAM/RAM/pagefile 一起测。

首发输入输出按 SDR 8-bit 产品路径声明。HDR10/PQ、10/12-bit、alpha correctness 单独验证后再开放。

### 6.9 warmup 成本

上游 `carrier_warmup_frames` 默认 120。短视频可能出现 warmup 成本大于实际帧数的情况。必须记录 setup、warmup、per-frame 和 encode 阶段耗时；没有验证前不采用 120 作为产品默认。

### 6.10 运行时更新与 node 更新

AetherScale runtime/vendor 存在 node 目录中。更新或重装 node 可能删除它们。

- 顺序固定为 node update -> runtime rehydrate -> one restart -> rescan；
- 扫描 manifest 与实际文件 hash；
- node revision 改变时旧 runtime 不自动复用，除非 compatibility table 明确允许；
- 任务执行期间禁止 node/runtime 替换；
- 旧 bundle 保留到没有 queued/running task 引用后再按 manifest 清理。

### 6.11 原生崩溃边界

Aether carrier worker 在子进程中，原生崩溃应被隔离并转成任务失败；Aether VFX 在 ComfyUI 进程内加载 native wheel，风险不同。两者的 runtime health、错误文案和恢复不能共用一个 generic “DLSS failed”。

### 6.12 上游成熟度

AetherScale v0.5.5 是非常新的仓库和 release。版本号增长不能替代生态成熟度。固定 commit 后必须保留 schema fixture、archive fixture、真实 smoke evidence；每次升级重新做 artifact audit，而不是跟随 main。

## 11. Stop conditions

遇到以下情况停止对应 Provider，不要绕过；另一个 Provider 可继续：

### HECer only

- 仍找不到固定、可验证、compatible 的 `vsdlsssr.dll`；
- 唯一办法是重命名/混用其他项目 DLL；
- wrapper schema 与 HECer bridge 不匹配；
- 需要执行未知来源二进制才可确认文件内容。

### AetherScale only

- Merserk asset/hash/六文件成员与 pin 不符；
- worker 启动需要关闭系统安全功能或全局杀毒排除；
- carrier 写 registry 无法记录/恢复且产品不能接受；
- `/interrupt` 和受控 worker cleanup 都无法停止任务；
- runtime 只能依靠执行时自动下载；
- node schema 没有 carrier/connected motion/auto_bootstrap controls；
- 输出尺寸、帧数、音频或 scene-cut 不符合合同；
- native worker 频繁 crash 或残留 process；
- 真实结果没有 feature-18/carrier 证据，只得到普通 resize。

### Shared

- 目标 hotspot 在实施中被用户/其他 Agent 改动且无法无损合并；
- 需要删除未知目录、用户 DLL、模型、缓存或外部 runtime；
- 需要修改 public/persisted contract 却没有兼容 normalization；
- 测试只能通过关闭 validation 或自动 fallback；
- 不能区分 static validation 和 real smoke。

## 12. Definition of Done

双 Provider 接入完成必须同时满足：

1. Settings 存在 HECer 与 AetherScale 两张独立 repo card。
2. HECer 节点/Depth/已有代码保留，SR 准确显示 blocked-upstream，不诱导用户重复安装。
3. AetherScale node/carrier 通过 app-native one-click install，执行时不联网。
4. AetherScale provider 使用 pinned carrier graph，不使用 VFX 冒充 DLSS，不使用 legacy direct。
5. Queue snapshot、编辑、重启、执行、取消和 History 都区分 provider/revision/runtime bundle。
6. 两 Provider 无共享 mutable runtime、无 cross-fallback、无 status coupling。
7. AetherScale 至少一个含音频短视频真实 smoke 成功，输出媒体事实验证通过。
8. cancel/worker cleanup/registry ownership 有真实或明确受限证据。
9. 所有现有 Upscale providers 回归通过，`npm.cmd run verify` 通过。
10. README、CHANGELOG 和 minor version 同步；Git 中没有 runtime/model/media/temp。

如果 WP1–WP6 已完成但没有真实 GPU smoke，状态只能写：

```text
双 Provider 产品实现完成；HECer 等待上游 wrapper；AetherScale 等待真实 runtime validation。
```

不能写“DLSS5 已可用”。

## 13. Luna Max 每阶段回报格式

Luna 不要一次性声称全部完成。每结束一个 WP，回报：

```text
阶段：WP0–WP8
Provider：shared / HECer / AetherScale
完成：实际落地行为
修改文件：git diff --name-status 中属于本阶段的文件
已有工作复用：保留了哪些当前 HECer/Depth 代码
保留项：确认哪些现有 provider/流程没有改变
测试：命令 + pass/fail 数量
静态证据：revision/schema/archive/hash/graph
真实运行：未运行 / 环境与结果
HECer 状态：blocked-upstream / 其他
AetherScale 状态：catalogued/detected/runtime-ready/smoke-passed
剩余风险：具体、可执行
下一阶段：准备修改的文件和入口
```

最终交付前：

1. `git status --short`；
2. `git diff --name-status`；
3. 完整审查 diff，尤其是 `src/types.ts`、queue、runtime installer 和 history；
4. 搜索并确认没有 DLL、ZIP、7z、model、mmap、log、absolute machine path；
5. 核对 package/lock versions；
6. 区分 automated、static、runtime、smoke、benchmark 五类证据；
7. 列出未测 GPU/driver/multi-GPU/pagefile/remote 组合。
