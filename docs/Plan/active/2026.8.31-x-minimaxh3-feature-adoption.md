## 0. 计划定位

本计划用于记录对 `PullMyBoots/X-MinimaxH3` 的持续学习、功能取舍、技术验证和产品接入进度。

目标不是复制 X-MinimaxH3，而是在 Local Video Studio 现有 Electron + ComfyUI 产品边界内，选择性吸收以下能力：

1. H3 原生 latent 二次采样到 1440p；
2. 模型、服务族、显存档位和运行时证据组成的能力矩阵；
3. clean joint AV latent artifact、checkpoint 和可恢复任务语义；
4. ComfyUI 工作流、Native provider 和未来 Web API 的统一应用边界；
5. 更可靠的模型 manifest、依赖诊断、资源监控和失败说明。

本计划不改变现有 H3 FL2VA、Ref2VA、Motion Context、SeedVR2、LoRA、队列、历史或 ComfyUI 运行路径的默认行为。所有新能力都必须以 additive 方式接入，并保留已有 fallback，直到用户明确要求替换。

## 2. 已确认的技术判断

### 2.1 “原生 2K”在本计划中的定义

上游所谓的原生 2K，实际主要是 H3 二次采样到 1440p，16:9 时为 2560×1440。它不是把完成的 MP4 交给普通视频放大器，而是：

```text
低/中分辨率 H3 首次生成
    → clean joint video/audio latent
    → latent 空间或学习型 3D 放大
    → H3 低噪声二次采样
    → 1440p 视频与音频
```

因此必须区分：

- `H3 native second sampling`：H3 latent 级二次采样；
- `SeedVR2/其他 post-upscale`：视频解码后的后处理放大；
- `Native Masked AV Extend`：以已有 AV 数据为基础的续写/掩码扩展。

本仓库已经有 1440p/4K SeedVR2 后处理，但这不等于已有 H3 原生二次采样。

### 2.2 Native Engine 不是算法前置条件

ComfyUI + H3 专用节点可以表达原生二次采样：

```text
H3 sampler pass 1
    → LTXVSeparateAVLatent
        → video latent upscale
        → audio latent 按 H3 audio sigma 处理
    → H3 conditioning upscale
    → LTXVConcatAVLatent
    → H3 AddNoise / DisableNoise
    → sampler pass 2
```

但是，ComfyUI 默认 H3 节点通常不足以直接完成这条路径。需要额外验证：

- H3 NestedTensor 的 video/audio 分离和重组；
- H3 CONST flow 的正确 noise scaling；
- video/audio 不同 sigma shift；
- reference/keyframe conditioning 的同步放大；
- 32 像素对齐和 DiT patch 几何；
- 长时长或高分辨率下的 temporal/spatial split。

Native Engine 的主要价值是执行控制：显存规划、模型驻留、offload、kernel、队列和独立部署。它不是“只有它才能生成原生 2K”。

### 2.3 PyTorch 版本不做全局升级

上游的 `PyTorch 2.13.0+cu130` 属于专用 Native H3 环境：它同时固定 Python、CUDA runtime/toolkit、MiniMax-H3、LightX2V、SageAttention、SpargeAttn、comfy-kitchen 和编译扩展。

本仓库此前针对现有 Windows + ComfyUI + custom nodes + H3 workflow 的实测基线固定在 PyTorch 2.10。上游 2.13 成功不能证明现有 ComfyUI 路径可以直接升级。

本计划的默认策略是：

- 现有 ComfyUI H3 继续使用已验证的 PyTorch 2.10；
- ComfyUI 原生二采样 POC 先在 2.10 环境验证；
- 如果必须使用 Native Engine，再为 Native provider 建立隔离 runtime；
- 禁止用一次全局 Torch 升级同时影响 H3、提示词、其他视频和图像工作流。

### 2.4 前后端分离采用“应用边界优先”

上游提供 Web console、REST API、durable queue 和 NativeBackendManager，但它的应用编排仍然不应原样搬进本项目。

本仓库先完成模块化单体：

```text
Electron shell / future Web adapter
          ↓
ApplicationRuntime
          ↓
Queue / History / State / GPU arbitration
          ↓
H3 provider / ComfyUI provider / optional Native provider
```

HTTP、SSE、WebSocket、LAN 和 Browser UI 仍然遵循 Headless 重构计划的 M5 Future Gate；在此之前不实现未被消费的 API 抽象。

## 4. 目标产品行为

### 4.1 二次采样入口

History 完成的视频卡片增加条件式动作：

> H3 原生二采样 · 1440p

动作只在以下条件满足时显示为可用：

- 任务是兼容的 H3 FL2VA/Ref2VA 生成；
- 存在完整且兼容的 Native AV artifact；
- H3 latent upscaler 和二次采样节点/provider 已通过 runtime gate；
- 当前 GPU/profile 接受目标尺寸、时长和帧数；
- 没有其他重 GPU 阶段运行。

二次采样必须创建新的 child queue task 和新的 History version：

```text
原始 H3 720p
    ├── SeedVR2 1440p
    └── H3 原生二采样 1440p
```

原始任务、prompt、参考素材、seed、视频和音频必须保持可访问。二采样失败不能静默改走 SeedVR2、重新生成或降低分辨率。

### 4.2 建议的用户选项

首版只暴露最小且可解释的选项：

- 目标：1080p / 1440p；
- 二采样 steps：由已验证 profile 提供，不让用户输入任意值；
- 强度：保持 / 标准 / 增强 / 强重绘；
- temporal window：默认自动，只有通过资源验证后才允许手动调整；
- 预计显存、预计耗时和不支持原因。

首版不暴露上游全部 scheduler、per-layer attention budget 或未经本机验证的 8/16GB launcher。

## 5. 领域与运行时契约

以下是拟议方向，接入时必须由当前 `src/types.ts` owner 根据现有 schema 和迁移策略最终冻结。

### 5.1 Capability profile

建议新增纯领域 profile，避免在 renderer、queue 和 environment 中分别写限制：

```text
H3CapabilityProfile
  provider: comfyui | native-sidecar
  serviceFamily: fl2va | ref2va
  modelVariant: base | lora
  resourceProfile: local-validated | 24gb-int8 | 16gb-int8 | 8gb-w4a8
  firstGenerationLimits
  secondSamplingLimits
  referenceLimits
  requiredModels
  requiredNodes
  requiredRuntime
  evidenceState
```

profile 是 capability 的来源，不是运行时结果。运行时仍需重新执行 `/object_info`、`/system_stats`、文件检查和真实 smoke。

### 5.2 Native AV artifact

优先复用 `docs/H3_NATIVE_MASKED_AV_LONG_VIDEO_PLAN.md` 的 `NativeAvContinuationArtifact` 方向：

- 二进制保存在 task-owned 目录，state 只保存安全引用；
- manifest 保存 schema version、producer、model/VAE、workflow/core fingerprint、geometry、frames、fps、shape、dtype、大小和 hash；
- 使用原子提交、partial cleanup、路径越界检查和 header/shape 校验；
- History、迁移、删除、重启恢复和旧记录读取必须保持一致；
- Motion Context latent 不得冒充 Native AV artifact；
- artifact 保存失败时允许普通视频 generation 成功，但必须记录 `save-failed` 和原因，并禁用二采样入口。

### 5.3 Provider contract

二次采样执行不应直接写入 `electron/main.ts`。建议由 Application/queue 依赖窄接口：

```text
H3SecondSamplingProvider
  preflight(request)
  execute(request, progress, cancellation)
  inspectOutput(result)
  releaseRuntime()
```

首个实现是 `ComfyUiH3SecondSamplingProvider`。只有 AD-08 被批准后，才增加 `NativeH3SidecarProvider`。

两个 provider 必须共享：

- 同一个 queue task snapshot；
- 同一个 GPU arbitration；
- 同一个 output/history metadata contract；
- 同一个 cancellation 和 cleanup 语义；
- 同一个 capability/evidence model。

### 6.1 AD-01 调查交付物

必须记录：

- 上游每个相关 node 的输入、输出、版本和许可证；
- 当前 ComfyUI `/object_info` 是否有对应类型；
- H3 AV latent 的真实类型、shape、NestedTensor 结构和保存方式；
- 目标 upscaler 权重来源、大小、hash、目录和许可证；
- Torch、CUDA、driver、Sage/Triton/kernels 的精确组合；
- ComfyUI 2.10 基线是否能承载纯 Python 节点；
- 哪些功能属于简单 workflow，哪些依赖 Native Engine 的专用 memory planner。

AD-01 不修改生产 workflow、依赖安装状态或用户模型目录。

本轮 AD-01 详细报告：
[2026.8.31-ad01-x-minimaxh3-runtime-comfyui-investigation.md](../investigation/2026.8.31-ad01-x-minimaxh3-runtime-comfyui-investigation.md)。

报告已完成上游源码、manifest、模型 hash、许可证、ComfyUI 节点行为、Native/connector 边界、Torch/CUDA/kernel 组合和本地缺口的静态比对；本机 /object_info 和真实二次采样仍属于后续 AD-03/AD-07 的 runtime gate。

### 6.2 AD-03 ComfyUI POC 顺序

按以下顺序缩小变量：

1. FL2VA Base、无 LoRA、无 Spectrum、无 Sage，使用当前 PyTorch 2.10；
2. 720p、短时长、低 steps，先完成同一 workflow 内的 pass 1 → pass 2；
3. 加入 H3 专用 latent/conditioning upscale；
4. 加入正确的 H3 AddNoise 和 audio sigma；
5. 验证 H3 VAE 输出、音频和 32 像素目标几何；
6. 再验证 720p → 1440p；
7. 最后加入 Ref2VA、参考素材、LoRA、时空切片和长时长。

POC 先证明算法和节点边界，不直接开放正式 UI。

### 6.3 AD-08 sidecar 触发条件

只有出现以下明确证据之一，才启动 Native Engine sidecar 评估：

- ComfyUI workflow 能正确二次采样，但目标分辨率/时长在本机显存中不可行；
- ComfyUI 时空切分后的速度或接缝质量不可接受；
- ComfyUI 无法稳定保存或恢复 clean joint AV latent；
- 要求复现上游 24GB/15 秒/1440p 资源合同；
- 需要独立 REST/Web 服务，并且 M5 已完成。

sidecar 必须使用独立 runtime、独立模型/依赖目录和明确的生命周期；不能在 Electron 主进程内嵌上游单体，也不能让 ComfyUI 和 Native Engine 同时加载两份 H3。

## 7. 模块化重构期间的并行与串行规则

### 7.1 可以并行的安全工作

- AD-01 的外部源码、许可证、schema 和 workflow 只读调查；
- 新增 `src/core` 独立 capability/profile 纯函数，不触碰现有 queue/main 热点；
- 独立实验 workflow 的静态构造和 JSON/schema 测试；
- 测试夹具、验证记录模板和 runtime evidence 文档；
- 对现有 H3 artifact 设计做字段审查，不立即改 persisted state。

### 7.2 必须等待或指定单一 owner 的工作

以下热点不能由模块化重构和本计划同时修改：

- `src/types.ts` 和 persisted schema/migration；
- `electron/main.ts`；
- `electron/store.ts`；
- `electron/queue-*.ts`；
- `src/core/workflow.ts`；
- History/Queue shared renderer shell；
- preload IPC contract。

如果这些文件在工作包开始后出现新 diff，必须先重新读取当前文件和完整 diff，重新声明 preserve list，再继续。不能把旧会话准备的 patch 直接重放。

### 7.3 与模块化里程碑的关系

```text
M0–M1：AD-01 调查、证据整理、独立纯函数设计
M2：   AD-02 capability profile；等待 queue/history/application ports 稳定
M3：   AD-04 artifact service；接入 ApplicationRuntime composition
M4：   AD-05/AD-06 provider、queue、History 和 renderer seam
M5：   AD-07 产品级资源验证；AD-09 才允许进入新的 API 计划
```

本计划不要求所有 AD 工作包等到 M5 才开始，但每个接入点都必须依赖对应的边界稳定状态。模块化重构优先级更高，不能为了提前显示“原生 2K”而破坏现有队列、历史或生命周期不变量。

## 8. 验证门槛

### 8.1 静态门

- capability profile 无重复限制来源；
- workflow 是 API-format，节点输入来自实际 `/object_info` 或权威 workflow；
- 模型、节点、Python、Torch/CUDA 和 provider 状态分开显示；
- `npm.cmd run verify` 通过；
- 不新增未使用的 HTTP、daemon、browser 或全局 runtime 抽象。

### 8.2 ComfyUI 真实 POC 门

必须记录：

- ComfyUI core version/commit；
- 选定 Python、PyTorch、torchaudio、CUDA runtime/driver；
- H3 模型、VAE、upscaler 权重及 hash；
- workflow revision；
- 分辨率、宽高、帧数、FPS、时长、steps、seed；
- video/audio latent shape、artifact 大小和 hash；
- VRAM/RAM 峰值、阶段耗时和最终封装耗时；
- 视频尺寸、帧数、音频采样率、PTS 和播放结果；
- 是否使用 fallback。

### 8.3 产品集成门

只有同时满足以下条件，才可把能力标为 `product integrated`：

1. 720p/1080p → 1440p 的真实二次采样成功；
2. 输出尺寸准确且满足 32 像素对齐；
3. 视频和音频完整，A/V 时间基准无明显漂移；
4. source task 不被修改，child task 快照不可变；
5. artifact 可保存、加载、校验、迁移和删除；
6. cancel、restart、failure、history delete 行为一致；
7. ComfyUI、Queue、History、Settings 和 Create 的相邻回归通过；
8. 无静默换后端、降分辨率或改用普通 post-upscale；
9. 在目标 Windows GPU 环境完成真实 smoke，而不是只通过 import/JSON 测试。

### 8.4 性能和质量表述

没有同条件 A/B 数据时，不写“更快”“更省显存”“质量更好”。必须区分：

- static validation passed；
- runtime schema validated；
- real minimal generation passed；
- product integrated；
- performance/quality comparison completed。

上游在 RTX 4090 SM89、Linux/WSL2、PyTorch 2.13+cu130 上的结果，不能替代本机 Windows + ComfyUI + PyTorch 2.10 的证据。

## 9. 失败策略与停止条件

以下情况必须 fail closed：

- artifact 缺失、损坏、shape/producer/core 不兼容；
- upscaler 权重或关键节点只存在于未审查来源；
- `/object_info` 与 workflow 输入不一致；
- 必须依赖隐式 Motion Context 或 MP4 round-trip 才能完成；
- 需要把 Torch 2.13 全局覆盖到现有 ComfyUI 才能执行；
- 只能通过静默降分辨率、换模型或换后端避免失败；
- 运行中无法证明 GPU 阶段和模型生命周期仍符合单卡策略；
- 许可证不允许当前使用或再分发。

POC 失败不等于项目失败。应记录失败层级：节点/schema、latent 几何、noise/sigma、VAE/A/V、显存、运行时 ABI、工作流或应用接入。只有在 ComfyUI 路线的失败证据完整后，才进入 AD-08 Native sidecar 决策。

## 10. 不纳入本计划首版的内容

- 替换现有 ComfyUI H3 首次生成、Motion Context 或 SeedVR2 路径；
- 全局升级 PyTorch、CUDA、SageAttention 或 Triton；
- 未经本机验证的 8GB/16GB/24GB 发布档位；
- 公网/LAN Web 服务、多租户、计费和远程任务管理；
- 直接复制 X-MinimaxH3 的 native engine、`h3serve` 单体服务或受限代码；
- 把普通视频放大标记成 H3 原生二采样；
- 将“模型文件存在”当作“runtime-ready”；
- 在同一条新任务中混合 H3 二采样、Native Masked AV Extend、Motion Context 和 SeedVR2，直到每条路径拥有独立的 artifact 和验证证据。

## 11. 进度同步格式

每个工作包完成一次阶段动作后，更新本文件对应行，并附以下最小记录：

```text
状态：Investigation / Static validated / Runtime validated / Product integrated
日期：YYYY-MM-DD
证据：测试文件、workflow、core commit、runtime 记录或输出路径
实际验证：做了什么；没有做什么
受影响文件：新增、修改、禁止修改
保留行为：旧路径、fallback、迁移和 UI 行为
阻塞：明确错误层级和下一步
```

阶段状态不能只写“已完成”。如果只完成静态 workflow、类型或节点 import，必须明确写成 `Static validated`。

## 12. 完成定义

本计划的最终完成不是“把上游所有功能搬过来”，而是：

1. 现有 H3/ComfyUI 路径保持稳定；
2. capability、artifact、provider、queue 和 history 有单一且向后兼容的契约；
3. ComfyUI-only 原生二采样已被实际验证，或 Native sidecar 的引入决定有真实证据支撑；
4. 原生 1440p 的限制、显存、依赖和失败原因对用户可解释；
5. 模块化重构与新功能没有形成第二套 state、queue、GPU 或命令路径；
6. REST/Web 前端若实施，必须在 M5 后通过独立计划复用 ApplicationRuntime；
7. 所有“支持”“可用”“原生 2K”声明都有本机真实运行证据。
