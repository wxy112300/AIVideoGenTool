# Local Video Studio 模块化架构重构计划

状态：Active，WP-00 至 WP-R02 已完成（working tree，待统一提交）；下一项为 WP-R03
日期：2026-08-31
当前目标：先把 Electron 应用从两个巨型入口拆成健康、清晰、可测试且更流畅的模块化单体
未来方向：Headless、API、Browser 与 LAN 仅保留为后续选项，不属于当前完成条件

## 1. 结论与范围校正

当前最重要的问题不是“还没有 Web API”，而是应用层职责没有形成稳定边界：

- `electron/main.ts` 约 4,000 行，同时负责启动、IPC、业务编排、状态写入、队列、历史、环境、进程和窗口生命周期；
- `src/main.ts` 约 3,100 行，同时负责 renderer 启动、页面装配、事件订阅和跨页面协调；
- IPC handler、业务命令和基础设施副作用混在一起，改动常跨越多个高风险区域；
- 状态、GPU 队列、ComfyUI 进程和窗口退出的所有权主要靠调用顺序维持，而不是由模块边界表达；
- 现有代码已有不少可复用的 `src/core/` 和 service，不需要重写，只需重新组织依赖和责任。

本计划采用以下顺序：

1. 固定当前行为和回归基线；
2. 在 Electron 内部抽出清晰的 application services、ports 和 adapters；
3. 把 `electron/main.ts` 收缩为 composition root 与桌面壳；
4. 把 `src/main.ts` 收缩为 renderer composition root，并按页面/能力注入依赖；
5. 同时修复已有测量证据支持的高影响启动、History 和整页渲染瓶颈；
6. 通过“架构健康与性能 Gate”后结束本轮重构；
7. 只有用户再次批准，才为 Headless/API/Browser/LAN 单独写下一份实施计划。

这不是微服务改造，也不要求当前代码真正前后端分离。目标是得到边界清楚的模块化单体，使未来是否分离成为低风险选择。

## 2. 当前架构评价

### 2.1 做得好的部分

- `src/core/` 已承载较多无 Electron global 的领域逻辑；
- queue executor、ComfyUI client、runtime/environment service 已有可复用模块；
- `JsonStore` 已处理默认值、迁移和串行持久化；
- preload 是 renderer 与特权能力之间的明确入口；
- 测试已覆盖队列、历史、设置、工作流和 runtime 的大量关键行为。

所以当前架构不是推倒重来型问题，主要问题集中在装配层和应用编排层过度聚合。

### 2.2 最大问题

`electron/main.ts` 已成为事实上的 God Object：业务规则、I/O、副作用和 Electron 生命周期在同一文件中互相引用。它导致：

- 一项功能修改需要理解整条应用启动和运行链路；
- 单元测试难以直接覆盖完整业务命令；
- IPC 看起来像接口，handler 内部却仍直接操作 store、worker 和进程；
- 新入口只能复制或调用 Electron 代码，不能复用稳定应用服务。

### 2.3 最脆弱的地方

按风险排序：

1. **队列与生命周期编排**：唯一 worker、恢复、取消、GPU 串行、prompt lease、ComfyUI owned process 相互影响；
2. **状态写入与副作用混合**：store mutation、事件、文件和进程操作常在同一命令中发生；
3. **历史完成与删除**：task terminal state、history/output identity、文件删除和 cover 必须一致；
4. **设置保存**：验证、迁移、持久化和运行时刷新是一条高风险事务链；
5. **两个巨型入口**：`electron/main.ts` 与 `src/main.ts` 都承担过多横向协调。

这些问题都可借本轮重构改善，不需要先引入 HTTP、数据库或新框架。

## 3. 本轮目标架构

```text
Electron desktop shell
  ├─ window / dialog / native file / protocol adapters
  ├─ IPC registration adapters
  └─ composition root
              │
              ▼
Application layer
  ├─ queue
  ├─ history
  ├─ draft + settings
  ├─ prompt
  ├─ environment + runtime admin
  ├─ media + image documents
  └─ lifecycle coordinator
              │
       ports  │  events
              ▼
Domain (src/core) + infrastructure
  ├─ workflow/task/state rules
  ├─ JsonStore repository adapter
  ├─ ComfyUI/runtime/environment integrations
  └─ filesystem/process adapters

Renderer composition root
  ├─ page controllers
  ├─ narrow client capabilities
  └─ Electron preload client adapter
```

### 3.1 依赖规则

- `src/core/**` 不依赖 Electron、renderer 或具体 transport；
- application service 不注册 IPC、不访问 `BrowserWindow`，也不读取 Electron global；
- Electron adapter 只做 payload 转换、主机能力适配和 service 调用；
- 一个业务命令只有一条 application path，禁止 IPC 内另写一套规则；
- `JsonStore` 仍是唯一持久化实现，本轮不迁移数据库；
- 一个进程内仍只有一个 state writer、queue worker 和 owned ComfyUI manager；
- renderer 页面依赖最窄 client interface，不直接依赖宽泛的全局 `AppApi`；
- 不为未来架构提前建立没有 consumer 的空接口、空目录或抽象层。

### 3.2 本轮完成后的状态

- Electron 行为、IPC contract、persisted state、工作流和 UX 不变；
- `electron/main.ts` 主要只剩启动、装配、窗口与 adapter 注册；
- `src/main.ts` 主要只剩 renderer 装配和启动；
- queue/history/settings 等可在不创建 Electron window 的条件下直接测试；
- 文件、进程、store 和 event 的 owner 在构造参数与模块名中可见；
- Agent 可只阅读一个工作包及相关模块完成局部修改，不必理解整个应用。
- 启动关键路径区分“首屏必需”和“可延后”工作，用户不再因无关扫描或修复等待空白窗口；
- 高频状态更新只刷新相关区域，History 屏外媒体不再制造无界 I/O、解码或布局工作。

不使用行数作为硬性 KPI。若只是把大文件切成多个仍互相读写全局状态的小文件，视为未完成。

### 3.3 性能与流畅度原则

- 先测量后优化；每个性能 WP 必须保存同 fixture、同窗口、同操作的前后数据；
- “首屏可交互”与“后台初始化完成”是不同里程碑，后者不得无理由阻塞前者；
- 动画只用于状态连续性，不用于掩盖 Long Task；主线程不流畅时不得先增加动画；
- 优先删除无用工作：避免整页 DOM 重建、重复 controller mount、屏外媒体解码和布局读写交错；
- 只优化基线确认的高影响路径，不顺便建立通用 scheduler、虚拟 DOM 或新 UI framework；
- 性能改动保持相同数据、IPC、交互和可访问性语义，并可按 WP 整包回退；
- 耗时确实来自磁盘、ComfyUI 或模型时，用非阻塞执行、阶段反馈和取消语义改善体验，不伪造“已完成”。

## 4. 强制 Preserve List

除非用户另行批准，全部工作包必须保持：

- 已排队任务是不可变执行快照；
- single heavy GPU stage 与 single queue worker；
- queue recovery、pause boundary、cancel cleanup 和 task/history 一致性；
- draft ownership、连续输入、focus、selection、undo/redo 和 mode switch；
- settings 单一保存路径、迁移 gate 和 dirty-close 语义；
- history cover、版本、播放、定位、删除和旧路径恢复；
- offline environment scan 与 remote ComfyUI connection-only；
- local ComfyUI startup takeover、正常退出和 forced cleanup；
- 现有 IPC channel、payload、return、error 文案和事件顺序；
- 旧 state、queue、history、media path 与 workflow compatibility。
- 每个 phase 结束时现有 Electron 入口均可启动并完成 Create -> Queue -> History -> Settings smoke；
- 性能优化不能破坏 focus、scroll、playback、可访问树、错误恢复或后台任务清理。

## 5. 执行规则

### 5.1 工作包状态与开始动作

状态只能是 `Pending`、`Ready`、`In Progress`、`Blocked`、`Review`、`Done`。只有 coordinator 填完 execution card 后才能改为 `Ready`。

执行 Agent 开始前必须：

1. 记录 `git status --short` 和 base SHA；
2. 阅读本 Plan、适用 contract、目标实现和相关测试；
3. 用 `rg` 重新生成调用/import inventory；
4. 写出该包 preserve list；
5. 确认目标 hotspot 没有其他 writer；
6. 重新读取目标文件后再编辑；
7. 目标文件若在执行期间变化，停止并交回 coordinator。

### 5.3 全局停止条件

- 需要改白名单之外的 hotspot；
- 需要修改 persisted/public contract，但该包没有 migration 决策；
- 必须复制 store、validation、worker、runtime state 或 media resolver 才能继续；
- baseline 已失败且无法区分原有失败与回归；
- destructive 文件/进程操作的 owner 或目标不明确；
- 单包扩展到两个以上 application area；
- 当前实现与 contract 冲突，需要产品决定。

### 5.4 并发规则

- `electron/main.ts`、`src/main.ts`、`src/types.ts`、`electron/store.ts`、版本文件始终单 owner；
- application extraction 默认串行；只读 inventory 和不相交 tests 可以并行；
- 共享 worktree 同时只允许一个 production-code writer；
- 执行 Agent 不 bump 版本，checkpoint release 由 coordinator 统一处理。

### 5.5 每包可运行 Gate

每个 production WP 合并前必须满足：

- 当前 Electron entry 仍是唯一入口，不需要下一个 WP 才能启动；
- compatibility adapter 在同一包内接通，禁止提交“先拆断、后续再接回”的中间状态；
- focused tests、typecheck 和该包要求的 verify 通过；
- 至少完成受影响页面/流程的原始行为 smoke；
- 若性能数值变差或无法稳定测量，回退该优化部分，不用动画掩盖；
- 未完成代码不得靠长期 feature flag、双写或第二套 command path 留在主线。

## 6. 里程碑与 Gate

```text
M0  行为、启动与交互性能 baseline
 |
M1  paths / events / repository ports
 |
M2  queue / history / settings / prompt / environment / media services
 |
M3  lifecycle + embedded application composition
 |
M4  renderer 入口与页面依赖拆分 + 已证实热点优化
 |
M5  Architecture Health & Performance Gate —— 本轮计划完成
 |
 └── Future Gate：另行批准 Headless/API/Browser/LAN 计划
```

### M0 Gate

- WP-00 已提交；
- IPC、event、startup、renderer global 使用有 inventory/characterization；
- cold/warm startup、first usable render、页面切换和高频状态更新有可复现基线；
- History 500 条 fixture、Long Task、媒体并发和滚动恢复沿用专门性能计划的基线；
- 生产重构前 `npm.cmd run verify` baseline 通过；
- coordinator 记录 dirty files 和 hotspot owner。

### M3 Gate：Backend Application Boundary

- application modules 不 import Electron；
- IPC adapter 不直接修改 store、启动 worker 或结束进程；
- 业务事件通过唯一 event bus/bridge；
- queue、history、settings、prompt、environment 和 media service 可直接测试；
- Electron Create -> Queue -> History -> Settings smoke 行为等价；
- 每个 backend WP 的启动与常见命令指标不得出现无法解释的明显回退；
- `npm.cmd run verify` 通过。

### M4 Gate：Renderer Composition Boundary

- 页面模块不直接依赖 `window.studio` 或完整 `AppApi`；
- preload contract 和 Electron 行为不变；
- renderer event subscription 均能清理；
- typing/focus、queue drag、history playback、settings save/close 回归通过；
- 高频事件不会无条件重建无关页面；History 媒体与布局达到专门性能计划的 Gate；
- development 与 packaged Electron smoke 无白屏。

### M5 Gate：架构健康与性能

- 两个 main 文件只承担装配和平台入口责任；
- 每个 application area 有唯一 owner、唯一 command path 和 direct tests；
- state、event、filesystem、process、queue ownership 有明确依赖方向；
- 没有为 Headless/HTTP 创建未使用代码；
- 启动、History 和 renderer 热点均有同基线前后证据；后台初始化有明确状态和失败路径；
- 完整 verify、适用 manual matrix 和 diff review 通过；
- 更新 `ARCHITECTURE_CONTRACT.md` 与 `AGENT_START_HERE.md` 的当前事实。

M5 通过即代表本计划完成，不要求 daemon、HTTP server 或 browser。性能验收以基线和可复现实验为准，不接受只写“感觉更流畅”。
