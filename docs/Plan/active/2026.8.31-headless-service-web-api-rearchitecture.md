## 1. 目标与结论

目标是让 Local Video Studio 的业务后端可以在没有 Electron 窗口、没有 GUI 的情况下独立启动并持续工作，同时让以下客户端复用同一套能力：

- 当前 Electron 桌面 GUI；
- 本机浏览器页面；
- 局域网内经过授权的浏览器或程序；
- CLI、Agent、OpenAPI client，以及后续可选的 MCP adapter。

可行性结论：**技术可行性高，但属于中高风险的跨模块重构，不适合一次性替换。**

现有业务逻辑并不需要整体重写。`src/core/` 已经承载大量无 Electron 全局的领域逻辑，队列执行器、ComfyUI 客户端、环境扫描和本地进程服务也大多是 Node 模块。真正的主要障碍是 `electron/main.ts` 同时承担 composition root、应用服务、事件分发、进程生命周期、路径解析和 IPC handler，renderer 则通过一个过宽的 `AppApi` 把业务能力、文件传输和桌面原生能力混在一起。

推荐采用绞杀式迁移：

1. 先建立行为基线和可回滚测试；
2. 逐个拆出 paths、events、queue、history、draft、settings、prompt、environment 和 media application services；
3. 保持现有 Electron IPC 行为可用，再用这些已解耦服务组装 embedded `StudioRuntime`；
4. 收口 renderer 对 `window.studio` 的依赖，但仍然只走现有 IPC；
5. 通过 transport-neutral Gate 后，再让同一个 runtime 由独立 headless entrypoint 启动；
6. 增加受控的 HTTP API、事件流、上传和媒体服务；
7. 最后启用浏览器、Agent，并在完成安全加固后开放 LAN。

不推荐直接把 preload 中的 IPC 方法一比一映射成 HTTP endpoint。当前接口包含任意本地路径、依赖安装、ComfyUI 强制停止、历史删除和主机 shell 操作；直接暴露会同时固化错误边界并扩大安全风险。

## 2. 当前架构调查

### 2.1 当前系统边界

架构契约将当前产品定义为 Electron desktop client：应用拥有创建体验、队列语义、历史元数据、环境发现和由应用启动的进程，ComfyUI 拥有实际模型执行。当前链路是：

```text
Creation draft
  -> immutable queue snapshot
  -> model/workflow adapter
  -> ComfyUI API
  -> generated media
  -> history/project record
```

证据：

- `docs/ARCHITECTURE_CONTRACT.md:5-18` 定义系统边界和 privileged operation 的 preload/IPC 约束。
- `docs/ARCHITECTURE_CONTRACT.md:20-35` 已把领域逻辑、持久化、运行时集成和 Electron 生命周期区分开。
- `docs/AGENT_START_HERE.md:34-40` 明确 queue execution 与 ComfyUI submission 目前仍留在 `electron/main.ts` 和 Electron services。

### 2.2 已经适合 headless 的部分

- `src/core/` 是确定性领域层，包含 queue mutation、task factory、workflow adapter、model policy 和兼容规则；这部分应保持共享，不需要为了 HTTP 复制。
- `electron/store.ts:420-426` 的 `JsonStore` 由外部传入文件名；`electron/store.ts:426-557` 在加载时完成旧状态迁移；`electron/store.ts:812-842` 通过进程内 write chain 和临时文件替换串行持久化。首个 headless 版本可继续使用它。
- `electron/queue-executor.ts:43-66` 已使用明确 dependencies，且不 import Electron，是抽取 `QueueService` 的最佳切入点。
- `electron/queue-worker.ts:12-82` 的 worker/controller 本体只依赖 Promise 和 AbortController；应把它与同文件的 IPC registration 分离。
- `electron/services/comfy-ui.ts` 使用标准 fetch/WebSocket 与 ComfyUI 通信，可以由普通 Node 进程运行。
- `electron/services/comfy-runtime-state.ts` 已经是可订阅的 runtime state controller，可以直接接入 transport-neutral event bus。
- `electron/services/comfy-runtime-service.ts` 已显式注入 discovery、launch、filesystem 等依赖，适合继续作为 backend infrastructure service。
- renderer 大部分是普通 DOM/TypeScript。`src/renderer/contracts.ts:42-54` 和 `src/renderer/bootstrap.ts:13-30` 已经以参数形式接收 `AppApi`，为 client adapter 留出了迁移缝隙。

### 2.3 当前主要耦合

#### Electron 启动即后端启动

`electron/main.ts:4005-4025` 在 `app.whenReady()` 内依次创建 store、恢复状态、注册 media protocol、注册 IPC、创建窗口并接管本地 ComfyUI。没有 Electron app ready 就没有完整业务后端。

#### 巨型 composition root

`electron/main.ts` 当前约 4,000 行。全局对象同时包含 `BrowserWindow`、store、queue worker、prompt worker/lease、迁移状态和 shutdown 状态（`electron/main.ts:266-303`）。任务更新、运行时准备、历史操作、prompt orchestration 和 settings side effects 也仍由该文件实现。

#### 事件直接绑定单个窗口

- state broadcast：`electron/main.ts:820-837`；
- prompt/runtime broadcast：`electron/main.ts:840-877`；
- task preview wiring：`electron/main.ts:2141-2149`。

这套机制只支持一个 `BrowserWindow`，没有事件序号、断线恢复或多个 client subscriber。

#### command 与 IPC registration 混合

- `electron/queue-ipc.ts:20-36` 的 mutation service 接口直接要求 `IpcMain`；
- `electron/queue-worker.ts:84-104` 将 worker control 和 IPC handler 放在同一模块；
- `electron/queue-enqueue.ts:1,74-81` 同时依赖 `IpcMain`、Electron `nativeImage`、文件系统和业务校验。

应该先抽 command/query service，再让 Electron IPC 和 HTTP adapter 各自注册 handler。

#### 路径来自 Electron app API

state、cover、mask、markup、migration scratch 和 clipboard 文件多处使用 `app.getPath("userData")`；例如 `electron/main.ts:211-219` 和 `electron/main.ts:4013`。独立 service 需要显式的 `StudioPaths`，不能 import Electron 才知道数据目录。

#### Renderer API 过宽

`src/types.ts:1354-1468` 的 `AppApi` 同时包含：

- state query 与业务 command；
- queue/runtime/progress subscription；
- 文件选择和本地绝对路径；
- media read/cache；
- Windows shell/player/clipboard；
- dependency install、repair 和 process control；
- window close handshake。

`electron/preload.cts:22-203` 将它逐项映射为 IPC，`electron/preload.cts:206` 暴露为 `window.studio`。`src/main.ts` 仍有大量直接 `window.studio` 调用，因此浏览器 bundle 目前没有可替换的 transport root。

#### Electron-only media 与文件语义

- renderer 使用 `studio-media://` 定位本地历史和队列媒体；协议由 `electron/main.ts` 注册，并已有 MIME、Range 和错误处理。
- Electron picker 和 `webUtils.getPathForFile` 返回 backend 主机上的绝对路径。
- Explorer、open directory、system player、Windows file clipboard 都描述 backend 主机动作。

远端浏览器无法把自己的 `File` 变成服务器绝对路径，也不应看见任意服务器路径。浏览器模式必须使用 upload/import 后得到的 opaque asset ID，并通过鉴权 media URL 读取内容。

## 3. 关键架构决定

### 3.1 后端是唯一状态与运行时所有者

任何时刻只有一个 `StudioRuntime` 可以写 state file、持有 queue worker、管理 prompt lease、调度 GPU 和管理 app-owned ComfyUI。

Electron、浏览器、CLI、Agent 全部是 client。禁止 Electron 主进程与独立 daemon 同时打开同一个 `studio-state.json`。现有 `JsonStore` 只有进程内 write chain，没有跨进程事务或锁，因此“双写者”不是可接受的过渡方案。

首版应实现 data-directory instance lock，并让第二个 backend 实例明确失败或连接已有实例。不要靠“通常只会开一个”维持一致性。

### 3.2 Electron 先保持兼容，最终变成薄壳

迁移期保留两种 host mode：

- `embedded`：Electron 启动一个与自身同生命周期的 `StudioRuntime`，IPC adapter 调用 application services；对用户行为保持不变。
- `standalone`：独立 headless process 拥有 `StudioRuntime`，Electron 和浏览器通过 loopback API 连接它。

只有 standalone mode 验证成熟后，才决定桌面默认是否切换为外部 daemon。GUI 关闭是否停止 backend 必须由 host mode 明确定义，不能由 socket 断开隐式决定：

- embedded mode：沿用当前关应用会清理 app-owned runtime 的契约；
- standalone mode：关 Electron 或浏览器标签不停止队列和 backend；仅明确的 admin shutdown command 或 OS service stop 才关闭。

### 3.3 API 调用 application services，不调用 GUI

Agent/API 自动化必须复用 enqueue、queue mutation、history、settings、environment 和 runtime application services。不要通过自动点击 GUI 工作，也不要创建一套绕过 immutable queue snapshot、validation、logging 或 GPU serialization 的“Agent 快速路径”。

推荐产出 OpenAPI 描述和官方 TypeScript client。MCP 是后续薄 adapter：它把语义化 tools 映射到同一个 API，不拥有独立状态或执行逻辑。

### 3.4 首版继续使用 JSON state，不同时更换数据库

独立后端已经是一次较大的生命周期与信任边界变更。C0 至 C5 继续使用现有 JSON state 和迁移逻辑，通过 `StateRepository` interface 隔离它。

只有在以下证据出现后再立独立 plan 评估 SQLite：

- history snapshot 或写入规模成为已测量瓶颈；
- 需要多实体事务而单文件持久化无法安全表达；
- 需要服务端分页索引且内存投影不足。

### 3.5 HTTP 用于 query/command，SSE 用于服务端事件

首版推荐：

- versioned REST JSON：query、command、resource metadata；
- SSE：state/runtime/progress/log/event stream，支持 `Last-Event-ID`；
- HTTP Range：视频、图片、cover、download；
- multipart upload：浏览器本地文件和 workflow import；
- OpenAPI：API client 与 Agent tool generation。

SSE 足以覆盖当前单向 `webContents.send` 事件，部署和断线恢复也比立即引入双向 WebSocket 简单。只有测量证明 live preview 频率或未来交互需要双向低延迟时，再增加 WebSocket；command 仍应保持普通 HTTP，以便审计、重试和幂等。

### 3.6 Browser 使用 capability-driven UX

Renderer 不应该假设所有 client 都有相同主机能力。建议拆分：

```ts
interface StudioClient { /* query, command, subscribe */ }
interface MediaLocator { /* asset -> authenticated URL */ }
interface AssetTransfer { /* upload, download, import */ }
interface HostCapabilities { /* native picker, reveal, player, window lifecycle... */ }
```

典型 capabilities：

- `nativeFilePicker`
- `hostFileReveal`
- `copyHostFile`
- `systemPlayer`
- `clipboardImage`
- `serverPathVisibility`
- `windowLifecycle`

浏览器不能执行的动作应隐藏或替换为 upload/download；如果操作实际发生在 backend 主机，文案必须明确“在服务器主机打开”，不能让 LAN 用户误以为会打开当前设备。

## 4. 目标架构

```text
Electron GUI       Browser GUI       CLI / Agent       MCP adapter
     |                  |                 |                 |
     +---------- typed StudioClient / OpenAPI client -------+
                                |
                     HTTP commands + SSE events
                                |
                  +-------------v--------------+
                  |       Studio API Host       |
                  | auth / DTO / validation     |
                  | upload / media / audit      |
                  +-------------+--------------+
                                |
                  +-------------v--------------+
                  |      Application Layer      |
                  | StudioRuntime               |
                  | Queue / History / Settings  |
                  | Prompt / Environment        |
                  | EventBus / ResourceArbiter  |
                  +-------------+--------------+
                                |
          +---------------------+----------------------+
          |                     |                      |
   StateRepository       Runtime services         Domain logic
   JSON + migrations     ComfyUI/process/media    src/core/*
          |                     |
   studio-state.json      local/remote ComfyUI
```

### 4.1 建议模块边界

目录名称在实施时可根据现有 convention 调整，但职责必须保持：

```text
src/backend/
  runtime/          StudioRuntime、startup、shutdown、instance lock
  application/      command/query services、resource arbiter
  events/           typed event envelope、revision、subscription
  ports/            StateRepository、StudioPaths、MediaStore、HostOps
  transport/http/   auth、validation、REST、SSE、media、upload
  clients/          shared HTTP client contract（如适合放 src/shared）

electron/
  shell/            BrowserWindow、native menu、dialog、window lifecycle
  adapters/         IPC adapter、Electron host operations、embedded host

src/renderer/
  clients/          ElectronStudioClient、HttpStudioClient
  platform/         MediaLocator、AssetTransfer、HostCapabilities
```

关键要求：不要把现有 `electron/main.ts` 原样移动到 `src/backend/main.ts`。每次抽取必须形成可注入、可单测的 service，并让 Electron composition root 逐步缩小。

### 4.2 应用服务边界

最少拆出以下服务：

- `StateQueryService`：返回经过 client DTO 处理的 snapshot；
- `DraftService`：保存 draft snapshots，但不改变已入队任务；
- `QueueCommandService`：enqueue、start、continue、pause、cancel、reorder、duplicate、reset；
- `QueueExecutionService`：唯一 worker、runtime preparation、ComfyUI submission、completion/recovery；
- `HistoryService`：分页查询、metadata update、delete plan/execute、media identity；
- `SettingsService`：统一 save coordinator 和 migration gate；
- `EnvironmentService`：offline scan、runtime scan、repair/install operation；
- `PromptService`：preflight、lease、enhance、cancel、release；
- `MediaService`：asset-based resolve、Range、cover、upload/import；
- `LifecycleService`：startup recovery、owned processes、graceful shutdown。

所有 transport handler 只负责：认证、schema validation、DTO mapping、调用 service、映射错误和记录 request context。handler 不直接改 store，不直接启动 worker，不直接杀进程。

### 4.3 Event 模型

当前全量 `AppState` 广播不适合作为长期 LAN 协议。引入统一 envelope：

```ts
interface StudioEvent<T = unknown> {
  id: string;          // 单调 event id，可用于 SSE resume
  revision: number;    // backend state revision
  type: string;
  occurredAt: string;
  operationId?: string;
  resourceId?: string;
  payload: T;
}
```

首批 event 类型建议：

- `state.snapshot.invalidated`
- `queue.task.changed`
- `queue.lifecycle.changed`
- `task.preview.available`
- `comfy.runtime.changed`
- `prompt.runtime.changed`
- `prompt.progress`
- `operation.progress`
- `history.changed`
- `server.shutdown`

迁移初期可以在 event 后重新 query snapshot，以降低 renderer 改动风险；随后再把 queue/history 高频路径改为细粒度 patch。必须保留当前 renderer 对 dirty draft、focus、selection、scroll 和 media playback 的保护，不能让网络推送导致本地编辑被远端 snapshot 覆盖。

### 4.4 Command 幂等与并发

- 每个 mutation 接受 `Idempotency-Key`；同一 principal、endpoint 和 key 返回首次结果。
- enqueue 必须在 key 重试时返回同一 task ID，不能重复创建任务。
- settings、draft、metadata update 使用 `expectedRevision` 或 ETag；冲突返回 `409`，不得静默覆盖另一 client 的新状态。
- start/continue/pause/cancel 等 command 在 service 层定义幂等语义。
- 只有 `QueueExecutionService` 能启动 worker；HTTP request 生命周期与 worker 生命周期完全分离。
- 引入 backend command serialization/mutex。现有 `JsonStore.update()` 的 mutator 是同步的，但业务 command 常包含 update 前后的异步检查，不能依靠文件 write chain 自动解决逻辑竞争。
- 单一 `ResourceArbiter` 继续保证同一时间只有一个 heavy GPU generation 或 post-processing stage，并统一 prompt lease 与 queue startup 的冲突策略。

### 4.5 API 资源草案

不是最终 OpenAPI，但用于约束资源模型：

```text

GET    /api/v1/events                # SSE
```

Agent-facing task creation应使用 semantic request（model、mode、asset IDs、prompt、output options），由现有 task factory 产生 immutable snapshot。不要让普通 Agent endpoint 接受未经适配的任意 ComfyUI workflow JSON；高级 workflow import 是独立、受权限控制的资源。

## 5. LAN 与安全模型

### 5.1 默认行为

- 默认只监听 `127.0.0.1` / `::1`；
- LAN 必须由用户显式启用；
- LAN bind 不能自动关闭认证；
- ComfyUI 自身是否对 LAN 暴露与 Studio API 是否对 LAN 暴露是两个独立设置；
- 浏览器永远不直接连接未经保护的本地 ComfyUI，所有操作通过 Studio backend policy。

### 5.2 身份与权限

至少定义三类 scope：

- `viewer`：读取 queue/history、查看 media 和 runtime state；
- `operator`：保存 draft、上传 asset、enqueue、pause/cancel/reorder、prompt request；
- `admin`：settings、path、process、repair/install/uninstall、history/media destructive action、server shutdown。

本机首启生成高熵 bootstrap secret；LAN client 通过一次性 pairing code 换取可撤销 token。token 只存 hash，显示最近使用、scope 和设备名称。不要把长期 bearer token 写进 URL、日志或 media query string。

### 5.3 请求防护

- 精确校验 Host 与 Origin，CORS 使用 allowlist，不使用 `*`；
- bearer token API 不依赖浏览器 cookie，从而降低 CSRF 面；若未来引入 cookie session，必须增加 SameSite 和 CSRF token；
- 每个 endpoint 做结构化 schema validation，限制 body、multipart、文件数量和总大小；
- 检查 MIME、扩展名和实际文件签名；workflow JSON 限制大小、深度和节点结构；
- 所有路径通过 asset ID 或 backend-side allowlist resolve；拒绝 `..`、UNC、device path、symlink escape 和任意 client absolute path；
- media ID 不可猜且仍需授权；支持 Range 但限制并发与每 client 带宽；
- process control、dependency install、delete/migration 使用 admin scope、审计日志和明确确认 token；
- 错误响应不返回服务器绝对路径、环境变量、命令行 secret 或完整子进程输出。

### 5.4 网络边界

首个 LAN release 至少提供以下之一：

- backend 原生 TLS，证书由用户导入；或
- 明确支持放在可信反向代理/VPN 后，并提供部署说明。

纯 HTTP LAN 只能作为显式的受限开发模式，并显示安全警告。Clipboard、部分浏览器媒体和其他 secure-context API 在 HTTP LAN 下也会退化，renderer 应提供 download/copy-text fallback。

### 5.5 审计

记录：principal、scope、client address、operation ID、command、resource IDs、结果和耗时。不要记录 token、完整 prompt 中的潜在隐私内容、上传二进制或未脱敏的本地绝对路径。

## 6. 面向执行 Agent 的总协议

本节是强制执行规则，不是建议。后续 Agent 只能领取一个标记为 `Ready` 的工作包；不能把整个 Phase 当成一个任务，也不能自行合并相邻工作包。

### 6.1 零行为变化原则

进入 Headless 和 HTTP 之前的所有解耦工作包都必须满足：

- Electron 是唯一运行入口，现有 renderer、preload channel、参数、返回值和事件名不变；
- 不修改 persisted `AppState` shape、schema version、defaults、migration 和 JSON 文件位置；
- 不修改 model/workflow、sampler、scheduler、precision、VAE、attention、cache、offload 或 GPU policy；
- 不修改用户可见文案、布局和交互；
- 不新增 HTTP、daemon、SQLite、asset ID、authentication 或 LAN listener；
- 先建立调用缝隙，再移动原逻辑；禁止在移动时“顺便优化”算法、错误文案或状态顺序；
- 每个工作包只有一个行为等价的结构性结果，并且可以整包回退；
- focused test、typecheck 或 required verify 失败时，工作包不得进入 `Review`；不能把失败留给后续工作包。
- 测试列表必须落实为完整命令，例如 `npm.cmd run test -- tests/queue-controls.test.ts`；触及 shared state、IPC、queue、history 或 workflow construction 时还必须运行 `npm.cmd run verify`。
- 同名 `.ts`/`.js` 文件存在时，执行 Agent 必须先确认 source-of-truth；默认编辑 TypeScript source，不得为了“看起来同步”机械修改生成或历史 JavaScript 镜像。

### 6.2 工作包状态与协调者

状态定义：

- `Pending`：依赖未完成；
- `Ready`：依赖、基线和文件所有权已经满足；
- `In Progress`：已记录 owner、base commit 和写入白名单；
- `Blocked`：有具体、可复现的阻塞证据；
- `Review`：实现完成，等待主 Agent 审查完整 diff 和证据；
- `Done`：主 Agent 已审查 diff、测试和 checkpoint 不变量；
- `Superseded`：被新工作包明确替代，保留历史记录。

只有一个 coordinator 可以修改总 Plan 的状态表和 checkpoint。执行 Agent 不得自行把 checkpoint 标记为通过。WP-00 将本 Plan 和 ADR 提交为稳定文档基线；后续 Agent 必须以包含该文档基线的仓库 HEAD 为执行起点，不能使用未提交副本或旧对话 snapshot。

### 6.3 每个 Agent 的开始动作

执行 Agent 必须按顺序：

1. 运行 `git status --short`，记录 base commit；
2. 完整阅读本 Plan、适用 contract 和该工作包列出的目标文件；
3. 用 `rg` 重新生成调用/import inventory，不依赖旧对话中的行号；
4. 写出本工作包的 preserve list；
5. 确认写入白名单未被其他 Agent 占用；
6. 重新读取每个目标文件后再编辑；
7. 如果目标文件在开始后发生变化，立即停止并交给 coordinator reconcile。

### 6.5 全局停止条件

出现以下任一情况，执行 Agent 必须停止，不得自行扩大 scope：

- 需要编辑写入白名单之外的 hotspot；
- 需要修改 persisted/public contract，但工作包没有 migration 决策；
- 需要复制一套 validation、queue worker、runtime state 或 media resolution 才能继续；
- baseline 已失败，且无法区分原有失败与本包回归；
- 需要让 Electron adapter 直接访问新的 store/worker 内部状态；
- 需要让 HTTP client 传服务器绝对路径；
- destructive media/process 操作的 owner、目标或确认语义不明确；
- transport-neutral 模块只能通过 import Electron 才能测试；
- 单个工作包扩展到两个以上 application area；
- 发现当前实现与 contract 冲突，需要产品决定。

### 6.6 并发和文件所有权

- 共享根 worktree 同一时间最多一个 production-code writer；真正并行实现应使用独立 worktree/branch。
- `electron/main.ts`、`src/main.ts`、`src/types.ts`、`electron/store.ts`、`package.json`、root lockfile 始终单 owner。
- `electron/main.ts` 的 application extraction 必须串行；不同 Agent 不能同时抽 settings、history 和 prompt。
- Renderer client contract、context 和 `src/main.ts` 迁移也必须串行。
- 只读 inventory、测试矩阵和威胁模型可以并行。
- 执行 Agent 不修改版本文件；只有 release owner 在 checkpoint release 时统一 bump。

### 6.7 交接报告格式

每个 Agent 必须报告：

- base SHA、head SHA 和 `git status --short`；
- `git diff --name-status` 与实际编辑文件；
- focused tests、typecheck、verify 的完整命令、退出码和测试数量；
- Electron manual UI 是否执行；
- ComfyUI 是 offline、connected 还是实际执行；
- 哪些结论只是 static validation；
- persisted-state fixture 是否覆盖旧版本；
- 未解决风险、下一工作包前置条件和整包回滚方式。

仅写“测试通过”“已解耦”“功能正常”不算可接受证据。

## 7. Checkpoint 与依赖顺序

### 7.1 强制执行顺序

```text
C0  Plan/contract/baseline 固定
 |
C1  Electron 内部健康模块化
 |   paths/events -> queue seams -> history/settings/prompt/environment/media
 |   -> repository port -> lifecycle -> embedded StudioRuntime
 |
C2  Transport-neutral backend Gate      R  Renderer client seam（可从 C0 后串行穿插，仍只走 IPC）
 |                                      |
C3  Headless Node process（无 HTTP）     R-Gate
 |
C4  Loopback read-only HTTP -> asset upload -> commands -> SSE/media
 |
C5  Localhost browser -> Agent/CLI
 |
C6  LAN security and release
```

禁止跳过 C2 直接开发 HTTP。禁止先建立一个包含旧 `electron/main.ts` 全部职责的巨型 `StudioRuntime`。完整 `StudioRuntime` 必须在 application services 已经抽取后才负责 composition。

### 7.2 Checkpoint 机械 Gate

#### C0 — 稳定执行基线

- Plan 已提交并有稳定 base SHA；
- Architecture Contract delta 已批准，但尚未把未来行为写成当前事实；
- IPC/event/startup/renderer client inventory 有 characterization tests；
- `npm.cmd run verify` 在任何生产重构前通过；
- coordinator 已记录当前已有用户修改和所有 hotspot owner。

#### C1 — Embedded application layer

- 每个 application service 可不创建 `IpcMain` 直接测试；
- Electron IPC channel、payload、return、error 文案不变；
- Electron 仍是唯一入口，关闭行为保持现状；
- `electron/main.ts` 只负责 composition、Electron shell、native adapter 和 bridge；
- 完整 Electron Create -> Queue -> History -> Settings 回归通过。

#### C2 — Transport-neutral backend complete

只有满足全部条件才允许 HTTP：

- application、runtime 和 ports 模块不 import `electron`；
- public service API 不出现 `IpcMain`、`BrowserWindow`、`WebContents` 或 IPC channel；
- IPC adapter 不直接 `store.update()`、启动 worker 或 kill process；
- 业务路径不直接调用 `app.getPath()`；Electron composition root 只负责构造 `StudioPaths`；
- enqueue 通过 image inspection port，不直接依赖 `nativeImage`；
- business events 只进入 `StudioEventSink/EventBus`；`webContents.send` 只存在于一个 Electron bridge，window close shell event 除外；
- queue、draft、settings、history、prompt、environment、runtime control 的 contract tests 均不创建 Electron；
- Node integration test 可完成 load -> recover -> subscribe -> command -> persist -> stop；
- Electron IPC parity tests、`npm.cmd run verify` 和手工 desktop smoke 通过。

C2 只审核 backend application/runtime 边界，不依赖 renderer WP-R00–WP-R07。Renderer seam 有自己的 R-Gate；localhost browser 必须同时依赖 C4 和 R-Gate。

#### C3 — 独立 Headless process

- 普通 Node 进程可启动、持有唯一 data-directory lock、恢复 state 并安全退出；
- 不创建窗口、不注册 IPC、不监听 HTTP；
- GUI/client 断线与 backend shutdown 已分离；
- 本地 ComfyUI 由 backend owner 管理，remote endpoint 仍 connection-only。

#### C4 — Loopback API

- 默认只绑定 loopback 且需要认证；
- read-only foundation、asset import、commands、SSE 和 media 分开交付；
- public enqueue 只接受 opaque asset ID，不接受 client absolute path；
- mutation 具有 idempotency、revision 和审计证据。

#### C5/C6 — Browser、Agent 与 LAN

- Electron 与 browser 共享 client/application contract；
- Agent/CLI 不绕过 queue/workflow validation；
- LAN 默认关闭；开启后 scope、pairing、TLS/可信代理、Origin/Host、quota、audit 全部通过安全 Gate。

### 7.3 Checkpoint 与版本

- C0：documentation 或 patch，无用户能力；
- C1/C2：内部重构，单独发布时是 patch；
- C3/C4：可选 headless/localhost API 是新能力，minor；
- C5：browser 和 Agent/CLI 是新能力，minor；
- C6：LAN opt-in 是新能力和安全边界，minor。

工作包可以各自形成原子 commit，但不各自 bump。release owner 在 checkpoint 发布时统一更新 package、lockfile、README、CHANGELOG，并运行版本与全量验证。

## 9. 前后端能力阶段（仅在 C2 通过后执行）

以下是 capability roadmap，不是单个 Agent 的任务。每一项在实施前仍要按 Section 6.4 拆成具体工作包。

### Phase H1 — Instance lock

- 为 data directory 建立 Windows-safe lock、owner metadata、stale detection 和 recovery tests。
- embedded 与 standalone 均通过同一个 lock policy；第二个 writer 必须失败或连接既有 backend。
- 不与 StateRepository interface 或 StudioRuntime extraction 同包实施，因为它改变 startup failure semantics。

### Phase H2 — Headless Node process（无 HTTP）

- 新增独立 entry/config/logging；复用 C2 的 StudioRuntime。
- 处理 SIGINT/SIGTERM、startup failure、graceful drain、forced cleanup。
- 验证无 Electron import/window/IPC 即可 load、recover、执行 application command、persist 和 stop。
- 行为通过后再更新 `docs/ARCHITECTURE_CONTRACT.md` 和 `docs/AGENT_START_HERE.md`，把 backend owner/headless entry 写成当前事实；实现前只在 ADR 中记录未来态。

### Phase A1 — Loopback HTTP foundation

- 只提供 health、server info、capabilities、认证、request ID、typed errors 和 read-only query。
- 默认 loopback；未认证不能读 state/media。
- 不在此包加入 mutation、SSE、upload 或 browser。
- read-only transport 验证通过后再更新 Architecture Contract 的 transport trust boundary；不能先用文档宣布未实现的 HTTP ownership。

### Phase A2 — Asset registry 与 upload/import

- 在公开通用 enqueue 前先提供 opaque asset ID、受控 inbox 和 multipart validation。
- legacy server-side media 可由 backend 注册，但 client 不传绝对路径。
- MIME/signature/size/path sandbox tests 独立完成。

### Phase A3 — HTTP commands

- 按 queue -> draft -> prompt -> history metadata -> settings -> admin 的顺序逐组映射现有 application services。
- mutation 加 idempotency key、revision/ETag、operation ID 和 audit。
- destructive/admin command 使用 scope 和 confirmation challenge。

### Phase A4 — SSE events

- 单调 event ID、有限 replay、`Last-Event-ID`、slow subscriber、overflow 和 snapshot fallback 独立交付。
- progress 可节流；terminal state/history mutation 不可丢。
- SSE listener 不能拥有或启动 worker。

### Phase A5 — HTTP Media/History

- asset/media ID resolve、Range、ETag、cover、download 和 history pagination。
- API response 默认不泄露 absolute path。
- Electron `studio-media://` 继续作为兼容 adapter，直到 browser parity 完成。

### Phase B1 — Localhost browser

- 前置：C4 Loopback API、R-Gate 和 WP-R07 全部通过。
- 新 browser entry 注入 HttpStudioClient；unsupported host capabilities 必须显式 unavailable。
- picker/drop 走 upload；Explorer/system player/window close 不伪装成功。
- 先完成 localhost refresh、deep link、reconnect、upload、media playback 和 Electron parity。

### Phase G1 — Agent/CLI/MCP

- OpenAPI 和 TypeScript client 稳定后再提供 CLI；MCP 是薄 adapter。
- Agent 完成 upload -> validate -> enqueue -> observe -> download，不绕过 workflow/queue validation。
- 默认无 destructive/admin scope。

### Phase L1 — LAN hardening

- pairing、token revoke/rotate、viewer/operator/admin、TLS/可信代理、Origin/Host、quota、rate/connections、audit。
- 首版建议把 dependency install、force-stop 和 server shutdown 限制在 loopback admin。
- LAN browser、slow client、多 client conflict、malicious upload、path escape 和 token revoke 全部通过后才能发布。

## 10. 被取代的宏观路线

最初版本曾把 Ports/EventBus/StudioRuntime 放在 application services 之前，并把 headless、HTTP、SSE、auth 和 commands 合成大 Phase。该顺序会制造第二个巨型 Runtime，也不适合低上下文 Agent 执行，现已被 Sections 6–9 的原子工作包和机械 Gate 完全取代。

本节没有可执行任务。需要追溯旧方案时使用 Git 历史；不要从旧对话或旧 Plan snapshot 恢复已被取代的 Phase。

## 11. Preserve list

整个重构必须保留：

- draft 修改绝不改变已经 queued/running 的任务快照；
- queue pause boundary、reorder、continue、cancel、retry 和 recovery 语义；
- 同一时间只有一个 heavy GPU generation/post-processing stage；
- prompt model lease 与 queue runtime profile 切换规则；
- app-managed local ComfyUI 单实例接管和退出清理；remote ComfyUI 始终 connection-only；
- selected/discovered/connected ComfyUI 三者区分，offline scan 仍可工作；
- 多 ComfyUI installation 的明确选择，不自动偷换 selected instance；
- H3、Qwen image、Sulphur、SeedVR2 和 legacy records 的运行策略隔离；
- 旧 `studio-state.json`、queue/history records、media fallback 和 workflow IDs 可读取；
- 原始输入、生成媒体、cover 和 temporary file 的身份区分；
- destructive media 操作需要确认，并报告 partial failure；
- renderer typing、focus、selection、drag/drop、scroll 和 media playback 不因推送刷新重置；
- History detail 的父导航上下文和长页面主操作可达性；
- Electron desktop 在每个迁移 checkpoint 都保持可运行、可回退。

## 12. 验证矩阵

### 12.3 API 与安全

## 13. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| Electron 与 daemon 双写 JSON | state 丢失、queue/history 互相覆盖 | 唯一 owner、data-dir lock、所有 client 走 API |
| 将 IPC 原样公开为 HTTP | 任意路径、进程和删除能力外泄 | application service + DTO + scope，不做一比一映射 |
| 网络重试重复 enqueue | 重复 GPU 任务和媒体 | idempotency key、operation record、稳定 task ID |
| 多 client 覆盖设置/draft | 用户编辑丢失 | revision/ETag、409、dirty draft merge policy |
| 全量 AppState 广播 | 大 history 下带宽/渲染抖动 | typed event、分页、snapshot invalidation、局部 query |
| 浏览器路径语义错误 | 上传文件不可用或泄露服务器路径 | opaque asset ID、upload/import、capability UX |
| GUI 关闭误杀独立任务 | headless 价值失效 | embedded/standalone 显式 lifecycle policy |
| daemon 崩溃遗留 ComfyUI | 端口/进程所有权混乱 | owned-process registry、startup reconciliation、graceful signals |
| LAN token 泄露 | 媒体和管理能力被接管 | pairing、hash storage、scope、revoke、TLS、redacted logs |
| 同时改数据库/后端/前端 | 回归难定位、回滚困难 | 首版保留 JsonStore，阶段可独立合并回退 |

## 14. 暂不做事项

在本计划前半程不做：

- 不把 ComfyUI 直接暴露给 browser/Agent 作为产品 API；
- 不允许多个 backend 共享写同一 data directory；
- 不同时迁移 SQLite 或重写所有 persisted types；
- 不删除 Electron IPC fallback，直到 HTTP client 达到行为等价；
- 不以远端路径字符串作为 asset identity；
- 不默认监听 `0.0.0.0`；
- 不在无认证情况下提供 LAN；
- 不让普通 operator 执行 install/uninstall/repair/process stop/delete；
- 不把 MCP adapter 做成第二套业务后端；
- 不因为浏览器化改变 workflow、模型精度、scheduler、sampler、VAE、attention、cache 或 offload policy；
- 不在没有真实证据时声明 headless runtime、LAN 或 GPU generation 已工作。

## 16. 发布与回滚策略

建议按多个 checkpoint 发布，而不是等待所有阶段后一次切换；内部解耦 checkpoint 是 patch，新 capability checkpoint 才是 minor：

1. 内部 application layer，用户行为不变；
2. 可选 headless localhost server；
3. localhost browser preview；
4. Agent/CLI beta；
5. LAN opt-in beta；
6. standalone daemon 稳定后再评估桌面默认切换。

每个 checkpoint：

- 旧 state 不做破坏性迁移；新增字段 additive 且有 defaults；
- 保留 embedded Electron fallback；
- 新 backend 无法启动时，Electron 可在明确提示后回到 embedded mode；
- 版本、README current-version 和 CHANGELOG 按发布规则同步；
- 不自动删除旧 media protocol、token、state backup 或 server config；清理另立明确 migration。

## 17. 完成定义

只有以下条件全部满足，才能认为本重构目标完成：

1. backend 可在没有 Electron/GUI 的普通 Node 进程中启动、恢复、执行队列并安全退出。
2. Electron、browser、CLI/Agent 使用同一 application services 和业务契约。
3. browser 不依赖 Electron preload、绝对路径或 `studio-media://`。
4. localhost API 默认受认证保护；LAN 默认关闭且启用后具有权限、TLS/可信代理、审计和限额。
5. 多 client 不会产生重复 worker、重复任务、状态覆盖或 GPU 并行冲突。
6. GUI/window/client disconnect 不影响 standalone backend；embedded mode 仍保留当前退出语义。
7. 旧 state、queue/history/media 和 model/workflow runtime policy 兼容。
8. Electron、本机浏览器、LAN 浏览器、CLI/Agent 的验证矩阵通过。
9. 至少一次真实 minimal ComfyUI generation 通过 headless API 完成，输出可由 browser/Agent 获取；在此之前只能声明静态或集成验证通过。

## 18. 审批前需要确认的产品决定

以下决定不阻塞 C0 的调查和 characterization，但在进入对应阶段前必须确认：

1. standalone backend 是手动启动、托盘托管，还是最终作为 Windows service 安装；推荐先手动/console，再评估托盘或 service。
2. Electron 默认继续 embedded，还是在 standalone 稳定后自动连接常驻 backend；推荐先保留 embedded 默认。
3. LAN 首版采用 backend 原生 TLS，还是明确依赖用户的 VPN/可信反向代理；不建议把裸 HTTP 作为正式默认。
4. Agent 首版只提供 OpenAPI/CLI，还是同时提供 MCP adapter；推荐先稳定 OpenAPI，再加薄 MCP adapter。
5. 是否允许 admin 在 LAN 上执行 dependency install 和 process force-stop；推荐首版将这类动作限制为 loopback admin。
